# Redis 功能篇

## 过期删除策略

### 过期时间

Redis 可以给 key 设置过期时间，常见命令如下：

| 命令 | 作用 |
| --- | --- |
| `EXPIRE <key> <n>` | 设置 key 在 `n` 秒后过期。 |
| `PEXPIRE <key> <n>` | 设置 key 在 `n` 毫秒后过期。 |
| `EXPIREAT <key> <n>` | 设置 key 在某个时间戳后过期，精确到秒。 |
| `PEXPIREAT <key> <n>` | 设置 key 在某个时间戳后过期，精确到毫秒。 |

设置字符串时，也可以同时设置 key 的过期时间：

| 命令 | 作用 |
| --- | --- |
| `SET <key> <value> EX <n>` | 设置键值对时，指定过期时间，精确到秒。 |
| `SET <key> <value> PX <n>` | 设置键值对时，指定过期时间，精确到毫秒。 |
| `SETEX <key> <n> <value>` | 设置键值对时，指定过期时间，精确到秒。 |

Redis 会维护一个**过期字典**，用于保存 key 的过期时间，该字典存储在 `redisDb` 结构中。

读取 key 时，Redis 的判断流程如下：

1. 先检查 key 是否存在于过期字典中。
2. 如果 key 不在过期字典中，则正常读取键值。
3. 如果 key 在过期字典中，则读取过期时间。
4. 如果 key 未过期，则正常返回键值。
5. 如果 key 已过期，则删除 key，并返回空值。

### 过期删除策略

常见的过期删除策略有三种：

| 策略 | 说明 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 定时删除 | 设置 key 的过期时间时，同时创建一个定时事件。时间到达后，由事件处理器自动删除 key。 | 过期 key 能及时删除。 | 对 CPU 不友好，过期 key 很多时会增加调度和删除开销。 |
| 惰性删除 | 不主动删除过期 key，每次访问 key 时才检查是否过期。如果过期，则删除 key。 | 对 CPU 友好，只有访问时才检查。 | 对内存不友好，长期不访问的过期 key 可能一直占用内存。 |
| 定期删除 | 每隔一段时间，随机从数据库中取出一定数量的 key 进行检查，并删除其中的过期 key。 | 在 CPU 和内存之间折中。 | 删除不够彻底，执行频率和扫描时长需要控制。 |

Redis 通常使用**惰性删除 + 定期删除**的组合策略。

#### 惰性删除流程

Redis 在读取 key 时会进行过期检查：

1. 如果 key 已过期，则删除 key，并返回空值。
2. 如果 key 未过期，则不处理，正常返回键值。

其中，过期 key 是同步删除还是异步删除，可以通过配置进行控制。

#### 定期删除流程

Redis 默认每秒进行 10 次过期检查。每轮检查流程如下：

1. 随机抽查 20 个 key。
2. 检查这 20 个 key 是否过期，并删除其中已经过期的 key。
3. 如果已过期 key 的数量超过 5 个，也就是超过 25%，则继续重复抽查。
4. 如果已过期 key 的比例小于 25%，则停止本轮检查，等待下一轮。

为了防止定期删除流程循环过久，Redis 会给定期删除流程设置时间上限。

## 内存淘汰策略

Redis 的最大运行内存可以在配置文件中通过 `maxmemory` 设置。

只有当 Redis 的运行内存达到 `maxmemory` 限制时，才会触发内存淘汰策略。

不同系统中的默认值通常不同：

- 64 位系统中，`maxmemory` 默认通常为 `0`，表示没有内存大小限制。
- 32 位系统中，`maxmemory` 默认通常为 `3GB`，因为 32 位机器支持的最大内存约为 `4GB`。

### 内存淘汰策略类型

常见的内存淘汰策略可以按选择规则分为几类：

| 类型 | 说明 |
| --- | --- |
| 不淘汰 | 不进行数据淘汰。 |
| `random` | 随机淘汰 key。 |
| `ttl` | 优先淘汰更早过期的 key。 |
| `lru` | 淘汰最近最少使用的 key。 |
| `lfu` | 淘汰最近最不常用的 key。 |

### LRU：最近最少使用

LRU 全称是 Least Recently Used，表示**最近最少使用**。

传统 LRU 通常使用链表实现，每次访问数据时，把数据移动到链表尾部；淘汰时，只需要删除链表头部即可。

Redis 没有使用完整链表实现严格 LRU，而是使用**随机采样**：

1. 随机选择若干个 key。
2. 在这些 key 中，选择最久没有被访问的 key 进行淘汰。

这样可以降低维护完整 LRU 链表的内存和时间开销。

### LFU：最近最不常用

LFU 全称是 Least Frequently Used，表示**最近最不常用**。

Redis 会维护一个 `lru` 字段：

- 在 LRU 算法中，`lru` 用于记录 key 的访问时间戳，从而判断最近访问时间。
- 在 LFU 算法中，`lru` 会被拆成两段：
  - 高 16 bit 存储最后访问时间；
  - 低 8 bit 存储访问频次。

因此，LFU 不只关注 key 最近有没有被访问，还会关注 key 的访问频率。

## 多节点的资源争抢

在多节点场景下，如果多个客户端同时争抢同一个共享资源，就需要使用锁来控制并发访问。

Redis 分布式锁常见问题和解决思路如下：

| 问题 | 说明 | 解决思路 |
| --- | --- | --- |
| 锁争抢 | 多个客户端同时尝试获取同一把锁。 | 将“判断锁是否被占用”和“占用锁”合并成一个原子操作，例如使用 `SETNX`。 |
| 僵尸锁 | 客户端加锁后异常退出，导致锁一直不释放。 | 给锁设置过期时间。 |
| 锁过期 | 业务还没执行完，锁已经过期，其他客户端可能拿到锁。 | 使用看门狗机制自动续期。 |
| 不可靠锁 | 单个 Redis 节点故障时，锁状态可能丢失。 | 使用 Redlock 机制，通过多个锁服务器保证多数成功才视为加锁成功。 |
