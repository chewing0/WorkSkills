在Redis中，如果所有的服务都放在一台机器上，放在单个Redis实例中，该实例宕机时，整个服务都将变得不可用；如果该服务器硬件损坏，可能导致严重的数据丢失。
因此需要对服务器进行备份，多台服务器存储相同的数据……有点类似磁盘阵列的冗余hhhh

这里引申出问题：数据如何同步？到底哪一台服务器向外提供服务？提供服务的服务器故障了，怎么进行故障转移？故障的服务器恢复后又应该怎么样？
# 主从复制

主从复制模式保证数据的一致性，并且主从节点采用读写分离的模式。主服务器执行读写操作，发生写操作时，把写操作同步给从服务器，实现数据同步；从服务器一般是只读，并接收主服务器发来的写命令，执行命令实现同步。
```
replicaof 192.168.1.10 6379
```
意思是：
```
当前 Redis 实例复制 192.168.1.10:6379 这个主节点
```
## 第一次同步

![主从服务器第一次同步流程图](images/主从服务器第一次同步流程图.png)

**Step 1：** 建立连接，协商同步
执行`replicaof`命令后，确定了主从关系。从节点会给主节点发送`psync`命令，表示要进行数据同步。
psync命令包含两个参数，分别是**主服务器的runID**和**复制进度offset**。
- runID：每个 Redis 服务器启动时自动生成的**唯一标识符**（40 位十六进制随机字符串）。从节点通过 runID 判断之前复制的是否还是当前这台主节点——如果不同，说明主节点已重启或从节点连错了主节点，需要触发**全量复制**。
- offset：**复制偏移量**，表示主节点累计发送给从节点的字节位置。主从节点各自维护 offset，通过对比可判断数据是否一致。从节点在 `psync` 中上报自己的 offset，主节点检查该 offset 是否仍在复制积压缓冲区（replication backlog）内：在则触发增量复制，否则触发全量复制。
主服务器收到命令后，判断是否可以进行增量同步，不行则进行全量同步（通常第一次同步都是全量同步）。返回`FULLRESYNC`响应命令，意思是进行全量复制。

**Step 2：** 主服务器同步数据给从服务器
主服务器会执行bgsave命令，生成RDB快照，并且交给从节点进行复制。这里就会引申出问题：新产生的写命令怎么办？
主服务器会把生成RDB快照时产生的新的写命令、发送RDB快照时产生的写命令、从服务器加载RDB快照时产生的写命令都缓存到缓冲区。

**Step 3：** 新命令写入
从服务器加载完成后，向主服务器上报完成。主服务器把缓存的写命令发送给从服务器进行同步，从而实现同步。这里仍然有可能存在新命令产生没有传递的情况，但是这里已经足够接近。

## 命令传播

主从服务器第一次同步完成后，会在二者之间建立一个长连接的TCP连接。后续主服务器可以通过这个连接将新的写命令传递给从服务器。长连接的目的是避免频繁的TCP建立，增加系统的开销。

## 压力分摊

主服务器可以有多个从服务器，但是如果主服务器要和多个从服务器都进行全量同步和通信，那么主服务器的压力同样会增加，主进程会被同步任务阻塞。这里可以采用多级结构，即把一些从服务器变成“孙子服务器”，挂在从服务器下。
主服务器给从服务器同步写命令，从服务器同步后给“孙服务器”同步。
主服务器负责写操作和读操作，其余服务器均负责读操作。

## 增量复制

如果主从服务器之间连接断开，等到连接再度连接时，就需要进行新一次的同步。这里尽量希望不需要全量同步，不然整体的开销太大了。
做法是，主服务器维护一个环形缓冲区，并记录一个offset标志主服务器的写命令写到哪里了。从节点同样维护一个offset表示自己读到哪里了。同步时，主服务器会根据从服务器的offset判断缺失的写命令在不在缓冲区。

存在断连时间太长，环形缓冲区被覆盖了一部分，这时候就一般需要重新进行全量同步。这里，环形缓冲区repl_backlog_buffer的size就很重要了。
## 总结

主节点负责处理写入，并把数据变化以复制流的形式发送给从节点；从节点执行相同的数据变更，从而尽量保持和主节点一致。


# 哨兵模式

上面的主从复制解决了单一Redis实例宕机后，无可用服务节点的问题。只需要选择一个从节点，作为新的主节点即可。但是这又出现了一个问题，谁监视并上报主节点情况？选择谁作为新的主节点？手动选择or自动选择？自动选择怎么做？
## 哨兵模式工作机制

一个节点通常设置多个哨兵，负责对节点的情况进行监控；在节点下线后，选择新的主服务器；通知现在新的主服务器。
## 故障判断

哨兵模式判断主节点故障通常分为两个阶段，主观下线和客观下线。
哨兵会每隔一秒给主服务器发送一个ping消息，主服务器收到消息后给哨兵回复pong消息。如果在一定时间内，哨兵没有收到回复，则认为主服务器下线了，把主服务器情况设置为**主观下线**。
接着向其他哨兵询问主服务器情况如何，如果超过设定数量的哨兵认为主服务器主观下线了，则认为服务器下线，接着哨兵把主服务器情况设置为**客观下线**。接着启动故障转移的程序。
## 故障转移

Q1：确定哪个哨兵作为leader进行故障转移
所有判断主服务器**主观下线**的哨兵都会成为候选人。接着开始投票，拿到超过设定数量票数的哨兵成为故障转移的leader。每个哨兵会首先给自己投一票，紧接着给其他哨兵发送给我投票的消息，哨兵会把自己的票投给第一个收到的投票请求方，直到自己手里的票投完。
哨兵节点个数一般设置为奇数，至少是quorom值的二分之一加一。

Q2：确定谁作为新的主服务器
step1：选择新的主服务器
首先，Redis维护一个down-after-milliseconds的配置项，是主从节点断连的最大超时时间，如果在这个时间内没有恢复连接，则认为断连一次。超过十次断连的节点，认定为网络状态不良。哨兵首先过滤网络状态不良的节点。
接着，按照预先设定的优先级，对余下的从节点进行筛选。优先级越高，则有限考虑作为新的主节点。优先级的设置可能考虑节点服务器的性能配置等。
之后，如果存在优先级一致的节点，考虑节点的复制进度。前面我们提到主节点维护一个环形缓冲区，主从节点分别维护一个写、读的进度。复制进度高的优先考虑作为新的主节点。
最后，如果还没选出来，每个Redis实例都有一个唯一的runID，选择ID最小的节点作为新的主节点。
选择新的主节点后，哨兵leader向新的主节点发送slaveof no one命令，让从节点把自己升级为主节点。紧接着，leader会持续向被选中的从节点发送info命令，查看该节点信息，直到该节点把自己更新为master（主节点）
step2：通知其他节点新的主节点
leader会向其他从节点发送slaveof命令，把其他从节点的主节点更新为新的主节点。
step3：通知客户端新的主节点
Redis通过发布者/订阅者机制向客户端通知主节点更新的消息。
step4：已下线节点重连
哨兵会继续监视已经下线的节点，如果重连，将其设置为当前主节点的从节点。

## 哨兵集群

上面我们提到哨兵通常是多个，哨兵集群的形成依赖Redis的发布者/订阅者机制。主节点上存在一个频道`__sentinel__:hello`，哨兵A会把自己的ip和端口号发布在这个频道，哨兵B、C订阅该频道就可以得到A的信息。他们就可以建立网络，同理哨兵B也可以这样和C取得联系。同时哨兵又通过info命令从主节点得到从节点的信息。从而形成哨兵网络集群。
