# Multi-Agent 总览

Multi-Agent 的直觉很容易理解：一个复杂任务交给一个 Agent 太重，那就拆给多个 Agent。比如一个软件开发任务可以拆成产品分析、架构设计、编码、测试、代码审查；一个研究任务可以拆成资料检索、事实核验、观点整理、反方质疑、最终写作。

但真正难的地方不在“拆”，而在“拆完之后如何合回来”。多 Agent 不是把多个模型输出拼起来，而是在一个受控系统里组织多个智能单元，让它们各自承担明确职责，同时通过通信、共享状态、调度和评估形成稳定闭环。

---

# 1. 为什么需要 Multi-Agent

多 Agent 的价值主要来自四类需求。

第一是专业分工。单个 Agent 可以被要求同时做规划、检索、编程、评审和总结，但角色越多，指令越复杂，输出越容易摇摆。把角色拆开后，每个 Agent 的目标更窄，Prompt 更稳定，工具权限也更容易控制。

第二是并行处理。很多任务天然可以并行，例如同时检索多个资料源、让多个候选方案独立生成、让测试 Agent 和实现 Agent 分别处理不同分支。并行不一定降低 token 成本，但可以降低 wall-clock latency，也能提升候选解的多样性。

第三是互相校验。LLM 容易自信地产生错误。让一个 Agent 生成，另一个 Agent 按证据、规范或测试结果审查，可以把一部分错误暴露出来。这里的关键不是“另一个 Agent 更聪明”，而是它有不同任务目标、不同上下文和不同评价标准。

第四是权限和责任隔离。生产系统里，并不是所有步骤都应该有同样权限。研究 Agent 可以联网检索，执行 Agent 可以调用内部 API，审批 Agent 只负责判断风险，审计 Agent 只读 trace。角色拆分使权限最小化更自然。

---

# 2. Multi-Agent 不是万能增强器

多 Agent 经常被误解成“Agent 越多越智能”。实际情况相反：Agent 数量增加后，系统复杂度通常增长得更快。

主要代价包括：

- 通信成本：Agent 之间需要传递上下文，消息越多，token 越多。
- 协调成本：谁先做、谁后做、谁负责合并，都需要编排。
- 一致性成本：多个 Agent 的假设、术语和中间状态可能不一致。
- 评估成本：最终答案错了，要定位是拆解错、检索错、执行错、评审错，还是合并错。
- 延迟成本：串行协作会变慢，并行协作也要等待最慢分支。
- 安全成本：更多 Agent 意味着更多工具入口和更多越权路径。

因此，多 Agent 只有在“分工带来的收益”大于“协调带来的损耗”时才值得使用。

# 3. 最小构成

一个多 Agent 系统至少包含这些元素：

```text
目标
  │
  ├─► Agent 角色：每个 Agent 的职责、能力边界、输出契约
  ├─► 工具集合：每个 Agent 能调用哪些工具，权限如何限制
  ├─► 通信机制：Agent 之间如何发送消息、转交任务、请求帮助
  ├─► 共享状态：哪些信息全局可见，哪些只属于局部上下文
  ├─► 调度逻辑：谁决定下一步，如何重试、并行、终止
  └─► 质量控制：如何评审、裁决、记录和回滚
```

如果一个系统只是顺序调用几个 Prompt，但没有角色边界、通信协议、状态管理和调度逻辑，它更像一个 chain 或 workflow，而不是真正意义上的多 Agent。

这并不是贬义。很多业务问题用 workflow 反而更可靠，因为路径明确、状态简单、测试容易。

---

# 4. 单 Agent、Workflow 与 Multi-Agent

三者的边界可以这样理解：

| 形态 | 核心特征 | 适合场景 |
|---|---|---|
| 单 Agent | 一个循环负责规划、工具调用和结果整合 | 中等复杂度、目标连续、工具数量有限 |
| Workflow | 由系统预定义步骤和分支 | 高确定性业务流程、审批流、ETL、固定 RAG 链路 |
| Multi-Agent | 多个角色通过消息、状态和调度协作 | 复杂开放任务、多专业分工、互相评审、并行探索 |

选择时不要从框架出发，而要从任务结构出发。

如果任务路径清楚，优先 workflow。如果任务需要少量动态决策，用单 Agent。如果任务需要多个能力域、多个视角或多个权限边界，再考虑 Multi-Agent。

# 5. 常见失败模式

多 Agent 系统最常见的问题不是“某个 Agent 不够聪明”，而是系统边界没设计好。

角色重叠会导致重复工作。两个 Agent 都认为自己负责规划，结果互相覆盖方案；两个 Agent 都能写文件，结果状态互相踩踏。角色不是名字，而是职责、权限和输出契约。

通信过度会导致上下文污染。把所有对话都广播给所有 Agent，看似透明，实际会让无关信息进入每个 Agent 的上下文，造成误引用、偏题和 token 浪费。

停止条件不清会导致循环讨论。生成 Agent 反复改，评审 Agent 反复提意见，协调 Agent 反复要求重试。如果没有预算、轮次、置信度和人工介入条件，系统会无限消耗。

裁决机制薄弱会导致“群体幻觉”。多个 Agent 都基于同一个错误前提推理，互相赞同并不会让答案更正确。质量控制必须引入证据、测试、外部工具或明确标准。

---

# 6. 设计原则

好的多 Agent 设计通常遵循几条原则。

第一，少即是多。先用最少的 Agent 完成闭环，再在明确瓶颈处拆分角色。每新增一个 Agent，都要说明它降低了什么复杂度。

第二，角色要可执行。不要只写“你是专家”，而要写清楚输入、输出、可用工具、不可做的事、完成标准和失败时如何处理。

第三，状态要显式。关键中间结果不要只藏在聊天历史里，而要进入结构化状态，例如任务列表、证据表、文件变更、决策记录、风险清单。

第四，通信要有契约。Agent 消息最好有类型、来源、目标、任务 ID、状态、摘要和证据，而不是随意自然语言长聊。

第五，评估要看过程。多 Agent 的错误往往发生在中间步骤，最终答案只能告诉你“错了”，trace 才能告诉你“在哪里错”。
