# 生产治理、安全、成本与评估

Multi-Agent 在原型阶段很容易让人兴奋，因为多个角色会产生一种“团队在工作”的感觉。但生产系统不能只看过程是否像人，而要看结果是否稳定、成本是否可控、风险是否可治理、失败是否可定位。

多 Agent 系统上线的难点，不是多写几个 Agent，而是把它们变成一个可运营的软件系统。

---

# 1. 生产级关注点

生产级 Multi-Agent 至少要关注这些问题：

```text
可靠性：任务是否稳定完成？
安全性：工具权限是否可控？
成本：token、工具、模型调用是否超预算？
延迟：多轮协作是否还能满足响应时间？
可观测性：失败时能否定位哪一步错了？
可恢复性：中断后能否从 checkpoint 继续？
可评估性：改 Prompt、模型或路由后是否知道变好还是变差？
```

如果这些问题没有答案，多 Agent 越复杂，线上风险越大。

---

# 2. 安全边界

多 Agent 的安全风险比单 Agent 更高，因为攻击面更大。

常见风险包括：

- 一个 Agent 被外部文本诱导，向其他 Agent 传播恶意指令。
- 检索 Agent 把 prompt injection 内容写入共享记忆。
- 执行 Agent 调用了超出任务范围的工具。
- 审查 Agent 因上下文不足放行高风险操作。
- 多个低风险动作组合成高风险结果。

治理方式包括：

- 系统指令和工具结果分层，不让外部内容覆盖系统规则。
- 共享记忆写入前做来源标记和风险过滤。
- 每个 Agent 使用最小权限。
- 高风险工具需要审批、幂等和审计。
- 对跨 Agent 消息做 schema 校验和内容过滤。
- 关键动作使用确定性规则校验，不只依赖 LLM 判断。

多 Agent 安全的核心是：不要相信任何单个 Agent 的自我约束，要让系统边界承担安全责任。

---

# 3. 成本控制

多 Agent 会放大 token 成本。假设一个任务有 5 个 Agent，每个 Agent 讨论 4 轮，每轮都带上长上下文，成本会很快失控。

常见控制策略：

- 限制最大轮次、最大 token、最大工具调用次数。
- 用小模型做分类、路由和简单审查，用大模型处理高难任务。
- 对共享上下文做摘要，而不是全量广播。
- 缓存可复用的检索结果、工具结果和中间摘要。
- 并行分支设置早停，低质量分支不进入后续合并。
- 对每个任务设置预算，超预算时返回部分结果和限制说明。

成本控制不是上线后的优化项，而是架构设计的一部分。没有预算的多 Agent 系统，很难稳定运营。

---

# 4. 延迟控制

多 Agent 延迟来自两类：串行深度和并行尾部。

串行深度指任务必须一步接一步，例如规划、检索、写作、审查、修改。每增加一轮，响应时间都会增加。

并行尾部指多个 Agent 同时执行时，总耗时取决于最慢的分支。某个检索或工具调用慢，会拖住整体合并。

优化方式包括：

- 把真正独立的任务并行化。
- 对慢分支设置超时和降级。
- 让轻量 Agent 先快速判断是否需要复杂流程。
- 把长任务异步化，先返回任务状态。
- 对常见任务使用固定 workflow，减少动态协商轮次。
- 对中间结果流式输出，但不要提前输出未确认结论。

多 Agent 不一定适合低延迟交互。如果用户期待秒级响应，系统可能需要先返回初步答案，再后台补充深度分析。

---

# 5. 可观测性

没有 trace 的多 Agent 系统几乎不可维护。

trace 至少要记录：

- 用户目标和任务 ID。
- 每次任务拆解和分配。
- 每个 Agent 的输入、输出和模型参数。
- 工具调用参数、结果、耗时和错误。
- 共享状态的写入记录。
- 评审、裁决和人工审批。
- token、成本、延迟。
- 最终结果和失败原因。

这些信息不一定都进入模型上下文，但必须进入日志和评估系统。生产问题往往不是“答案不好”，而是“为什么这一次走了这条路径”。

可观测性还可以帮助发现系统性问题，例如某个 Agent 经常返工、某类工具调用经常失败、某个 Judge 过度放行低质量结果。

---

# 6. 评估方法

多 Agent 评估要分层。

任务结果层看最终是否完成用户目标，例如答案正确率、代码测试通过率、报告质量、工单解决率。

过程质量层看协作是否合理，例如任务拆解准确率、路由准确率、重复工作比例、无效轮次、冲突处理质量。

工具行为层看外部行动是否可靠，例如工具成功率、参数错误率、重试次数、权限拦截次数。

成本性能层看 token、延迟、模型调用次数、并发资源占用。

安全合规层看越权、敏感信息泄露、prompt injection 传播、人工审批命中率。

上线前最好建立回归集。每次改 Prompt、模型、路由策略或 Agent 数量，都用同一批任务回放，比较成功率、成本和 trace 差异。

---

# 7. 渐进落地

多 Agent 不建议一步到位。

更稳的路径是：

```text
固定 workflow
  -> 单 Agent 加工具
  -> Orchestrator-Worker
  -> 增加 Critic 和质量门禁
  -> 引入共享状态和 checkpoint
  -> 按瓶颈拆分更多 Agent
```

这样做的好处是，每一步都能明确新增复杂度带来的收益。如果一开始就设计十几个 Agent，系统很难判断问题来自哪里。

落地时还要保留降级路径。例如多 Agent 深度流程失败时，是否可以退回单 Agent 答案、返回检索结果、创建人工工单，或输出已完成部分。可靠系统不是永不失败，而是失败时可控。

---

# 8. 是否应该使用 Multi-Agent

最后可以用一个简单检查表：

- 任务是否真的需要多个专业视角？
- 子任务之间是否能明确拆分？
- 是否有清楚的合并和裁决标准？
- 是否存在并行收益或权限隔离收益？
- 是否能承受额外成本和延迟？
- 是否有 trace、评估和回归测试？
- 是否有高风险动作的权限和审批？
- 是否有失败、超时和降级策略？

如果多数答案是否定的，先不要上多 Agent。用 workflow、RAG、Prompt 优化或单 Agent 可能更稳。
