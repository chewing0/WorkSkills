# 冲突、共识与质量控制

多 Agent 系统会自然产生冲突：不同 Agent 给出不同事实、不同方案、不同风险判断。冲突不是坏事，很多时候它正是多 Agent 的价值来源。问题在于系统是否有办法把冲突转化为更可靠的结论。

没有裁决机制的多 Agent，只会把单个 Agent 的不确定性变成多个 Agent 的噪声。

---

# 1. 冲突的来源

冲突大致来自四个层面。

第一是信息不一致。不同 Agent 使用了不同资料源，或上下文版本不同，结论自然不同。

第二是目标不一致。实现 Agent 追求完成，安全 Agent 追求风险最小，产品 Agent 追求用户体验。它们的建议冲突并不一定代表有人错了，而是优化目标不同。

第三是评价标准不一致。一个 Agent 按成本评价方案，另一个按准确率评价方案，如果没有统一标准，争论无法收敛。

第四是模型随机性和幻觉。即使输入相同，不同 Agent 也可能因为采样、Prompt 或上下文差异产生不同答案。

处理冲突前，要先判断冲突属于哪一类。事实冲突需要证据，目标冲突需要权衡，标准冲突需要统一指标，幻觉冲突需要外部验证。

---

# 2. 投票不等于真理

最简单的共识方式是多数投票。让多个 Agent 独立回答，再选择出现最多的答案。

投票适合答案空间较小、可独立采样、错误相对随机的任务，例如分类、选择题、简单判断。它类似 self-consistency，可以降低某些偶然错误。

但投票有明显局限：

- 如果多个 Agent 共享同一个错误前提，多数票会放大错误。
- 如果问题需要专业证据，票数不能替代证据。
- 如果 Agent 之间互相看过答案，投票就不再独立。
- 如果答案空间开放，表面不同的答案可能本质相同，也可能表面相同但理由完全不同。

所以投票最好用于低风险、可离散化的判断。高风险场景要加入证据审查、规则校验或人工确认。

# 3. 仲裁者与 Judge

Judge Agent 负责在多个候选结果之间做裁决。它可以比较方案、检查证据、按 rubric 打分，也可以决定是否需要补充信息。

一个好的 Judge 不应该只回答“哪个更好”，而应输出：

```text
judgement
  ├─ selected_answer
  ├─ reasons
  ├─ evidence_used
  ├─ rejected_options
  ├─ unresolved_risks
  └─ confidence
```

Judge 的标准必须明确。比如代码审查 Judge 应该看需求满足度、可运行性、安全性、复杂度和测试覆盖；事实核验 Judge 应该看来源可靠性、引用是否支持结论、是否存在相反证据。

Judge 本身也是 LLM，也会错。对于关键任务，Judge 的判断最好再接受确定性检查，例如测试、schema 校验、权限规则、事实检索或人工审批。

# 4. Generator-Critic 闭环

Generator-Critic 是最实用的质量控制模式之一。

```text
Generator 产出初稿
  │
  ▼
Critic 按标准审查
  │
  ├─ 通过 -> 输出
  └─ 不通过 -> 给出具体修改点 -> Generator 修改
```

这个闭环有效的关键是 Critic 的反馈必须可执行。比如“写得不够好”没有意义，“第 2 节缺少来源，第 4 节结论和证据不一致，代码没有处理空输入”才有意义。

同时要限制轮次。Critic 如果不断提出风格偏好，会让系统陷入无意义迭代。可以设置：只允许指出阻塞性问题；最多修改 N 轮；非关键建议进入后续优化清单。

---

# 5. 证据约束

多 Agent 质量控制不能只靠语言互评，必须引入证据。

不同任务的证据不同：

- RAG 问答：引用片段、文档 ID、召回分数。
- 代码任务：测试结果、编译结果、静态分析、diff。
- 数据分析：查询语句、样本数据、图表、统计口径。
- 业务决策：规则条款、用户记录、审批日志。
- 安全审查：权限矩阵、风险清单、操作审计。

如果一个 Agent 提出结论但无法说明证据，Judge 应该降低置信度或要求补充。证据不是装饰，而是多 Agent 共识的地基。

# 6. 避免群体幻觉

群体幻觉是指多个 Agent 看似互相确认，实际共同走向错误结论。它常发生在所有 Agent 都依赖同一个模型、同一个上下文、同一个错误摘要时。

降低群体幻觉的方法包括：

- 让不同 Agent 独立生成初始答案，再汇总比较。
- 给 Critic 提供不同上下文或专门的反例搜索任务。
- 要求关键结论必须引用外部证据。
- 用工具或测试验证，而不是只靠语言判断。
- 在合并时保留未解决分歧，不强行制造共识。
- 对高风险输出增加人工审批。

多 Agent 的目标不是让所有 Agent 都同意，而是让系统知道哪些结论可靠、哪些结论仍然不确定。

# 7. 质量门禁

生产系统中，质量控制最好变成门禁，而不是事后抱怨。

例如，一个多 Agent 报告生成系统可以有这些门禁：

```text
检索覆盖率不足 -> 不允许进入写作
引用不支持结论 -> 不允许输出
风险项未处理 -> 进入人工审批
格式校验失败 -> 自动修复或重试
超过预算 -> 返回部分结果并说明限制
```

门禁可以由规则、测试、模型评审或人工组成。越高风险的任务，越应该依赖确定性检查和人工审批；越低风险的创意任务，可以更多依赖模型评审。

---

# 8. 评估质量要看过程

多 Agent 的评估不能只看最终输出。最终输出好坏固然重要，但如果系统偶然走对了，下一次仍可能失败。

过程评估包括：

- 任务拆解是否合理。
- Agent 分配是否正确。
- 工具调用是否必要且成功。
- Agent 之间是否重复工作。
- 冲突是否被发现和处理。
- 证据是否被正确使用。
- 修改轮次和成本是否可接受。
- 停止条件是否合理。

这些都需要 trace。没有 trace 的多 Agent 系统，很难从失败中学习。
