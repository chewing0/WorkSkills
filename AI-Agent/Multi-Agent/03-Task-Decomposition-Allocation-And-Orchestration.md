# 任务拆解、分配与调度

多 Agent 的核心不是“有很多角色”，而是“任务如何在角色之间流动”。同样的 Agent 列表，如果拆解方式不同，系统表现会完全不同。

任务拆解决定了做什么，任务分配决定了谁来做，调度决定了何时做、失败后怎么办、什么时候停止。三者缺一不可。

---

# 1. 从目标到任务图

复杂目标最好不要直接拆成一串自然语言指令，而要拆成任务图。

```text
目标：产出一份技术调研报告
  ├─ T1：明确调研问题和范围
  ├─ T2：检索资料
  ├─ T3：提取事实与证据
  ├─ T4：比较方案
  ├─ T5：撰写报告
  └─ T6：审查事实、引用和风险
```

任务图至少要描述四件事：

- 子任务的输入是什么。
- 子任务的输出是什么。
- 子任务之间有什么依赖。
- 子任务完成的判断标准是什么。

没有输出契约的任务很难合并。比如“研究一下 RAG”太宽泛，而“输出 5 条带来源的召回优化策略，按成本和收益排序”就更容易被下游使用。

# 2. 静态分配

静态分配是指系统预先规定每类任务由哪个 Agent 处理。

```text
检索类任务 -> Research Agent
实现类任务 -> Coding Agent
测试类任务 -> Test Agent
审查类任务 -> Review Agent
```

它的优势是稳定、可解释、容易测试。业务流程固定、权限要求明确、风险较高时，静态分配通常更适合。

缺点是灵活性较弱。如果任务类型模糊，或者一个子任务跨多个能力域，静态规则可能分派不准。此时可以让 Coordinator 先做任务分类，再走静态路由。

静态分配的关键不是角色名，而是路由规则。例如：什么条件下交给检索 Agent，什么条件下交给代码 Agent，什么情况必须进入人工审批。

---

# 3. 动态分配

动态分配由模型或调度器根据当前任务选择 Agent。

它适合开放任务，例如用户请求形式多变、子任务边界不确定、可用 Agent 能力经常变化。动态分配可以更灵活，但也更难控制。

动态分配至少需要一个能力目录：

```text
Agent Profile
  ├─ name
  ├─ capability
  ├─ tools
  ├─ input_schema
  ├─ output_schema
  ├─ cost
  ├─ latency
  └─ risk_level
```

调度器不应只根据自然语言描述选择 Agent，还应考虑工具权限、当前负载、历史成功率、成本预算和任务风险。

对于高风险系统，可以采用“模型建议，规则确认”的方式：LLM 提出分配方案，确定性代码检查是否越权、是否满足依赖、是否超预算。

# 4. 并行与合并

多 Agent 的一个重要收益是并行，但并行之后必须合并。

并行适合这些情况：

- 多个资料源可以同时检索。
- 多个候选方案可以独立生成。
- 多个文件或模块可以分别处理。
- 多个评审维度可以同时检查。

合并比并行更难。合并 Agent 需要知道每个分支的目标、证据、置信度、冲突点和未解决问题。如果只是把多个输出拼接起来，结果会冗余、矛盾或前后不一致。

好的合并通常分三步：

1. 归一化：把不同 Agent 的输出转成同一 schema。
2. 对齐：找出一致结论、冲突结论和证据缺口。
3. 决策：按标准选择、融合或请求补充。

# 5. 负载感知与预算感知调度

真实系统不能只考虑“谁最适合”，还要考虑“谁现在可用、成本多少、延迟多少”。

调度器可以维护这些信息：

- 每个 Agent 当前任务数。
- 每类任务平均耗时。
- 每次调用平均 token 成本。
- 工具调用失败率。
- 最近一段时间成功率。
- 当前用户或任务的预算。

例如，一个复杂模型 Agent 适合高难任务，但简单分类不必每次都调用它。可以用小模型做初筛，用大模型处理困难分支，用规则处理确定性分支。

这类策略在多 Agent 中尤其重要，因为 Agent 数量和轮次会放大成本。

# 6. 重试、回滚与停止条件

多 Agent 系统必须知道什么时候继续，什么时候停。

常见继续条件：

- 子任务失败但可重试。
- 审查发现明确可修复问题。
- 证据不足，需要补充检索。
- 下游任务依赖未完成。

常见停止条件：

- 所有必要子任务完成。
- 达到质量门槛。
- 超过预算或轮次。
- 关键工具持续失败。
- 需要人工输入或审批。
- 任务目标本身不清楚。

不要让 LLM 自己无限决定是否继续。系统层要有最大轮次、最大 token、最大工具调用次数、最大时间和人工介入条件。

回滚也很重要。对于写文件、调用 API、修改数据库这类动作，每个 Agent 的行动都应尽量幂等、可审计、可撤销。否则多 Agent 并发执行时，错误会扩散得很快。

# 7. 调度设计的常见反模式

第一个反模式是过度拆解。每个小步骤都分给一个 Agent，看似模块化，实际大部分成本浪费在通信和合并上。

第二个反模式是没有依赖管理。测试 Agent 在实现完成前开始测试，写作 Agent 在证据确认前开始总结，都会制造返工。

第三个反模式是所有任务都交给 Orchestrator 即兴判断。早期可以这样做，但生产系统应逐渐沉淀规则、schema 和状态机。

第四个反模式是缺少失败语义。失败到底是工具失败、输入不足、权限不足、模型格式错误，还是任务不可完成？不同失败需要不同处理方式。
