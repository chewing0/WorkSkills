# 通信协议、消息与共享状态

多 Agent 系统最容易被低估的是通信。很多失败不是因为 Agent 不会推理，而是因为它们传递的信息不完整、不结构化、没有边界，导致接收方无法判断消息的来源、意图、置信度和下一步动作。

在单 Agent 系统里，上下文通常是一条对话历史；在多 Agent 系统里，上下文必须被设计成通信协议和共享状态。否则系统会变成一团长聊天记录，既难调试，也难恢复。

---

# 1. 通信到底传什么

Agent 之间不应该只传“自然语言观点”，而应该传可执行的信息。

一条有用的消息通常包含：

```text
message
  ├─ id：消息 ID
  ├─ task_id：所属任务
  ├─ from / to：发送方和接收方
  ├─ type：请求、结果、问题、风险、审批、状态更新
  ├─ content：正文或结构化数据
  ├─ evidence：证据、引用、工具结果
  ├─ confidence：置信度或不确定性
  ├─ required_action：期望接收方做什么
  └─ status：pending、running、blocked、done、failed
```

这类结构化消息的好处是，系统可以路由、过滤、重试、审计，也可以把消息写入 trace 供后续评估。

自然语言仍然有价值，但它应该放在协议内部，而不是替代协议。

# 2. 上下文边界

一个常见错误是把所有 Agent 的所有历史都塞给每个 Agent。这样做看似减少信息丢失，实际会带来三类问题。

第一是上下文污染。无关讨论会影响当前 Agent 的判断，让它关注不该关注的细节。

第二是成本膨胀。Agent 数量和轮次增加后，全量广播会让 token 成本近似爆炸。

第三是责任模糊。所有 Agent 都看到所有信息时，很难判断谁应该基于哪些证据做决策。

更好的做法是分层管理上下文：

- 私有上下文：某个 Agent 的工作草稿、局部推理、中间尝试。
- 任务上下文：与当前子任务相关的输入、约束和结果。
- 全局状态：所有 Agent 都需要知道的目标、已确认事实、决策和风险。
- 审计日志：完整 trace，用于调试和评估，不一定进入每次模型上下文。

这意味着“可追踪”和“可见给模型”是两件事。系统可以记录所有过程，但只把必要信息提供给当前 Agent。

# 3. 共享状态与黑板

共享状态是多 Agent 系统的共同事实来源。它可以是内存对象、数据库、文档、任务表、向量库，也可以是结构化黑板。

共享状态适合保存这些内容：

- 用户目标和不可违反的约束。
- 子任务列表、负责人、依赖和状态。
- 已确认事实、证据来源和引用。
- 关键决策、决策理由和反对意见。
- 产物位置，例如文件路径、报告链接、代码分支。
- 风险清单、未解决问题和人工审批记录。

共享状态不适合保存所有闲聊、所有中间推理和所有失败尝试。那些内容应该进入 trace 或私有上下文，必要时再摘要成可共享信息。

好的共享状态有三个特征：结构化、可版本化、可追溯。否则多个 Agent 同时读写时，很容易出现“最后写入覆盖前面结论”的问题。

---

# 4. 消息传递、发布订阅与事件

最简单的通信是点对点消息：A 把任务发给 B，B 返回结果给 A。这适合 Orchestrator-Worker。

更复杂的系统会使用事件或发布订阅：

```text
事件：research.completed
  ├─ Writer Agent 订阅后开始写作
  ├─ Reviewer Agent 订阅后开始审查证据
  └─ Coordinator 更新任务状态
```

事件化的好处是解耦。Agent 不需要知道所有下游是谁，只需要发布状态变化。但事件系统也更难调试，因为任务路径不再是单一调用栈。

生产系统里，事件通常要配合任务 ID、幂等键、重试策略、超时和死信队列。否则一次失败的工具调用可能触发重复执行。

# 5. 任务状态协议

多 Agent 通信必须有任务状态，否则系统无法判断当前是完成、阻塞、失败还是等待人工。

常见状态包括：

```text
created -> assigned -> running -> waiting -> blocked -> done
                                  └─ failed / cancelled
```

状态不是为了好看，而是为了控制系统行为：

- running 太久需要超时。
- blocked 需要说明阻塞原因和所需输入。
- failed 需要记录是否可重试。
- waiting 需要知道等待工具、等待其他 Agent，还是等待人工。
- done 需要有完成标准和产物位置。

没有状态协议的多 Agent 系统，通常只能靠 LLM 自己说“我完成了”。这在工程上不可靠。

# 6. MCP、A2A 与 Agent Card 的位置

协议类概念可以放在这条线上理解：

- MCP 更偏向“模型或 Agent 如何连接外部工具、资源和上下文”。
- A2A 更偏向“Agent 与 Agent 之间如何发现能力、交换任务和跟踪状态”。
- Agent Card 可以理解为 Agent 的能力说明书，描述它能做什么、如何调用、支持哪些输入输出和认证方式。

不要把这些协议当成神秘概念。它们背后的共同问题是：

```text
谁能调用谁？
调用前如何知道能力？
任务如何描述？
状态如何跟踪？
结果如何返回？
权限如何认证？
失败如何处理？
```

即使不使用某个标准协议，设计多 Agent 系统时也要回答这些问题。

# 7. 通信设计原则

第一，消息要短而完整。接收方不需要知道所有历史，但需要知道完成当前任务所需的目标、约束、上下文和期望输出。

第二，结论要带证据。尤其是 RAG、研究、代码审查和安全判断场景，消息里不能只有观点，还要有来源、工具结果或测试结果。

第三，状态要由系统维护。LLM 可以建议状态变化，但最终写入任务状态的动作最好由确定性代码校验。

第四，广播要谨慎。默认点对点，必要信息写入共享状态，只有全局重要事件才广播。

第五，协议要可演进。早期可以简单，但要预留 message type、version、task_id、trace_id 这类字段，否则后续很难扩展。
