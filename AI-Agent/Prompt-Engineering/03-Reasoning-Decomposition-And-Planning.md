> **核心考点**：复杂任务不是靠一句“请认真思考”解决的。Prompt 的价值在于把问题拆成可处理的中间状态、明确检查标准，并让模型在必要时使用工具或多候选策略。

---

# 1. 核心问题：为什么复杂任务需要拆解

LLM 逐 token 生成。复杂任务如果一次性要求模型直接给最终答案，容易出现：

- 漏掉约束。
- 中间步骤算错。
- 前后状态不一致。
- 过早给出看似合理的结论。
- 无法定位错在哪一步。

例如：

```text
帮我设计一个支持万级并发的客服 Agent 系统。
```

这个任务包含需求澄清、架构拆分、模型路由、状态管理、RAG、工具权限、评估监控、成本控制。直接回答很容易变成泛泛而谈。

更好的方式是拆成阶段：

```text
请按以下步骤回答：
1. 先列出关键需求和假设。
2. 再拆出核心模块。
3. 对每个模块说明输入、输出和瓶颈。
4. 最后给出高风险点和扩展方案。
```

拆解不是为了让答案变长，而是为了降低每一步的认知负担。

# 2. Chain-of-Thought：让模型显式经过中间推理

Chain-of-Thought 常指引导模型进行多步推理。它适合：

- 数学题。
- 逻辑题。
- 多条件判断。
- 复杂比较。
- 需要先分析再决策的任务。

但要注意两点：

## 2.1 CoT 不是万能增益

对于分类、抽取、简单改写，强行要求长推理可能降低稳定性，增加成本，还可能让模型编造理由。

## 2.2 生产系统不一定要暴露完整推理

很多场景更适合这样写：

```text
请在内部完成必要分析，最终只输出结论和关键依据。
```

这样既保留分步处理的倾向，又避免输出冗长、不可控的中间文本。需要审计时，可以要求输出“关键依据”或“检查项”，而不是要求完整思考过程。

# 3. 任务拆解：把大问题变成小决策

任务拆解的基本方法：

```text
目标
  │
  ├─► 子问题 1
  ├─► 子问题 2
  ├─► 子问题 3
  └─► 汇总决策
```

例如合同审阅：

```text
请按以下维度审阅合同：
1. 付款条款是否明确。
2. 交付物是否可验收。
3. 违约责任是否对等。
4. 终止条件是否清楚。
5. 是否存在需要法务复核的高风险条款。
```

拆解后模型更容易覆盖关键维度，人工也更容易检查。

拆解要避免两个问题：

- 步骤太细，导致输出机械且成本高。
- 步骤没有判定标准，仍然只是换一种方式泛泛而谈。

# 4. Plan-and-Solve：先计划，再执行

Plan-and-Solve 思路是先让模型制定计划，再按计划解决。

适合：

- 多步骤写作。
- 系统设计。
- 数据分析。
- 代码修改。
- Agent 工具调用。

提示方式：

```text
请先给出解决计划，计划只包含必要步骤。
然后根据计划完成任务。
最后检查答案是否遗漏用户约束。
```

计划的价值是让模型先建立任务结构。但计划也可能有问题，所以高风险任务要允许修改计划：

```text
如果执行过程中发现计划不适合，可以先说明原因，再调整计划。
```

Agent 系统里，计划还应包含停止条件，否则模型可能反复行动。

# 5. 自检与批判：让模型按标准检查输出

自检不是让模型简单说“请检查一下”。要给检查标准。

差的写法：

```text
请检查你的答案是否正确。
```

更好的写法：

```text
输出前按以下清单检查：
1. 是否回答了用户所有约束？
2. 是否使用了资料之外的事实？
3. JSON 是否包含所有必填字段？
4. 如果信息不足，是否明确输出 null 或无法判断？
```

自检适合发现：

- 格式遗漏。
- 条件遗漏。
- 明显矛盾。
- 引用缺失。

但自检不能保证事实正确。模型可能检查不出自己不知道的事实，也可能为错误答案编造合理解释。事实问题仍需要外部证据、工具或人工复核。

# 6. Self-Consistency：多条路径投票

Self-Consistency 的思路：

```text
生成多条独立解法
  │
  ├─► 比较答案
  ├─► 投票或打分
  └─► 选择最一致的结果
```

适合：

- 数学推理。
- 逻辑判断。
- 复杂选择题。
- 需要降低偶然错误的任务。

代价：

- token 成本增加。
- 延迟增加。
- 如果模型系统性误解题目，多路径也可能一起错。

工程上通常不会让所有线上请求都用 Self-Consistency，而是在高价值、高风险、低并发或离线任务中使用。

# 7. Tree-of-Thoughts 和 Graph-of-Thoughts：搜索多个中间状态

Tree-of-Thoughts 把推理看成搜索树：

```text
当前状态
  ├─► 候选思路 A
  ├─► 候选思路 B
  └─► 候选思路 C
```

每一步生成多个候选，再评价、剪枝、继续扩展。

Graph-of-Thoughts 更一般，允许中间想法形成图结构，支持合并、回溯和复用。

这些方法适合非常复杂、需要探索的任务，比如规划、证明、组合优化和复杂创作。但在普通业务系统里，常见做法是取它们的核心思想：

- 生成多个方案。
- 用评分标准比较。
- 保留最好方案。
- 必要时回溯修改。

不必一上来实现完整 ToT 或 GoT 框架。

# 8. 复杂任务 prompt 模板

```text
目标：
{最终要完成什么}

已知条件：
{上下文、约束、可用资源}

请按阶段处理：
1. 明确假设和缺失信息。
2. 拆解任务。
3. 对每个子任务给出判断或行动。
4. 汇总最终答案。
5. 按检查清单验证结果。

检查清单：
- 是否覆盖所有用户约束？
- 是否有未经证据支持的结论？
- 是否存在格式或字段缺失？
- 是否需要拒答、澄清或调用工具？

输出：
{只输出最终结论 / 输出计划加结果 / 输出 JSON}
```

这个模板的重点不是固定步骤，而是把复杂任务从“一次生成”变成“有结构的处理流程”。

# 9. 常见误区

## 9.1 所有任务都加“请一步步思考”

简单任务不需要。多余推理会增加成本和幻觉解释。只有在多步推理、规划、复杂比较中才明显有价值。

## 9.2 自检能保证正确

不能。自检只能帮助发现一部分显性错误。事实、代码和数学仍需要检索、测试、计算器、编译器或人工验证。

## 9.3 计划越详细越好

计划太详细会让模型被早期错误绑定。好的计划应该足够指导执行，也允许根据新信息调整。

## 9.4 多候选一定更好

多候选增加了探索，但也增加成本。还需要可靠的选择器，否则只是生成更多不可控内容。

# 10. 面试 Q&A

## Q1：CoT 为什么能提升复杂推理？

因为它让模型在生成最终答案前经过中间状态，减少一步到位时遗漏条件的概率。它对数学、逻辑、多条件推理更有效，对简单抽取和分类不一定有帮助。

## Q2：生产系统中应该直接输出完整 CoT 吗？

不一定。通常更建议让模型内部完成必要分析，最终输出结论、关键依据和可检查的中间结果。完整推理文本可能冗长、泄露实现细节，也不一定可靠。

## Q3：自检 prompt 怎么写才有效？

要给明确检查清单，而不是只说“检查一下”。检查项应对应真实失败模式，比如字段缺失、引用不足、越权、格式错误和遗漏用户约束。

## Q4：Self-Consistency 的代价是什么？

它通过多次生成和投票降低偶然错误，但会增加 token 成本和延迟。如果模型对题目有系统性误解，多条路径也可能同时错误。
