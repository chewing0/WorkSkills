> **核心考点**：Prompt Engineering 的本质是设计模型本次推理可见的上下文。它能引导模型在已有能力范围内更稳定地完成任务，但不能凭空补足缺失知识、工具、权限和验证机制。

---

# 1. 核心问题：Prompt 为什么能影响模型行为

LLM 推理时做的是：

```text
给定当前上下文，预测下一个 token 的概率分布
```

Prompt 就是这段“当前上下文”的主要来源。它会告诉模型：

- 现在要完成什么任务。
- 哪些信息是已知事实。
- 期望使用什么风格和格式。
- 哪些行为应该避免。
- 是否需要调用工具、引用证据或拒绝回答。

所以 prompt 不是外部命令，而是模型生成过程中的条件。模型看到的上下文变了，后续 token 的概率分布就会变。

例如：

```text
解释 Transformer。
```

这个 prompt 太宽，模型可以写科普、论文综述、面试答案，也可以写很长。换成：

```text
你是 AI 应用开发面试官。
请用面试回答的方式解释 Transformer 的核心机制。
要求：
1. 先讲 self-attention 解决什么问题。
2. 再讲 Q/K/V、多头、位置编码和 FFN 的作用。
3. 最后用 3 个常见追问收尾。
```

模型会更容易朝“面试结构化回答”这个区域生成。

# 2. Prompt 不是咒语，而是输入接口

很多人误以为 Prompt Engineering 是收集固定句式：

```text
请一步步思考。
你是一个资深专家。
如果做得好我会给你奖励。
```

这些句子有时有用，但如果脱离任务目标、上下文和校验机制，就只是表面技巧。

工程化的 prompt 更像一个接口定义：

```text
输入：
  用户问题
  背景材料
  可用工具
  业务规则

处理要求：
  如何使用材料
  如何处理不确定性
  如何处理冲突
  如何调用工具

输出：
  字段
  类型
  格式
  错误处理
```

好 prompt 的价值不在于“语气像专家”，而在于减少歧义、限制无效输出、让系统可以判断结果是否合格。

# 3. Prompt 有效的三个来源

## 3.1 预训练中的模式迁移

模型在预训练中见过大量文本模式。Prompt 可以把任务包装成模型熟悉的模式。

例如：

```text
问题：...
答案：...
```

这种格式会让模型倾向于继续生成“答案”。Few-shot 示例也是这个原理：用少量样例把模型拉到目标分布附近。

## 3.2 后训练中的指令遵循

Chat 模型经过 SFT、RLHF、DPO 等后训练后，更倾向于遵循用户指令、保持对话格式、拒绝危险请求。System prompt、工具 schema、输出格式要求能生效，依赖的就是这种指令遵循能力。

但指令遵循不是绝对的。指令越模糊、上下文越冲突、任务越超出能力，模型越容易偏离。

## 3.3 输出空间被压缩

Prompt 可以缩小模型的输出空间。

例如分类任务：

```text
只输出以下三类之一：positive、neutral、negative。
```

这比开放生成更稳定，因为模型不需要自由组织答案，只需要在小范围内选择。结构化输出、工具调用、枚举字段都是同一思想。

# 4. Prompt 的工程位置

真实系统里，prompt 不是孤立存在的。

```text
用户输入
  │
  ├─► 预处理：清洗、识别意图、补充上下文
  ├─► Prompt 构造：指令、材料、示例、工具、输出契约
  ├─► 模型推理：生成自然语言、JSON 或工具调用
  ├─► 后处理：解析、校验、过滤、重试
  ├─► 外部动作：检索、API、数据库、代码执行
  └─► 评估监控：质量、成本、安全、失败样本
```

Prompt Engineering 主要负责中间的“Prompt 构造”，但必须理解前后环节。因为很多 prompt 问题并不能靠改文字解决。

| 失败现象 | 可能根因 | 不一定该改 prompt |
|---|---|---|
| 回答事实错误 | 缺少知识来源 | 需要 RAG 或工具 |
| JSON 不合法 | 输出无强约束 | 需要 schema、解析、重试 |
| 工具参数错 | 工具定义含糊 | 需要改 schema 和示例 |
| 多轮状态乱 | 状态没有持久化 | 需要会话状态管理 |
| 越权操作 | 权限边界缺失 | 需要工具权限和审计 |
| 回答质量波动 | 没有评估集 | 需要回归测试 |

# 5. Prompt 能做什么，不能做什么

Prompt 擅长：

- 明确任务目标和回答格式。
- 指定风格、角色、受众和粒度。
- 提供上下文材料和示例。
- 引导模型分解复杂任务。
- 约束模型使用证据、工具和输出 schema。
- 让模型在不确定时拒答或请求更多信息。

Prompt 不擅长：

- 让小模型稳定完成超出能力上限的复杂任务。
- 补足上下文里没有的事实。
- 保证数学、代码、法律、医疗等高风险结论正确。
- 替代权限控制、数据校验和安全审计。
- 在没有评估集时证明“这个 prompt 更好”。

面试里可以这样回答：

> Prompt 是推理时的行为引导，不是训练。它能改变模型使用已有能力的方式，但不能可靠创造新能力。生产系统要把 prompt、RAG、工具、schema、校验和评估放在一起设计。

# 6. Prompt 设计的最小闭环

一个可迭代的 prompt 设计流程：

```text
定义任务
  │
  ├─► 写出输入输出契约
  ├─► 构造初版 prompt
  ├─► 在代表性样本上测试
  ├─► 分类失败原因
  ├─► 修改 prompt 或系统组件
  └─► 回归测试，防止修好一个弄坏另一个
```

关键是“分类失败原因”。不要看到坏输出就继续堆规则。先判断失败属于哪一类：

- 任务理解失败。
- 上下文不足。
- 示例误导。
- 格式约束不足。
- 模型能力不足。
- 工具或检索结果错误。
- 后处理和校验缺失。

不同失败类型需要不同修法。

# 7. 常见误区

## 7.1 Prompt 越长越好

不一定。Prompt 越长，越容易带入无关信息、冲突规则和成本。长 prompt 的关键是结构清楚，而不是内容堆满。

## 7.2 角色扮演等于专业能力

“你是资深律师”可以影响语气和回答角度，但不能保证法律结论正确。专业任务仍需要可靠资料、边界声明和人工复核。

## 7.3 加上“不要胡说”就能防幻觉

不能。减少幻觉要靠证据、检索、工具、引用、拒答规则和评估。单独一句“不要编造”只能弱约束。

## 7.4 Prompt 可以替代程序逻辑

不应该。确定性规则、权限判断、字段校验、金额计算、数据库写入等应尽量由程序处理，让模型处理语言理解和模糊判断。

# 8. 面试 Q&A

## Q1：Prompt Engineering 的本质是什么？

Prompt Engineering 是设计模型本次推理可见上下文的工程方法。它通过任务说明、上下文材料、示例、约束和输出格式，引导模型在已有能力范围内生成更符合目标的结果。

## Q2：为什么 prompt 能改变模型输出？

因为 LLM 的输出依赖当前上下文。Prompt 改变上下文后，会改变后续 token 的概率分布。Chat 模型还经过指令对齐，因此更容易遵循明确的任务说明和格式约束。

## Q3：Prompt 和 fine-tuning 的区别是什么？

Prompt 不改变模型参数，只改变本次推理输入；fine-tuning 通过训练改变模型权重。Prompt 适合快速适配任务和约束，fine-tuning 适合长期稳定地改变模型行为、风格或领域能力。

## Q4：为什么不能只靠 prompt 保证生产质量？

因为模型输出仍然可能受上下文缺失、采样随机性、模型能力、工具错误和攻击输入影响。生产系统需要 schema、校验、RAG、权限控制、日志和评估集共同保证质量。
