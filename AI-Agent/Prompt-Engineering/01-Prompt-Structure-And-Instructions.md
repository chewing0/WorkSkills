> **核心考点**：稳定 prompt 不是一句自然语言请求，而是一份面向模型的任务说明书。它需要清楚定义目标、输入、约束、输出格式和冲突处理方式。

---

# 1. 核心问题：一个 prompt 应该包含什么

一个可用 prompt 通常包含五层：

```text
身份与目标
  │
  ├─► 任务说明：要做什么
  ├─► 上下文材料：基于什么做
  ├─► 规则约束：必须遵守什么
  ├─► 输出契约：输出什么结构
  └─► 失败处理：不知道、冲突、信息不足时怎么办
```

简单例子：

```text
你是一个技术面试辅导助手。
任务：把候选人的回答改写成更适合面试表达的版本。
上下文：候选人回答如下：<<<...>>>
要求：
1. 不改变技术事实。
2. 保留候选人的原意。
3. 如果回答中有明显错误，先指出错误，再给改写版本。
输出：
用 Markdown 输出，包含“问题点”和“改写版”两节。
```

这比“帮我优化一下”稳定得多，因为模型知道目标、输入、边界和输出形态。

# 2. 任务说明：先说清楚要完成的动作

任务说明要避免抽象词堆叠。

差的写法：

```text
帮我分析一下这段话。
```

问题是“分析”太宽。模型不知道要分析事实、情绪、逻辑、风险、格式还是写作质量。

更好的写法：

```text
请判断这段客服回复是否满足以下三点：
1. 是否回答了用户关于退款时间的问题。
2. 是否承诺了不存在的赔偿。
3. 是否给出了下一步操作。
```

任务说明可以用动词开头：

- 判断
- 提取
- 分类
- 总结
- 改写
- 生成
- 比较
- 审核
- 规划
- 调用工具

动词越明确，输出越稳定。

# 3. 角色设定：定义职责，不是换皮肤

角色设定有用，但它应该服务于任务。

差的写法：

```text
你是世界顶级专家，请给我最好的答案。
```

这种写法可能改善语气，但没有说明怎么判断“最好”。

更好的写法：

```text
你是后端系统设计面试官。
你的职责是：
1. 先判断候选答案是否覆盖核心点。
2. 再指出缺失的工程权衡。
3. 最后给出一个 2 分钟面试回答版本。
```

角色的重点是责任和判断标准：

| 角色 | 应该补充的职责 |
|---|---|
| 面试官 | 评分维度、追问方向、回答粒度 |
| 代码审查者 | bug、风险、测试缺口、可维护性 |
| 客服助手 | 语气、政策边界、转人工条件 |
| 数据抽取器 | 字段、类型、缺失值处理 |
| Agent Planner | 任务拆解、工具选择、停止条件 |

如果只写角色，不写职责，模型会根据常见文本模式自由发挥。

---

# 4. 上下文材料：让模型知道依据在哪里

上下文材料要和指令分开。

推荐写法：

```text
任务：
请根据“资料”回答用户问题。

资料：
<<<
...
>>>

用户问题：
<<<
...
>>>

要求：
如果资料中没有答案，请回答“资料中未提及”。
```

这样做有三个好处：

1. 模型更容易区分指令和数据。
2. 后续可以自动替换资料块。
3. 遇到 prompt 注入时更容易设置安全边界。

不要把指令、资料、示例和用户输入混在一段自然语言里。混在一起会增加歧义，也更难调试。

---

# 5. 规则约束：写可执行规则，而不是愿望

差的规则：

```text
回答要准确、专业、简洁。
```

这些词方向正确，但不可判定。更好的规则是：

```text
要求：
1. 每个结论必须引用资料中的原句或段落编号。
2. 不要使用资料之外的事实。
3. 如果资料互相冲突，列出冲突点，不要自行裁决。
4. 最多输出 5 条要点。
```

好规则通常具备三个特点：

- 能被模型执行。
- 能被程序或人工检查。
- 和任务结果直接相关。

约束不是越多越好。约束太多、优先级不清，会让模型在冲突时随机选择。

---

# 6. 输出契约：让答案能被消费

输出契约要说明：

- 输出格式。
- 字段名称。
- 字段类型。
- 缺失值怎么表示。
- 是否允许额外解释。

例如：

```text
输出 JSON：
{
  "decision": "approve | reject | needs_review",
  "reasons": ["..."],
  "missing_info": ["..."]
}

规则：
- decision 只能是三个枚举值之一。
- reasons 最多 3 条。
- 没有缺失信息时 missing_info 输出空数组。
- 不要输出 JSON 之外的文字。
```

这不是为了“好看”，而是为了让下游程序能解析、校验和重试。

如果任务进入生产系统，优先使用 schema、function calling 或约束解码，不要只依赖自然语言提示。

---

# 7. 失败处理：提前定义不知道怎么办

很多幻觉来自 prompt 没有定义“不知道”。

例如 RAG 问答应该写清楚：

```text
如果资料无法回答用户问题：
1. 不要猜测。
2. 回答“资料中未提及”。
3. 说明还需要哪类信息。
```

信息抽取应该写清楚：

```text
如果字段无法从原文确定，输出 null，不要根据常识补全。
```

工具调用应该写清楚：

```text
如果用户请求超出可用工具能力，说明无法执行，不要编造工具。
```

失败处理不是消极保守，而是让系统在信息不足时保持可信。

# 8. Prompt 模板骨架

可以从这个骨架开始：

```text
角色：
你是 {role}。

目标：
{用一句话说明任务成功标准}

输入：
{输入字段说明}

上下文：
<<<
{context}
>>>

要求：
1. {规则 1}
2. {规则 2}
3. {规则 3}

不确定性处理：
{信息不足、冲突、越权、无法判断时怎么办}

输出格式：
{JSON schema / Markdown 结构 / 表格字段}
```

模板不是固定答案。真正重要的是这些槽位背后的思考：目标、依据、规则、输出和失败处理。

# 9. 常见误区

## 9.1 把语气要求当成任务要求

“专业、清晰、友好”只能控制风格，不能定义任务结果。任务要求必须写清楚动作和判定标准。

## 9.2 只写禁止，不写替代行为

不要只写“不要编造”。还要写“如果不知道，输出什么”。模型需要一个可生成的替代路径。

## 9.3 输出格式放得太随意

如果输出要给程序用，格式要求应该单独成节，并且尽量使用 schema 或校验器。

## 9.4 规则之间没有优先级

例如“必须简洁”和“必须完整引用证据”可能冲突。高风险任务要写清楚优先级：事实性优先于简洁，安全优先于完成任务。

# 10. 面试 Q&A

## Q1：一个好的 system prompt 应该包含什么？

应该包含角色职责、任务边界、行为规则、输出格式、安全限制和失败处理。重点不是写得很长，而是让模型知道在冲突和不确定时如何行动。

## Q2：角色扮演为什么有时有效？

因为角色会激活模型在训练中见过的相似文本模式，比如“面试官会评分”“代码审查者会找 bug”。但角色不能替代任务说明、证据和校验机制。

## Q3：Prompt 里的规则应该怎么写？

规则要具体、可执行、可检查。比如“每个结论引用资料编号”比“回答要准确”更好，因为前者能直接约束输出行为。

## Q4：为什么要定义失败处理？

因为模型默认倾向于继续生成答案。定义失败处理能让模型在信息不足、资料冲突或请求越权时有明确的输出路径，减少幻觉和越权操作。
