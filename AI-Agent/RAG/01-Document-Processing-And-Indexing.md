> **核心考点**：RAG 的质量上限常常在文档入库时就决定了。解析错、切分坏、元数据缺失，会让后面的 embedding、向量库、reranker 和 LLM 都在错误输入上工作。

---

# 1. 核心问题：为什么文档处理这么重要

很多人做 RAG 时从 embedding 开始，但真正的第一步是：

```text
把原始资料变成模型和检索系统都能使用的知识单元
```

原始文档并不是天然适合检索的。它们可能是：

- PDF。
- Word。
- HTML。
- Markdown。
- 表格。
- 扫描图片。
- API 文档。
- 聊天记录。
- 工单系统。

这些资料有格式、标题、页眉页脚、表格、代码块、图片、脚注、版本和权限。如果处理时全部压成纯文本，就可能丢掉关键结构。

RAG 的索引构建不是“读文件然后切成 500 字”，而是让每个可检索单元保留足够语义、来源和边界。

---

# 2. 文档解析：先保住结构

解析阶段的目标不是只拿到文字，而是尽量保住文档结构：

```text
标题层级
段落
列表
表格
代码块
图片说明
页码
链接
版本
来源
```

例如一份制度文档：

```text
3.2 差旅报销
  3.2.1 市内交通
  3.2.2 跨城市交通
```

如果解析后只剩：

```text
市内交通可以报销。跨城市交通需审批。
```

模型可能不知道这两条属于“差旅报销”，检索也可能丢失章节语义。更好的做法是在 chunk 元数据或正文前缀里保留标题路径：

```text
标题路径：差旅报销 > 跨城市交通
正文：跨城市交通需提前审批...
```

# 3. 清洗：去噪但不要误删信息

清洗要处理：

- 页眉页脚。
- 重复导航栏。
- 水印。
- 无意义空白。
- 乱码。
- 重复段落。
- 广告和版权尾巴。
- OCR 错字。

但清洗不能粗暴。比如：

- 表格里的空单元格可能表示“不适用”。
- 法律条款编号很重要，不能删。
- API 文档里的符号和缩进很重要。
- 页码可能是引用来源。

清洗原则：

> 去掉会干扰检索的噪声，保留能支撑答案和引用的结构。

# 4. Chunk：检索的基本单元

chunk 是被检索、排序和放入 prompt 的基本片段。

一个 chunk 太小：

- 语义不完整。
- 缺少上下文。
- 模型拿到后无法判断指代关系。

一个 chunk 太大：

- embedding 表示变混。
- 检索不精确。
- 占用上下文窗口。
- reranker 和生成成本更高。

所以 chunking 的核心问题是：

> 一个片段应该刚好包含回答某类问题所需的最小完整语义。

---

# 5. 常见切分策略

## 5.1 固定长度切分

按字符数或 token 数切。

优点：

- 实现简单。
- chunk 大小可控。

缺点：

- 容易切断段落、表格和代码。
- 不理解标题层级。

适合结构弱、文本连续的材料，比如普通长文。

## 5.2 段落或标题切分

按 Markdown 标题、HTML heading、Word 样式或段落切。

优点：

- 保留文档结构。
- 更适合制度、手册、API 文档。

缺点：

- 有些章节太长或太短，需要二次切分。

## 5.3 递归切分

按优先级尝试分隔符：

```text
标题 -> 段落 -> 句子 -> 固定长度
```

这是很多通用 RAG 系统的默认选择，因为它兼顾结构和长度控制。

## 5.4 语义切分

根据语义变化切分，比如 embedding 相似度突变处切开。

优点：

- 更贴近主题边界。

缺点：

- 成本更高。
- 结果不一定稳定。
- 对短文本和格式化文档不一定优于标题切分。

# 6. Overlap：为什么要重叠

chunk overlap 是相邻片段之间保留部分重复文本。

作用：

- 避免答案刚好被切在边界。
- 保留指代关系。
- 提高召回机会。

但 overlap 也有代价：

- 索引变大。
- 检索结果重复。
- 上下文里可能塞入重复片段。

经验上，不要先问“overlap 设多少”，而要看失败样本：

- 如果经常切断定义和解释，增加 overlap 或按结构切。
- 如果检索结果重复严重，降低 overlap 或做去重。

# 7. Parent-Child Chunk：小片段召回，大片段生成

常见矛盾：

- 小 chunk 检索精确，但上下文不足。
- 大 chunk 上下文完整，但检索不精确。

Parent-Child 的做法：

```text
child chunk：用于 embedding 和召回
parent chunk：召回后返回给模型的更大上下文
```

例如：

```text
child：某一条报销条件
parent：整个“差旅报销”小节
```

这样可以兼顾召回精度和生成上下文完整性。

---

# 8. 元数据：不要只存文本和向量

每个 chunk 至少应考虑这些元数据：

| 元数据                     | 用途             |
| ----------------------- | -------------- |
| document_id             | 回溯原文           |
| title / heading_path    | 保留章节语义         |
| source_url / file_path  | 引用来源           |
| page / paragraph        | 精确引用           |
| created_at / updated_at | 处理新旧版本         |
| author / department     | 判断权威性          |
| tenant / permission     | 权限过滤           |
| document_type           | 区分政策、FAQ、代码、工单 |
| language                | 多语言检索          |

元数据的作用不只是展示引用，还能参与检索过滤：

```text
只检索当前用户有权限的文档
只检索最新版本
只检索产品 A 的文档
只检索 2025 年之后的政策
```

没有元数据，RAG 很难进入生产。

---

# 9. 索引不止一种

一个成熟 RAG 系统通常不只有向量索引。

```text
向量索引：语义相似
关键词索引：精确词、数字、型号、错误码
元数据索引：权限、时间、类型、租户
全文索引：短语匹配、过滤、排序
原文存储：展示引用和重建上下文
```

向量索引负责“语义像不像”，但不能很好处理：

- 订单号。
- 错误码。
- 人名。
- 数字范围。
- 法条编号。
- 精确术语。

所以生产系统常用多索引配合。

# 10. 增量更新和删除

知识库不是一次性建完。

需要考虑：

- 新文档如何入库。
- 旧文档如何更新。
- 删除文档如何从索引移除。
- 版本冲突如何处理。
- embedding 模型升级后是否重建索引。
- 权限变化是否实时生效。

常见做法：

```text
文档内容 hash
  │
  ├─► 内容没变：跳过
  ├─► 内容变化：删除旧 chunk，写入新 chunk
  ├─► 权限变化：更新元数据过滤
  └─► 模型升级：异步重建向量
```

如果不处理增量更新，RAG 很快会出现旧答案、新旧文档混用和权限泄漏。

# 11. 常见误区

## 11.1 chunk size 有标准答案

没有。制度文档、代码、FAQ、论文、工单的最佳切分都不同。应通过检索评估和失败样本调参。

## 11.2 文档越多越好

不一定。低质量、重复、过期文档会降低检索质量。RAG 需要知识治理，不只是堆数据。

## 11.3 只要 embedding 好，切分随便

不对。embedding 表示的是 chunk。如果 chunk 本身语义残缺或混杂，embedding 再好也无法恢复。

## 11.4 PDF 能解析出文字就够

不够。表格、标题、页码、脚注、图片说明、公式和代码块都会影响问答质量。

# 12. 面试 Q&A

## Q1：chunk size 应该怎么选？

先看文档结构和任务。FAQ 可以小，制度和手册要保留章节上下文，代码要按函数或类切。最终应通过检索召回率、答案忠实性和上下文噪声来调，而不是固定一个数字。

## Q2：为什么要保留元数据？

元数据用于引用、过滤、权限控制、版本管理和排序。没有元数据，系统很难判断文档来源、新旧版本和用户是否有权限访问。

## Q3：overlap 有什么作用和风险？

overlap 可以避免关键信息被切在边界，提高召回；风险是索引膨胀、重复召回和上下文浪费。应根据失败样本调整。

## Q4：为什么 RAG 需要增量更新机制？

业务知识会不断变化。没有增量更新，系统会回答旧政策、混用版本，甚至泄露已撤回或无权限的内容。
