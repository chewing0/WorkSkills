> **核心考点**：RAG 检索不是一次向量 top-k。真正稳定的系统通常是多路召回加重排：先尽量找全候选，再把真正能支持答案的证据排到前面。

---

# 1. 核心问题：为什么只靠向量检索不够

用户问题可能有多种形态：

```text
这个错误码 ERR_AUTH_401 是什么？
离职账号多久关闭？
报销上限 300 是按天还是按次？
v2.3.1 之后接口字段变了吗？
```

这些问题里，有些靠语义匹配，有些靠关键词、编号、数字、版本、时间和过滤条件。

单一路径很容易偏：

- dense retrieval 擅长语义，但可能漏精确词。
- BM25 擅长关键词，但不懂同义表达。
- 元数据过滤能缩小范围，但不能判断语义。

所以检索常分两阶段：

```text
召回：尽量把可能相关的候选找出来
重排：从候选中选出最能回答问题的片段
```

---

# 2. BM25：关键词检索为什么仍然重要

BM25 是经典稀疏检索方法，核心看 query 词项在文档中的匹配程度，同时考虑词频、逆文档频率和文档长度。

直觉：

- query 里的词在文档里出现，分数增加。
- 稀有词比常见词更重要。
- 文档太长会有长度归一化。

BM25 擅长：

- 错误码。
- 专有名词。
- 型号。
- 人名。
- 法条编号。
- 精确短语。
- 低频关键词。

它不擅长：

- 同义改写。
- 口语化表达。
- 跨语言。
- 需要理解上下文含义的问题。

所以 BM25 不是过时技术，而是 dense retrieval 的互补。

# 3. Hybrid Search：语义和关键词一起用

Hybrid Search 通常把多个召回结果合并：

```text
query
  ├─► dense retrieval
  ├─► BM25 / full-text
  ├─► metadata filter
  └─► merge candidates
```

合并方式可以简单，也可以复杂：

- 分数归一化后加权。
- 各取 top-k 后合并去重。
- 用 RRF 按排名融合。
- 先过滤再向量检索。
- 先关键词召回再语义扩展。

常见配置：

```text
dense top 50
BM25 top 50
合并去重
reranker 排到 top 5
```

Hybrid 的关键不是“两个都开”，而是通过评估看各路召回补到了哪些失败样本。

---

# 4. RRF：按排名融合

RRF（Reciprocal Rank Fusion）是一种常见排序融合方法。

直觉：

```text
一个文档如果在多个检索器里都排得靠前，就应该更靠前。
```

公式通常类似：

$$
score(d)=\sum_i \frac{1}{k + rank_i(d)}
$$

其中 $rank_i(d)$ 是文档在第 i 个检索器里的排名，$k$ 用来平滑。

RRF 的好处：

- 不需要不同检索器分数可比。
- 实现简单。
- 对多路召回融合稳定。

它解决的是候选合并问题，不替代 reranker 对语义相关性的精细判断。

# 5. Reranker：为什么重排常常有效

向量检索通常是双塔结构：

```text
query -> vector
doc -> vector
相似度计算
```

速度快，但 query 和 doc 的交互有限。

Reranker 常用 cross-encoder：

```text
[query, doc] -> model -> relevance score
```

它把 query 和候选文档一起输入模型，能更细地判断：

- 文档是否真正回答问题。
- 是否只是主题相似。
- 否定、数字、条件是否匹配。
- 哪个版本更相关。

代价是慢，所以 reranker 通常只处理召回后的几十或几百个候选，而不是全库。

---

# 6. 召回和重排的权衡

常见配置：

```text
召回 top 100
  │
  ├─► rerank
  └─► 取 top 5 放入 prompt
```

如果召回 top-k 太小：

- 正确证据可能没进入候选，reranker 无法补救。

如果召回 top-k 太大：

- reranker 成本上升。
- 噪声变多。
- 延迟增加。

如果最终给 LLM 的片段太少：

- 证据不完整。

如果最终给 LLM 的片段太多：

- 上下文噪声多，模型容易混淆。

所以调参不是只调一个 `top_k`，而是分别调：

```text
召回候选数
rerank 候选数
最终上下文片段数
每个片段长度
```

# 7. Query Rewriting：用户问题不等于检索查询

用户问题常常不适合直接检索：

```text
那这个还能退吗？
```

它依赖上下文、指代和业务规则。查询改写可以把它变成：

```text
订单 A12345 已签收 9 天，商品耳机，是否符合退货条件？
```

Query rewriting 包括：

- 补全指代。
- 提取关键词。
- 加入上下文条件。
- 改写成文档里的正式术语。
- 生成多个查询。
- 拆分复合问题。

它的风险是改写错了会把检索带偏。所以改写结果最好可观测，并在评估中单独分析。

# 8. Multi-query Retrieval：多路问法召回

同一个问题可以生成多个检索 query：

```text
原问题：离职后系统账号多久关闭？

query 1：离职账号停用时间
query 2：劳动关系终止后账号关闭
query 3：员工离职 IT 系统权限回收
```

优点：

- 提高召回。
- 覆盖不同表达。

缺点：

- 检索成本增加。
- 候选噪声增加。
- 需要去重和重排。

适合术语不统一、用户口语化、文档写法多样的知识库。

# 9. HyDE：先生成假设答案再检索

HyDE（Hypothetical Document Embeddings）的思路：

```text
用户问题
  │
  ├─► LLM 生成一个假设答案或假设文档
  ├─► 对假设文档做 embedding
  └─► 用它去检索真实文档
```

为什么有用：

用户 query 很短时，假设答案可能更接近文档表达。

风险：

- 假设答案可能带入错误方向。
- 成本更高。
- 不适合高精确关键词问题。

HyDE 适合开放语义检索，不适合订单号、错误码、法规条款编号这类精确查询。

# 10. 元数据过滤：先缩小正确范围

很多问题不是全库搜索，而是带条件搜索：

```text
只查当前产品
只查当前租户
只查用户有权限的文档
只查最新版本
只查 2026 年政策
```

元数据过滤通常应该发生在检索前或检索中，而不是生成后让模型判断。因为无权限文档不应该进入模型上下文。

常见过滤：

- tenant_id。
- user_group。
- product。
- language。
- updated_at。
- document_type。
- version_status。

没有元数据过滤，RAG 容易出现“答得对但越权”的严重问题。

# 11. 常见误区

## 11.1 reranker 可以弥补召回失败

不能。reranker 只能重排候选。如果正确证据没被召回，它无能为力。

## 11.2 dense 和 BM25 分数可以直接相加

不一定。不同检索器分数尺度不同，直接相加可能失真。可以用归一化、权重或 RRF。

## 11.3 查询改写一定提升效果

不一定。改写可能引入错误假设。必须通过评估观察改写前后的召回变化。

## 11.4 top-k 调大就能提高答案质量

top-k 调大可能提高召回，也可能增加噪声。最终质量取决于召回、排序、上下文构造和生成约束。

# 12. 面试 Q&A

## Q1：为什么生产 RAG 常用 hybrid search？

因为 dense retrieval 擅长语义，BM25 擅长精确词和低频关键词。业务问题常同时包含语义和精确条件，hybrid 能提高召回鲁棒性。

## Q2：reranker 的作用是什么？

reranker 在召回候选上重新判断 query-doc 相关性，把真正能回答问题的片段排到前面。它通常更准但更慢，所以只处理少量候选。

## Q3：查询改写解决什么问题？

解决用户问题短、口语化、指代不明、术语不匹配和复合问题的问题。它把用户请求改成更适合检索的 query。

## Q4：RRF 适合什么场景？

适合融合多个检索器的排名，比如 dense、BM25、多 query 召回。它不依赖不同检索器分数同尺度，比直接加权分数更稳。
