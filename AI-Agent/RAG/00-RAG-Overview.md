> **核心考点**：RAG 不是让模型“拥有知识库”，而是在每次推理时把相关证据取出来，放进上下文，让模型基于证据生成答案。它改善事实性、时效性和可溯源性，但同时引入检索、排序、上下文构造和引用评估的新问题。

---

# 1. 核心问题：为什么需要 RAG

直接问 LLM 有三个天然限制：

1. 模型参数里的知识可能过时。
2. 模型不知道你的私有文档和业务数据。
3. 模型生成的是高概率文本，不保证答案可溯源。

例如：

```text
公司最新报销政策中，跨城市打车能不能报销？
```

如果直接问模型，它可能根据训练中见过的通用公司制度生成一个看似合理的答案。但你的公司政策可能刚更新，或者有特殊限制。

RAG 的做法是：

```text
先从公司政策库里找相关条款
  │
  ├─► 把条款作为上下文给模型
  └─► 要求模型只基于条款回答，并给出引用
```

这样模型不需要把所有知识都记在参数里，而是在回答时查证据。

# 2. RAG 的最小链路

RAG 可以拆成两条链路。

## 2.1 离线索引链路

```text
原始文档
  │
  ├─► 解析：PDF、Word、网页、Markdown、表格
  ├─► 清洗：去噪、去重、修复乱码、保留结构
  ├─► 切分：按标题、段落、语义或长度切 chunk
  ├─► 元数据：来源、标题、权限、时间、版本
  ├─► 向量化：embedding
  └─► 入库：向量索引、关键词索引、元数据索引
```

这条链路决定“知识是否以正确形态进入系统”。

## 2.2 在线问答链路

```text
用户问题
  │
  ├─► 查询理解：意图、关键词、过滤条件
  ├─► 召回：向量检索、关键词检索、多路召回
  ├─► 重排：reranker 重新排序候选片段
  ├─► 上下文构造：去重、压缩、排序、引用编号
  ├─► 生成：要求模型基于证据回答
  └─► 校验：引用、忠实性、拒答、日志
```

这条链路决定“用户问题能不能找到证据，并被模型正确使用”。

# 3. RAG 解决了什么

## 3.1 私有知识

模型本身不知道企业内部文档、项目 README、工单、制度、接口文档。RAG 可以在推理时把这些资料检索出来。

## 3.2 新鲜知识

模型训练完成后，参数不会自动更新。RAG 可以通过更新知识库支持新政策、新产品、新公告。

## 3.3 可溯源回答

RAG 可以要求答案带引用，让用户知道结论来自哪份文档、哪一段。这对企业知识库、客服、合规场景非常重要。

## 3.4 成本和维护

如果只是补充知识，RAG 通常比 fine-tuning 更轻。更新文档比重新训练模型更便宜，也更可控。

---

# 4. RAG 没解决什么

RAG 不是万能方案。

| 问题       | RAG 是否天然解决 | 原因               |
| -------- | ---------- | ---------------- |
| 文档中没有答案  | 不能         | 没有证据就只能拒答或转人工    |
| 文档本身错误   | 不能         | RAG 会忠实使用错误资料    |
| 检索不到正确片段 | 不能         | 召回失败会导致模型缺证据     |
| 复杂计算     | 不擅长        | 应使用工具或程序计算       |
| 权限控制     | 不能只靠模型     | 需要检索前后的 ACL      |
| 多步业务操作   | 不够         | 需要 Agent/工作流/状态机 |

一句话：

> RAG 提供证据，不提供真理；RAG 改善知识接入，不替代数据治理。

# 5. RAG 的典型失败模式

RAG 失败时，不要急着怪模型。可以按链路定位。

## 5.1 索引失败

现象：

- 文档解析乱码。
- 表格结构丢失。
- 标题和正文断开。
- 图片里的文字没有 OCR。
- 新文档没有入库。

结果是：正确答案从一开始就没有以可检索形态进入系统。

## 5.2 召回失败

现象：

- 用户问“报销上限”，系统只找到了“报销流程”。
- 用户用缩写，文档用全称，向量没对上。
- 用户问数字、型号、订单号，dense retrieval 没召回。

结果是：模型拿不到证据，只能猜或拒答。

## 5.3 排序失败

现象：

- top-k 里有正确片段，但排在后面。
- 前面都是相似但不支持结论的片段。
- 旧版本文档排在新版本前面。

结果是：上下文窗口被弱相关内容占满。

## 5.4 生成失败

现象：

- 检索结果里没有的信息，模型自己补。
- 多个片段冲突时，模型自行裁决。
- 引用 A，却回答 B。
- 不知道时没有拒答。

结果是：答案看起来像 RAG，实际上没有忠实于证据。

# 6. RAG 的工程定位

RAG 在 LLM 应用里通常处于这个位置：

```text
用户问题
  │
  ├─► RAG：找证据
  ├─► Prompt：组织证据和任务规则
  ├─► LLM：基于证据生成
  ├─► Parser/Validator：解析和校验
  └─► Observability：记录检索、生成、引用和反馈
```

它和 Prompt Engineering 的关系：

- RAG 决定给模型什么材料。
- Prompt 决定模型如何使用这些材料。

它和 Fine-tuning 的关系：

- RAG 适合知识更新、引用和私有资料。
- Fine-tuning 适合稳定改变风格、格式、领域行为或工具使用能力。

很多系统两者都会用：用 fine-tuning 提升模型遵循领域格式的能力，用 RAG 提供最新知识。

# 7. 一个最小可用 RAG 系统

最小系统不一定需要复杂框架，但需要闭环：

```text
1. 选一批高质量文档。
2. 解析并按结构切分。
3. 为每个 chunk 保存来源、标题、时间、权限。
4. 建 dense + keyword 检索。
5. 用 reranker 排序 top candidates。
6. 把证据编号后放进 prompt。
7. 要求模型只基于证据回答。
8. 答案必须带引用或说明资料不足。
9. 记录 query、retrieved chunks、answer、feedback。
10. 用失败样本迭代切分、召回、排序和 prompt。
```

其中第 9、10 步经常被忽略，但它们决定系统能不能持续变好。

# 8. 常见误区

## 8.1 RAG 等于向量数据库

不对。向量数据库只解决相似度检索的一部分。RAG 还包括文档处理、元数据、关键词检索、重排、上下文构造、生成约束和评估。

## 8.2 top-k 越大越好

不一定。top-k 大会增加召回机会，也会塞入更多噪声，占用上下文窗口，让模型更难聚焦。

## 8.3 找到相似文档就够了

相似不等于能回答。RAG 需要的是支持答案的证据，而不是看起来相关的文本。

## 8.4 RAG 可以消除幻觉

不能消除，只能降低。模型仍可能误读证据、混合常识、引用错误或在信息不足时编造。

# 9. 面试 Q&A

## Q1：RAG 的本质是什么？

RAG 是在生成前检索外部知识，把相关证据放进模型上下文，让模型基于证据回答。它不是改变模型参数，而是改变本次推理可见的信息。

## Q2：RAG 相比 fine-tuning 有什么优势？

RAG 更适合私有知识、新鲜知识和需要引用溯源的场景。更新知识库比重新训练模型更快、更便宜，也更容易控制权限和来源。

## Q3：RAG 为什么还会幻觉？

因为检索可能没找到正确证据，排序可能把弱相关内容放前面，上下文可能冲突，模型也可能没有忠实使用证据。RAG 降低幻觉风险，但不等于事实保证。

## Q4：RAG 失败怎么排查？

按链路拆：先看文档是否正确入库，再看是否召回正确证据，再看排序是否靠前，再看上下文是否构造合理，最后看生成是否忠实引用证据。
