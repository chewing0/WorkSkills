> **核心考点**：Agent 框架解决的是工程组织问题，不直接解决模型能力、工具权限、数据质量和任务评估问题。框架能让你更快搭出链路，但不能替你定义可靠的 Agent 行为边界。

---

# 1. 核心问题：为什么需要 Agent 框架

一个稍微复杂的 Agent 应用会涉及：

- 模型调用。
- Prompt 模板。
- 工具定义。
- 工具调用和结果回传。
- 对话状态。
- RAG 检索。
- 多步骤流程。
- 错误重试。
- 日志和 trace。
- 评估和回放。
- 人工确认。

如果全部手写，很快会变成混乱的胶水代码。

Agent 框架的价值是把常见模式抽象出来：

```text
LLM -> Prompt -> Tool -> State -> Workflow -> Trace -> Eval
```

但框架只是骨架。真正决定 Agent 质量的是任务设计、工具边界、状态管理、评估和安全控制。

---

# 2. 框架能解决什么

框架通常能帮你：

| 能力 | 作用 |
|---|---|
| 模型适配 | 统一不同模型 API |
| Prompt 管理 | 模板化输入和变量 |
| Chain 编排 | 把多步调用串起来 |
| Tool 抽象 | 定义工具名、描述、参数 schema |
| Memory/State | 管理对话和任务状态 |
| Graph/Workflow | 组织分支、循环和状态转移 |
| Callback/Trace | 记录中间过程 |
| Integration | 连接向量库、数据库、搜索、API |
| Eval | 运行测试样本和打分 |

这些能力能提高开发效率，也能减少重复工程。

---

# 3. 框架不能解决什么

框架不能自动保证：

- 模型回答正确。
- 工具选择正确。
- 工具执行安全。
- RAG 检索准确。
- Prompt 不被注入。
- 权限不泄露。
- 业务流程不出错。
- 多 Agent 协作一定更好。

如果底层 prompt、工具 schema、数据、状态和评估没有设计好，换框架也只是换一种方式制造问题。

# 4. 常见框架类型

## 4.1 Chain/RAG 框架

代表：

- LangChain。
- LlamaIndex。
- Haystack。

关注：

- Prompt。
- RAG。
- 工具调用。
- 文档加载。
- 向量库集成。

适合知识问答、简单工具链路和快速原型。

## 4.2 Stateful Agent / Workflow 框架

代表：

- LangGraph。
- Semantic Kernel planners。
- Temporal + LLM 组合。

关注：

- 状态。
- 分支。
- 循环。
- checkpoint。
- Human-in-the-loop。

适合复杂、多步、可恢复 Agent。

## 4.3 Multi-Agent 框架

代表：

- AutoGen。
- CrewAI。
- MetaGPT。

关注：

- 多角色协作。
- 对话协议。
- 任务分配。
- 角色职责。
- 协作过程。

适合模拟团队协作、代码任务、研究和创作流程。

## 4.4 低代码 Agent 平台

代表：

- Dify。
- Coze。
- Flowise。

关注：

- 快速搭建。
- 可视化工作流。
- 知识库管理。
- 发布和运营。

适合内部工具、业务原型和非深度定制场景。

# 5. 什么时候不需要框架

如果你的任务只是：

```text
用户输入 -> Prompt -> 模型回答
```

或者：

```text
用户问题 -> 检索 -> 模型回答
```

可能不需要复杂 Agent 框架。少量清晰代码更容易控制。

不需要框架的场景：

- 单轮任务。
- 工具很少。
- 无状态或弱状态。
- 无复杂分支。
- 无多 Agent 协作。
- 团队需要完全掌控每行逻辑。

框架引入后也会带来依赖、抽象成本和调试成本。

---

# 6. 框架选型的主线

先问任务形态：

```text
是单步还是多步？
是否需要工具？
是否需要状态持久化？
是否有分支和循环？
是否需要人工确认？
是否需要多 Agent？
是否要快速给业务使用？
```

对应选择：

| 任务形态 | 倾向 |
|---|---|
| 简单 Prompt/RAG | 轻量手写或 LangChain/LlamaIndex |
| 多步工具调用 | LangGraph 或自定义 workflow |
| 高风险业务流程 | 状态机/workflow + LLM |
| 多角色协作 | AutoGen/CrewAI/MetaGPT |
| 快速内部应用 | Dify/Coze/Flowise |
| 强生产可控 | 显式状态 + trace + 评估，框架只是辅助 |

# 7. 常见误区

## 7.1 用了框架就等于有 Agent

不对。Agent 需要目标、状态、工具、反馈和停止条件。框架只是组织方式。

## 7.2 框架越重越专业

不一定。简单任务用重框架会增加复杂度和调试成本。

## 7.3 多 Agent 框架一定比单 Agent 强

不一定。多 Agent 会增加通信成本、冲突和不可控性。只有角色分工真实有价值时才值得。

## 7.4 框架能替代评估

不能。框架提供 trace 和 eval 工具，但评估样本、指标和失败分类仍要自己设计。

# 8. 面试 Q&A

## Q1：Agent 框架解决的核心问题是什么？

它把模型调用、prompt、工具、状态、流程、回调和评估等重复工程抽象出来，降低复杂 Agent 的开发和维护成本。

## Q2：为什么框架不能替代 Agent 设计？

因为任务目标、工具权限、状态边界、安全策略和评估标准需要业务和工程设计。框架只是实现这些设计的载体。

## Q3：什么时候应该避免使用重框架？

单步问答、简单 RAG、工具很少、状态简单且团队需要精确掌控逻辑时，轻量手写可能更合适。

## Q4：选型时最重要看什么？

看任务是否多步、是否有状态、是否需要工具和人工确认、是否要多 Agent 协作、是否有生产观测和恢复要求。
