> **核心考点**：低代码 Agent 平台的价值是降低搭建、发布和运营门槛，尤其适合内部知识库、客服助手和流程原型。但它们不应掩盖底层的 RAG、Prompt、工具权限、评估和数据治理问题。

---

# 1. 低代码平台解决什么

低代码平台通常提供：

- 可视化工作流。
- Prompt 配置。
- 模型选择。
- 知识库管理。
- 工具/API 配置。
- Web 发布。
- 用户管理。
- 日志和监控。

适合业务团队快速搭建：

```text
知识库问答
表单助手
客服机器人
内部流程助手
简单工具 Agent
```

# 2. 代表平台

## 2.1 Dify

常见能力：

- 应用编排。
- RAG 知识库。
- Workflow。
- Agent。
- 模型接入。
- API 发布。

适合内部知识库、企业应用原型和较快上线的 LLM 应用。

## 2.2 Coze

偏 bot 构建和插件生态，适合快速搭建对话机器人和工具型助手。

## 2.3 Flowise

可视化 LangChain 编排，适合理解链路和快速原型。

## 2.4 其他

- LlamaIndex Cloud。
- LangSmith + LangServe。
- Semantic Kernel 生态。
- 各云厂商智能体平台。

# 3. 低代码平台的优势

- 上手快。
- 适合业务人员参与。
- 内置知识库和工作流。
- 部署发布方便。
- 运维成本低。
- 可快速验证需求。

对于很多内部工具，低代码平台比从零写框架更经济。

---

# 4. 低代码平台的限制

## 4.1 深度定制有限

复杂状态、特殊权限、定制 reranker、复杂工具事务，可能超出平台能力。

## 4.2 可观测性受限

平台可能提供日志，但对底层 prompt、检索、工具参数和中间状态的控制不够细。

## 4.3 版本和迁移成本

平台配置可能难以像代码一样 review、diff、测试和回滚。

## 4.4 复杂工程能力仍要补

比如：

- 权限系统。
- 业务审计。
- 高风险动作确认。
- 评估集。
- 数据脱敏。
- 灰度发布。

---

# 5. 什么时候用低代码

适合：

- 快速原型。
- 内部知识库。
- 非高风险客服。
- 轻量流程自动化。
- 业务团队自助配置。
- 需求还不稳定。

不适合：

- 强事务业务。
- 高风险外部动作。
- 大规模复杂多租户。
- 深度定制检索和评估。
- 需要严格代码审查和版本治理的核心系统。

---

# 6. 低代码和代码框架如何配合

常见组合：

```text
低代码平台：业务配置、Prompt、知识库、简单流程
后端服务：权限、关键工具、审计、复杂计算
代码框架：复杂 Agent、定制 RAG、评估和部署
```

低代码平台可以作为前台编排，关键动作仍走受控后端 API。

不要把密钥、权限判断和高风险业务逻辑完全放在平台 prompt 里。

---

# 7. 评估低代码平台

选型时看：

- 模型接入能力。
- 知识库质量和检索可控性。
- 工具/API 权限控制。
- 工作流分支和状态能力。
- 日志和 trace。
- 版本管理。
- 导出和迁移能力。
- 私有化部署。
- 数据安全。
- 成本。

不要只看 demo 漂亮。要看坏案例怎么定位和修复。

---

# 8. 常见误区

## 8.1 低代码平台不需要工程能力

不对。Prompt、RAG、权限、评估、数据治理仍然需要工程理解。

## 8.2 平台知识库默认效果够用

不一定。文档解析、chunk、召回、重排和引用仍要评估。

## 8.3 业务人员能配就不用版本管理

配置也是生产逻辑，需要版本、审批和回滚。

## 8.4 低代码无法上生产

也不对。合适场景下可以生产使用，但要补齐权限、观测和评估。

# 9. 面试 Q&A

## Q1：低代码 Agent 平台适合什么场景？

适合快速原型、内部知识库、客服助手、轻量工作流和业务团队参与配置的场景。

## Q2：低代码平台的主要风险是什么？

深度定制、权限控制、可观测性、版本治理和迁移能力可能不足。高风险业务不能只依赖平台 prompt。

## Q3：低代码和代码框架如何取舍？

需求不稳定、风险低、强调速度时用低代码；复杂状态、高风险动作、深度定制和严格治理时用代码框架或自研 workflow。

## Q4：如何评估一个低代码平台？

看知识库质量、工具权限、工作流状态、trace、版本管理、数据安全、私有化和迁移能力。
