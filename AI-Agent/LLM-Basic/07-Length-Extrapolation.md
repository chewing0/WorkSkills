# 1. 核心问题：长上下文不是把窗口调大

长度外推（Length Extrapolation）关心的是：

> 模型训练时只见过较短序列，推理时能不能稳定处理更长序列？

比如训练最大长度是 4K，推理时希望用 32K、128K。这不是简单改一个配置，因为模型会遇到三类问题：

```text
放得进：位置编码和上下文窗口是否支持更长位置
算得动：Attention、KV Cache、显存和延迟是否可承受
用得好：模型是否真的能找回、引用和综合长文信息
```

一句话：

> 长上下文有三关：放得进、算得动、用得好。

---

# 2. 基础机制：位置编码为什么会限制长度

Transformer 的 Self-Attention 本身不自带顺序感。如果没有位置编码，模型只知道 token 之间的内容关系，不知道谁在前谁在后。

训练时，模型只见过某个范围内的位置关系：

```text
训练长度：0 ~ 4095
推理位置：0 ~ 32767
```

推理时出现更远位置，会产生分布偏移：

- 绝对位置 embedding 没有训练过更大编号。
- RoPE 虽然能计算任意位置，但高频旋转在超长距离下可能进入陌生模式。
- Attention 分数分布可能和训练时不同。
- 模型没有学过“长文档里如何找证据和综合信息”的任务格式。

所以长度外推不是只修公式。它通常需要位置策略、推理系统和长上下文数据共同配合。

# 3. 同族概念分组：位置外推方案

这一组解决“放得进”的问题，也就是让模型面对超过训练长度的位置时不至于完全失控。

## 3.1 RoPE：用旋转表达相对位置

RoPE（Rotary Position Embedding）把位置信息注入 Q/K 向量的旋转角度中。

直觉：

```text
位置越靠后，向量旋转角度越大。
两个 token 的相对距离，会反映在 Q 和 K 的旋转关系里。
```

RoPE 的重要性质：

- 不需要单独学习绝对位置表。
- 天然适合表达相对位置。
- 是 Llama、Qwen、Mistral 等 Decoder-only LLM 的常见选择。

但 RoPE 不等于无限长度。超过训练长度后，模型会看到训练中没见过的旋转频率组合，attention 分布可能偏移。

## 3.2 位置插值：把长位置压回熟悉范围

位置插值的思想是：

```text
原始推理位置：0 ~ 32767
缩放后位置：  0 ~ 4095
```

也就是把长序列位置压缩到模型训练过的范围附近。

优点：

- 简单直接。
- 不需要完全重训模型。
- 可以扩展已有 RoPE 模型的上下文长度。

代价：

- 相邻位置变得更“挤”。
- 局部位置分辨率下降。
- 通常需要少量长上下文微调恢复性能。

## 3.3 NTK-aware RoPE Scaling：调整频率而不是简单压缩

NTK-aware scaling 试图更细致地调整 RoPE 频率，让模型在更长上下文下仍保持较合理的 attention 行为。

直觉：

- 不同维度对应不同频率。
- 高频维度更关注局部位置。
- 低频维度更适合长距离关系。
- 缩放策略要尽量保留局部分辨率，同时扩展远距离范围。

它比简单位置插值更温和，但仍然不是万能长上下文训练。

## 3.4 YaRN：插值、缩放和微调组合

YaRN 可以理解为一套 RoPE 扩展方案，结合位置缩放、频率调整和少量长上下文训练。

核心理解：

> 长上下文扩展不是单一公式，而是位置策略 + 数据训练 + 推理工程的组合。

它的目标不是让模型“数学上可以输入更长”，而是让模型在更长长度上仍保持可用质量。

## 3.5 ALiBi：用距离惩罚表达位置

ALiBi 不使用显式位置 embedding，而是在 attention score 上加入距离相关 bias：

```text
距离越远，attention 分数惩罚越大
```

优点：

- 外推相对自然。
- 不依赖固定位置表。
- 实现思路清晰。

局限：

- 现代主流 Decoder-only LLM 更多使用 RoPE。
- ALiBi 的归纳偏置更明确，但表达方式和 RoPE 不同。

# 4. 同族概念分组：注意力范围和计算方案

这一组解决“算得动”的问题。即使位置编码能扩展，完整 attention 和 KV Cache 成本仍然会随长度暴涨。

## 4.1 全量注意力：能力强，但成本高

全量 self-attention 允许每个 token 看见所有历史 token。它最直观，也最通用，但 attention 计算随序列长度近似平方增长。

长上下文下主要压力来自：

- prefill attention 计算。
- KV Cache 显存。
- 高并发时的缓存管理。
- 首 token 延迟。

这些内容和 [[06-Context-Window-KV-Cache]]、[[08-Inference-Optimization]] 直接相关。

## 4.2 滑动窗口注意力：只看附近一段

Sliding Window Attention 让每个 token 只关注最近窗口内的 token：

```text
token t 只能看 t-window ~ t
```

优点：

- 计算和显存更可控。
- 适合局部依赖强的长文本。
- 可支持更长输入。

缺点：

- 远距离信息可能不可见。
- 对需要跨全文综合的任务不够。
- 通常需要配合 global token、检索或分层机制。

## 4.3 FlashAttention：优化计算实现，不解决外推本身

FlashAttention 通过分块和 IO 优化减少 attention 显存读写。它能让长 prompt 的 prefill 更快、更省显存，但它不改变 attention 数学公式，也不让模型自动学会长文推理。

边界：

- 它帮助“算得动”。
- 它不直接解决“放得进”。
- 它也不保证“用得好”。

## 4.4 PagedAttention 与 KV 管理

PagedAttention 管理的是 KV Cache 的内存分配和碎片问题。长上下文和高并发下，它能提高显存利用率，但不是新的注意力机制。

# 5. 同族概念分组：长上下文训练解决“用得好”

即使位置编码和系统都支持 128K，模型也可能不会有效使用长文信息。

常见失败：

- 只能找开头和结尾，忽略中间。
- 找到证据但引用错。
- 能找单点信息，不能综合多处证据。
- 长文本中前后约束冲突时不会处理。
- 输出时忘记早期系统要求。

长上下文训练要让模型见过类似任务：

- 长文档 QA。
- 多文档综合。
- 长代码仓库理解。
- 长对话状态跟踪。
- 证据引用和冲突处理。

这解释了为什么“支持 128K”不等于“128K 任务效果好”。能力来自位置方案、推理实现和训练数据共同作用。

# 6. 同族概念分组：RAG 是外部检索，不是长度外推

RAG 和长上下文经常被混在一起，但它们解决的问题不同。

| 方案 | 解决什么 | 不解决什么 |
|---|---|---|
| 长度外推 | 让模型能处理超训练长度位置 | 不保证能找到和综合信息 |
| 长上下文训练 | 让模型学习长文任务 | 不降低长输入成本 |
| 滑动窗口注意力 | 降低长序列计算 | 可能丢远距离依赖 |
| RAG | 从外部知识库取相关片段 | 检索失败时模型看不到信息 |

RAG 的核心是：

```text
先找相关信息，再把相关信息放入上下文
```

它适合知识库问答、企业文档、实时资料和大规模文档集合。长上下文适合完整合同审阅、长代码文件、长对话复盘、多证据综合等不容易提前检索裁剪的任务。

---

# 7. 工程含义：长上下文 vs RAG 怎么选

| 场景 | 更适合 |
|---|---|
| 用户问知识库中某个明确问题 | RAG |
| 需要引用最新外部文档 | RAG |
| 文档很多，但每次只相关少数片段 | RAG |
| 需要完整审阅一份长合同 | 长上下文 |
| 需要修改一个长代码文件 | 长上下文 |
| 需要跨多处证据综合 | 长上下文 + RAG |
| 成本敏感、请求高频 | 优先 RAG 和上下文压缩 |

实践中常见组合是：

```text
RAG 先召回相关片段
  │
  ├─► 长上下文容纳更多证据
  ├─► reranker 控制片段质量
  └─► 引用和评估检查答案是否忠实
```

# 8. 工程含义：长上下文评估不能只看 Needle

Needle-in-a-Haystack 测试把一条“针”藏在长文本里，看模型能否找回来。

它有价值，但边界明显：

- 它主要测找回，不充分测推理。
- 它不代表引用准确性。
- 它不代表多证据综合。
- 它不代表长代码修改。
- 它不代表 Agent 多轮状态管理。

长上下文评估应覆盖：

| 能力 | 例子 |
|---|---|
| 单点找回 | 在长文中找到某个事实 |
| 多点综合 | 合并多个位置的信息得出结论 |
| 引用准确 | 答案引用的片段确实支持结论 |
| 冲突处理 | 多份文档说法不一致时说明差异 |
| 长程约束 | 早期要求在后续输出中仍被遵守 |
| 成本延迟 | TTFT、KV Cache、吞吐是否可接受 |

# 9. 常见误区

## 9.1 支持 128K 就代表会用好 128K

不对。支持长窗口只说明“放得进”，还要看模型能否稳定找回、引用、推理和综合多处证据。

## 9.2 长度外推等于长上下文训练

不对。长度外推主要处理位置编码和推理长度扩展，长上下文训练则让模型真实学习长距离依赖和长文任务格式。

## 9.3 RAG 可以完全替代长上下文

不对。RAG 适合大规模外部知识检索，但多文档综合、完整合同审阅、长代码文件修改仍可能需要较长上下文。

## 9.4 Needle 高分等于长文推理强

不对。Needle 更像找回测试，不能充分代表多证据综合、引用准确性和复杂推理。

# 10. 面试 Q&A

## Q1：长度外推为什么困难？

因为训练和推理长度不一致会带来位置编码分布偏移、attention 分数变化、KV Cache 成本上升，以及模型没学过长文任务格式等问题。

## Q2：RoPE 为什么适合长上下文扩展？

RoPE 用旋转方式把位置信息注入 Q/K，天然表达相对位置，不依赖固定长度的位置表。但超过训练长度后仍会出现频率和分布偏移，所以需要插值、NTK scaling、YaRN 或长上下文微调。

## Q3：位置插值解决什么问题？

它把更长的位置范围压缩回模型熟悉的训练范围，降低超长位置分布偏移。但压缩会牺牲局部分辨率，通常需要长上下文微调恢复效果。

## Q4：支持 128K 是否说明长上下文能力强？

不一定。要区分“能输入 128K”和“能在 128K 中准确找证据、引用、推理、综合”。后者需要专门评估。

## Q5：长上下文和 RAG 怎么选？

明确知识库问答、实时资料和大规模文档集合优先 RAG；完整长文审阅、多处证据综合、长代码上下文更依赖长上下文。实际系统常把二者结合。
