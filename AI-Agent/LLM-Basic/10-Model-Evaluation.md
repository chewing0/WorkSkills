# 1. 核心问题：评估为什么是在找失败模式

评估 LLM 时，最容易问错问题：

> 这个模型强不强？

更好的问题是：

> 这个模型在我的目标任务上，什么时候会失败，失败代价有多大，能不能稳定改进？

LLM 不是单一能力系统。一个模型可能：

- 通用 benchmark 高，但业务格式经常错。
- 对话自然，但事实引用不可靠。
- 单轮问答强，但多轮状态管理差。
- 代码题会写，但真实仓库修改容易破坏上下文。
- RAG 答案流畅，但引用并不支持结论。

所以评估不是给模型贴一个“强/弱”标签，而是建立一张风险地图：

```text
目标任务
  │
  ├─► 能不能答对？
  ├─► 答案是否可验证？
  ├─► 格式是否稳定？
  ├─► 失败能否恢复？
  ├─► 延迟和成本是否可接受？
  └─► 上线后是否持续稳定？
```

# 2. 基础机制：先分清评估对象

不同类型的 LLM 系统，评估重点完全不同。

| 评估对象 | 主要问题 | 常见指标 |
|---|---|---|
| Base Model | 语言建模能力如何 | loss、PPL、下游 benchmark |
| Chat Model | 是否听指令、是否有帮助 | 人类偏好、rubric 评分、安全性 |
| Code Model | 能否生成可运行代码 | pass@k、单测通过率、仓库任务成功率 |
| RAG System | 是否基于证据回答 | 检索召回、忠实性、引用准确率 |
| Agent System | 是否能完成多步任务 | 工具选择、参数正确率、任务成功率、成本 |
| Online Product | 用户是否真的满意 | A/B、留存、人工质检、投诉率、延迟 |

这一步非常重要。因为很多争论来自把不同对象混在一起：

- 用 PPL 判断 Chat 体验。
- 用 MMLU 判断业务客服质量。
- 用 Needle 判断长文推理能力。
- 用一次 demo 判断 Agent 稳定性。

正确做法是先定义任务边界，再选指标。

# 3. Perplexity：适合语言建模监控，不等于助手质量

Perplexity 衡量模型预测文本时有多“困惑”：

$$
PPL = \exp\left(-\frac{1}{N}\sum_i \log P(x_i)\right)
$$

直觉：

- 如果模型很容易预测下一个 token，PPL 低。
- 如果模型对文本分布很不确定，PPL 高。

PPL 适合：

- 预训练过程监控。
- 比较同一 tokenizer、同一数据集上的语言建模 loss。
- 检查继续训练是否破坏基础语言分布。
- 观察领域适配是否让领域文本更可预测。

但 PPL 不等于助手质量：

- Chat 模型经过 SFT/RLHF/DPO 后，可能更会拒答、更符合偏好，但 PPL 不一定最低。
- PPL 低不代表事实正确。
- PPL 低不代表能遵守 JSON schema。
- 不同 tokenizer 下 PPL 不宜直接比较。
- 业务任务的好坏往往取决于指令遵循、证据、工具使用和安全边界。

面试里可以这样说：

> PPL 是语言建模指标，适合训练监控和基础模型比较；但对齐后的助手质量需要任务评估、人类偏好、事实性和安全性等指标共同判断。

# 4. 同族概念分组：离线评估只能回答部分问题

通用 Benchmark 的价值是提供公开、可复现的横向参考。

常见类型：

| 类型   | 衡量内容      | 典型风险              |
| ---- | --------- | ----------------- |
| 综合知识 | 多学科知识、推理  | 数据污染、选择题偏差        |
| 数学   | 分步推理、符号计算 | prompt 敏感，答案格式影响大 |
| 代码   | 函数生成、单测通过 | 与真实仓库开发差距大        |
| 阅读理解 | 文本理解和问答   | 数据集格式单一           |
| 多语言  | 跨语言能力     | 高资源语言和低资源语言差异大    |
| 长上下文 | 检索或长文任务   | 找针不等于复杂推理         |

Benchmark 的常见问题：

## 4.1 数据污染

如果测试题出现在训练数据中，模型分数会虚高。越热门的公开数据集，污染风险越高。

## 4.2 Prompt 敏感性

同一模型在不同 prompt、few-shot 示例、解码参数下可能差异很大。评测结果必须记录模板和参数。

## 4.3 选择题局限

选择题方便自动评分，但真实业务往往是开放生成、引用证据、调用工具或遵守格式。

## 4.4 不可迁移到业务

MMLU 高不代表客服好，HumanEval 高不代表能安全修改大型仓库，Needle 高不代表能综合多份合同条款。

因此 Benchmark 适合做：

- 初筛模型。
- 跟踪大版本变化。
- 判断能力大致上限。
- 对外报告参考。

不适合单独决定：

- 业务上线。
- 安全合规。
- Agent 自动化权限。
- 领域知识可靠性。

# 5. Chat 模型评估：看它是否像可靠助手

Chat 模型评估通常关注：

| 维度 | 要问的问题 |
|---|---|
| 指令遵循 | 是否按用户要求回答，是否遗漏约束 |
| 有用性 | 是否解决问题，而不是泛泛而谈 |
| 事实性 | 是否编造事实、数字、链接、引用 |
| 格式稳定 | 是否输出合法 JSON、表格、字段 |
| 安全性 | 是否拒绝危险请求，是否过度拒答 |
| 多轮一致性 | 是否记住当前对话状态，不前后矛盾 |
| 风格 | 是否符合产品语气和用户预期 |

Chat 评估不能只看“答案好不好看”。要尽量把抽象偏好拆成可判定规则。

例子：

```text
任务：把用户报销描述转换成 JSON。

坏评分规则：
  答案是否好。

好评分规则：
  1. 是否为合法 JSON。
  2. amount 是否为数字。
  3. currency 是否缺省为 CNY。
  4. date 缺失时是否返回 null。
  5. 不确定字段是否没有编造。
```

评估越接近真实任务约束，越能指导改进。

# 6. RAG 评估：拆开检索和生成

RAG 系统失败时，不能只怪模型。需要拆成四层：

```text
用户问题
  │
  ├─► 检索：有没有找到相关文档？
  ├─► 上下文：放进 prompt 的片段是否有用？
  ├─► 生成：答案是否忠实于上下文？
  └─► 引用：引用是否真的支持结论？
```

## 6.1 检索质量

常见指标：

- Recall@k：正确文档是否出现在前 k 个结果中。
- Precision@k：前 k 个结果中有多少相关。
- MRR：第一个相关结果排在多前。
- nDCG：排序质量。

关键问题：

- 向量召回是否漏掉关键词型问题。
- 关键词召回是否漏掉语义相近问题。
- reranker 是否把真正证据排到前面。

## 6.2 上下文质量

检索到了文档，不代表放进模型的上下文好。

需要看：

- chunk 是否切断关键段落。
- 上下文是否有冲突文档。
- 是否塞入太多无关内容。
- 是否把最新版本和旧版本混在一起。
- 是否包含表格、代码、图片说明等特殊格式。

## 6.3 生成忠实性

忠实性关注：

> 答案是否被给定上下文支持？

常见错误：

- 文档没说，模型自己补。
- 引用 A 文档，却回答 B 文档里的内容。
- 把多个片段错误拼接成不存在的结论。
- 对不确定问题没有说明无法判断。

## 6.4 引用准确性

引用不是装饰。它要能支撑答案里的关键结论。

可以检查：

- 引用片段是否包含答案依据。
- 引用位置是否正确。
- 多证据问题是否引用了所有必要证据。
- 答案和引用之间是否存在推理跳跃。

RAG 评估的核心结论：

> 先定位失败发生在检索、上下文、生成还是引用，再决定改 embedding、reranker、chunk、prompt 还是模型。

# 7. Agent 评估：看过程，不只看最终答案

Agent 的难点是多步决策。最终任务成功很重要，但只看最终成功率不够，因为失败可能来自不同环节。

需要评估的过程指标：

| 指标 | 要看什么 |
|---|---|
| 工具选择 | 是否选对工具，是否乱调用 |
| 参数正确 | API 参数、文件路径、时间范围是否正确 |
| 状态管理 | 是否记住当前计划和已完成步骤 |
| 失败恢复 | 工具报错后是否能修正 |
| 循环控制 | 是否反复做无效操作 |
| 成本控制 | token、工具调用、时间是否过高 |
| 安全边界 | 是否越权执行危险操作 |

一个 Agent 任务可以拆成轨迹：

```text
用户目标
  │
  ├─► 计划是否合理
  ├─► 工具是否选对
  ├─► 参数是否正确
  ├─► 观察结果是否理解
  ├─► 失败是否恢复
  └─► 最终产物是否满足要求
```

这类评估常常需要保存 trace：

- 每轮模型输入输出。
- 工具调用参数。
- 工具返回结果。
- 中间计划变化。
- 错误和重试。
- 最终结果。

对于 AI Agent 应用开发，过程评估比单轮问答更关键。因为一个看似正确的最终答案，可能背后做了高风险或高成本的动作。

# 8. LLM-as-a-Judge：让模型评模型，但要校准

LLM-as-a-Judge 是用一个模型对另一个模型的输出打分或比较。

常见方式：

| 方式 | 做法 | 适合 |
|---|---|---|
| Pairwise | 比较 A/B 哪个更好 | 模型版本对比 |
| Rubric 打分 | 按评分规则给 1-5 分 | 结构化质量检查 |
| Error Tagging | 标注错误类型 | 分析失败模式 |
| Reference-based | 对照标准答案评分 | 有黄金答案的任务 |

它的优势：

- 成本低于大规模人工评审。
- 可重复运行回归测试。
- 能处理开放生成任务。
- 可输出错误原因，便于分析。

但必须注意偏差：

- 偏好更长答案。
- 偏好格式更漂亮的答案。
- 可能被模型自信语气影响。
- 对事实细节也会误判。
- 同源模型可能偏好相似风格。

工程上应做校准：

```text
1. 抽样人工标注一批数据。
2. 用 judge 评分同一批数据。
3. 比较 judge 和人工一致性。
4. 调整 rubric、prompt 和评分阈值。
5. 上线后持续人工抽查。
```

不要把 LLM judge 当成绝对真理。它更适合作为可扩展的辅助评估器。

# 9. 工程含义：业务黄金集是真正有用的评估资产

业务黄金集是专门为目标场景构建的一组高质量测试样本。

它应该覆盖：

- 高频真实问题。
- 高风险问题。
- 边界样本。
- 历史失败案例。
- 用户容易误问的问题。
- 需要拒答或转人工的问题。
- 多轮和工具调用场景。

构建流程：

## 9.1 收集样本来源

来源可以包括：

- 线上日志脱敏。
- 客服工单。
- 搜索无结果问题。
- 人工专家设计。
- 历史事故和投诉。
- 产品核心流程。

## 9.2 设计评分规则

每类任务要有明确 rubric。

例如 RAG 问答：

| 评分项 | 通过标准 |
|---|---|
| 结论正确 | 关键事实和标准答案一致 |
| 有证据 | 引用能支持关键结论 |
| 不编造 | 上下文没有的信息不乱说 |
| 完整性 | 覆盖用户问题的所有约束 |
| 格式 | 按要求输出字段或结构 |

## 9.3 加入边界样本

只测简单样本会产生虚假安全感。边界样本包括：

- 信息不足。
- 多文档冲突。
- 时间敏感。
- 名称相似。
- 需要计算。
- 需要拒答。
- 需要工具失败恢复。

## 9.4 固化回归测试

每次改模型、prompt、RAG、工具、解码参数，都应跑黄金集。

目标不是追求一次高分，而是防止：

- 新版本修好 A，弄坏 B。
- prompt 改动破坏格式。
- 检索参数变化导致引用退化。
- 成本优化造成质量下降。

业务黄金集是 LLM 应用从 demo 走向工程系统的分界线。

# 10. 线上评估：离线高分不代表线上稳定

上线后还要监控：

| 类别  | 指标                     |
| --- | ---------------------- |
| 质量  | 点赞率、差评率、人工质检通过率、问题解决率  |
| 安全  | 违规回复、越权工具调用、敏感信息泄露     |
| 稳定性 | JSON 失败率、工具失败率、重试率     |
| 性能  | TTFT、TPOT、端到端延迟、超时率    |
| 成本  | token 消耗、工具调用次数、单位任务成本 |
| 漂移  | 新问题类型、知识库变化、用户行为变化     |

A/B 测试也要谨慎：

- 样本量是否足够。
- 用户群是否一致。
- 是否只看短期点击而忽略长期信任。
- 是否引入成本和延迟指标。
- 是否人工抽查失败样本。

线上评估最有价值的产物不是一个总分，而是持续更新的失败样本池。它会反过来补充黄金集、改进 prompt、优化 RAG 和训练数据。

# 11. 常见误区

## 11.1 “Benchmark 第一就适合业务”

不一定。公开 benchmark 只能说明部分能力，业务还要看领域知识、格式约束、事实引用、成本和安全边界。

## 11.2 “PPL 越低，Chat 越好”

不一定。PPL 是语言建模指标，对齐后的助手质量还取决于指令遵循、偏好、安全和事实性。

## 11.3 “RAG 答案错就是模型差”

不一定。可能是检索没召回、chunk 切错、reranker 排错、上下文冲突或引用规则不清。

## 11.4 “Agent 成功率高就可以放权”

不够。还要看失败模式、越权风险、工具参数错误、循环调用和恢复能力。高风险工具必须有权限和审计。

## 11.5 “LLM-as-a-Judge 可以完全替代人工”

不应完全替代。Judge 需要人工校准和抽样复核，尤其是事实、合规、高风险场景。

# 12. 面试 Q&A

## Q1：为什么说评估 LLM 不能只看一个分数？

因为 LLM 能力是多维的。基础语言能力、对话质量、事实性、RAG 忠实性、Agent 工具使用、延迟和成本都可能独立变化。一个总分无法定位失败模式，也无法指导工程改进。

## Q2：PPL 适合评估什么，不适合评估什么？

PPL 适合评估语言建模能力和训练过程中的分布拟合情况，尤其是在同一 tokenizer、同一验证集上比较。不适合直接评估助手质量、事实性、指令遵循、工具调用和业务满意度。

## Q3：通用 Benchmark 有哪些局限？

主要包括数据污染、prompt 敏感、选择题和真实业务差距大、不同评测框架不可直接比较。它适合做初筛和横向参考，但不能替代业务黄金集。

## Q4：RAG 应该怎么评估？

应拆成检索质量、上下文质量、生成忠实性和引用准确性。先定位错误发生在哪一层，再决定改 embedding、reranker、chunk、prompt、引用规则还是模型。

## Q5：Agent 评估为什么要看过程？

Agent 是多步系统。最终成功或失败可能来自计划、工具选择、参数、状态管理、错误恢复或权限控制。只有看过程 trace，才能知道系统是否可靠、可控、可优化。

## Q6：LLM-as-a-Judge 怎么用才靠谱？

用 pairwise 或 rubric 明确评分标准，再用人工标注样本校准 judge 的一致性。上线后持续抽样复核，并警惕偏好长答案、漂亮格式和自信语气等偏差。

## Q7：业务黄金集应该怎么设计？

从真实日志、工单、历史失败、高风险流程和专家设计中采样，覆盖高频、边界、冲突、拒答、多轮和工具场景。为每类任务写清评分规则，并作为模型、prompt、RAG 和工具改动后的回归测试集。
