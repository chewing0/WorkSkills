> **核心考点**：训练目标决定模型学会什么。预训练让模型学会“语言、知识和模式”；SFT 让模型学会“按指令回答”；偏好对齐让模型学会“哪个回答更好”；工具和安全训练让模型学会“在系统边界内行动”。不要把 RLHF、DPO、KTO 当成名词表背，要先理解每个阶段在修什么问题。

# 1. 核心问题：训练目标如何把文本预测器变成助手

LLM 训练可以理解为把一个模型一步步塑造成助手。

最开始，模型只是随机参数。预训练之后，它变成一个很强的“文本续写器”。SFT 之后，它开始像一个“听指令的助手”。偏好对齐之后，它更像一个“知道什么回答更合适的助手”。再经过工具、安全、领域训练，它才更适合真实应用。

```text
随机模型
  │
  ├─► 预训练：学会预测文本
  │      └─ 得到 Base Model
  │
  ├─► SFT：学会按照指令回答
  │      └─ 得到 Instruct / Chat Model
  │
  ├─► 偏好对齐：学会偏向更好的回答
  │      └─ 更有用、更安全、更符合人类偏好
  │
  ├─► 专项训练：工具、JSON、代码、数学、领域、安全
  │
  └─► 评估和线上反馈：持续发现问题
```

每一阶段解决的问题不同：

| 阶段 | 解决的问题 | 典型输入 | 模型学到什么 |
|---|---|---|---|
| 预训练 | 模型还不懂语言和世界 | 海量自然文本、代码、书籍 | 语言、知识、格式、模式 |
| 继续预训练 | 模型缺某个领域或长度分布 | 医疗、法律、代码、长文档 | 领域知识和分布 |
| SFT | 模型会续写但不一定听话 | 指令和标准回答 | 指令遵循、格式、多轮对话 |
| 偏好对齐 | 模型会回答但不知道哪个更好 | chosen/rejected 或评分 | 有用性、安全性、风格偏好 |
| 专项训练 | 模型缺某种工程能力 | 工具轨迹、JSON、测试反馈 | 工具调用、结构化输出、推理习惯 |

# 2. 基础机制：训练目标到底是什么

训练目标就是告诉模型：

> 你每次犯错时，应该朝哪个方向改参数？

模型输出一个概率分布，训练目标计算 loss，优化器根据 loss 更新参数。

```text
输入 token
  │
  ├─► 模型输出概率
  │
  ├─► 与目标答案比较，得到 loss
  │
  └─► 反向传播，更新参数
```

不同目标会塑造不同能力。

让模型“补空”，它会更擅长理解。

让模型“预测下一个 token”，它会更擅长生成。

让模型“模仿好回答”，它会更听指令。

让模型“偏向 chosen 而远离 rejected”，它会更符合偏好。

# 3. 同族概念分组：预训练目标如何塑造基础能力

Decoder-only LLM 最常见的预训练目标是 Causal Language Modeling，也就是预测下一个 token。

给定文本：

```text
Transformer 的核心机制是 注意力
```

模型实际学的是一连串任务：

```text
Transformer -> 的
Transformer 的 -> 核心
Transformer 的 核心 -> 机制
Transformer 的 核心 机制 -> 是
Transformer 的 核心 机制 是 -> 注意力
```

公式：

$$
P(x_t \mid x_{<t})
$$

损失：

$$
\mathcal{L}_{CLM}
= -\sum_{t=1}^{T}\log P_\theta(x_t \mid x_{<t})
$$

这就是看起来很朴素、但威力很大的 next token prediction。

## 3.1 为什么“猜下一个 token”能学到知识

因为要猜对下一个 token，模型不得不学习文本背后的规律。

例子：

```text
巴黎是法国的首都，埃菲尔铁塔位于
```

如果模型经常在训练数据中看到相关文本，它会提高“巴黎”这类 token 的概率。

再看代码：

```python
for i in range(10):
    print(
```

要预测后面的 token，模型要学会括号、缩进、变量、函数调用等代码结构。

数学题解也是类似：

```text
两边同时除以 2，得到 x =
```

模型要预测合理的下一步，就要压缩题解中的推理模式。

所以 next token prediction 不只是背句子，它会逼迫模型学习：

- 语法。
- 事实。
- 代码结构。
- 文章格式。
- 问答模式。
- 推理文本中的步骤规律。

## 3.2 为什么预训练模型还不是助手

预训练目标只告诉模型：

> 继续写一段最像训练数据的文本。

它没有明确告诉模型：

- 用户问问题时要直接回答。
- 不知道时不要编。
- 输出 JSON 时要严格合法。
- 面对危险请求要拒绝。
- 多轮对话要保持角色边界。

所以 Base Model 可能这样续写：

```text
用户：解释 KV Cache。
助手：
用户：再解释一下 Attention。
```

它可能继续模仿对话文本，而不是稳定地完成助手任务。

这就是为什么需要 SFT。

# 4. Causal Mask：训练并行与生成约束如何同时成立

训练时，为了效率，模型会一次处理整段文本；但每个位置不能看未来 token，否则预测下一个 token 就作弊了。

Causal Mask：

```text
        key position
        1  2  3  4
query 1 ✓  ✗  ✗  ✗
query 2 ✓  ✓  ✗  ✗
query 3 ✓  ✓  ✓  ✗
query 4 ✓  ✓  ✓  ✓
```

这样可以同时满足：

- **训练并行**：整段文本一次送入 GPU。
- **生成约束**：每个位置只能依赖过去。

这解释了一个常见问题：

> 训练时模型明明一次看完整句子，为什么不算偷看？

答案是：它拿到了完整张量，但 attention mask 阻止每个位置读取未来 token。

# 5. MLM：为什么 BERT 更像阅读理解模型

BERT 类 Encoder-only 模型常用 Masked Language Modeling。

例子：

```text
原文: 我 喜欢 学习 自然语言处理
输入: 我 喜欢 [MASK] 自然语言处理
目标: 学习
```

模型可以看 `[MASK]` 左右两边，所以它学到的是：

> 给定完整上下文，恢复缺失信息。

这非常适合理解任务，因为分类、抽取、匹配通常都允许模型先看完整输入。

## 5.1 MLM 擅长什么

- 句子表示。
- 分类。
- NER。
- 语义匹配。
- rerank。
- 抽取式阅读理解。

## 5.2 MLM 为什么不天然适合 Chat

聊天生成要求：

```text
历史 token -> 下一个 token -> 再下一个 token
```

MLM 训练要求：

```text
左文 + [MASK] + 右文 -> 被遮住的 token
```

二者不一致。

所以 BERT 不是“不会语言”，而是训练目标和推理形式不适合开放式自回归生成。

# 6. Seq2Seq：为什么 T5 适合输入到输出转换

Encoder-Decoder 模型常用 Seq2Seq 或 Span Corruption。

翻译例子：

```text
输入: translate English to Chinese: I love NLP.
输出: 我喜欢自然语言处理。
```

模型分两步：

1. Encoder 双向读完整输入。
2. Decoder 一步步生成输出，并通过 Cross-Attention 回看 Encoder 表示。

这类训练目标适合：

- 翻译。
- 摘要。
- 改写。
- 纠错。
- 文本到结构化结果。

T5 的关键思想是 text-to-text：所有任务都写成“文本输入 -> 文本输出”。这和 Decoder-only 后来统一任务接口的思想很接近，只是架构不同。

# 7. 继续预训练：补知识还是改行为

继续预训练是在已有 Base Model 上继续做语言建模训练。

它解决的问题是：

> 模型没有见过足够多的某类文本，所以对这个领域的语言、知识、格式不熟。

适合：

- 医疗、法律、金融等领域语料。
- 企业内部文档。
- 代码仓库。
- 长文档和长对话。
- 特定语言或方言。

## 7.1 继续预训练 vs SFT

这是非常高频的判断题。

| 问题 | 更像继续预训练 | 更像 SFT |
|---|---|---|
| 模型不知道某领域术语 | 是 | 否 |
| 模型知道知识但回答格式不好 | 否 | 是 |
| 模型不会企业文档里的概念 | 是 | 可辅助 |
| 模型不会输出固定 JSON | 否 | 是 |
| 模型中文表达差 | 可能是 | 也可能是 |
| 模型不遵守系统指令 | 否 | 是 |

一句话：

> 缺知识和分布，用继续预训练；缺行为和格式，用 SFT。

## 7.2 灾难性遗忘

如果继续预训练只用很窄的领域数据，模型可能变得“只会领域话”，通用能力下降。

缓解方式：

- 混入通用数据。
- 降低学习率。
- 控制训练步数。
- 使用高质量领域语料。
- 同时评估通用集和领域集。

# 8. 同族概念分组：后训练如何改变模型行为

后训练不是一堆互相独立的方法名。它们都在解决同一个问题：

> Base Model 会续写文本，但不一定会按用户意图、产品格式和安全边界行动。

可以把后训练分成三层：

| 层次 | 代表方法 | 主要改变 |
|---|---|---|
| 模仿好答案 | SFT | 学会指令、格式、对话和工具调用样式 |
| 比较哪个更好 | RLHF、DPO | 在多个可能回答中偏向更有用、更安全的回答 |
| 简化偏好信号 | KTO、ORPO 等 | 用更容易收集的反馈或更简单目标优化偏好 |

## 8.1 SFT：把续写器教成助手

SFT（Supervised Fine-Tuning）是监督微调。它用高质量指令数据告诉模型：

> 遇到这种用户请求，应该这样回答。

样本形式：

```json
{
  "messages": [
    {"role": "system", "content": "你是一个严谨的助手。"},
    {"role": "user", "content": "解释 KV Cache。"},
    {"role": "assistant", "content": "KV Cache 是一种推理缓存机制..."}
  ]
}
```

训练时通常只对 assistant 内容计算 loss，system/user 作为上下文。

### SFT 改变了什么

SFT 主要改变模型行为：

- 看到问题后直接回答。
- 遵守 system/user/assistant 角色。
- 按指定格式输出。
- 学会多轮对话。
- 学会拒答边界。
- 学会工具调用格式。

它不主要负责从零注入大量世界知识。

如果一个模型完全没学过医学知识，只靠几千条医学问答 SFT，很难真正变成可靠医学模型。

### 为什么 SFT 数据质量很重要

SFT 是模仿学习。数据怎么写，模型就怎么学。

坏数据会让模型学会：

- 过度啰嗦。
- 模板化开头。
- 不懂也编。
- JSON 字段不稳。
- 随便道歉。
- 过度拒答。

好数据应该：

- 问题真实。
- 答案正确。
- 格式稳定。
- 难度分层。
- 覆盖边界情况。
- 对不知道的问题有正确处理方式。

### SFT 为什么还不够

同一个问题可能有多个回答：

```text
回答 A：正确但啰嗦。
回答 B：正确且清晰。
回答 C：看似清晰但事实错。
回答 D：安全但过度拒答。
```

SFT 只告诉模型“模仿某个答案”，但没有系统告诉它：

> 多个可行回答里，哪一个更好？

这就需要偏好对齐。

## 8.2 偏好对齐：从“会回答”到“答得更好”

偏好对齐使用比较数据，而不只是标准答案。

例子：

```text
prompt: 解释 Q/K/V

chosen:
Q 是查询，K 是被匹配的索引，V 是真正被聚合的信息...

rejected:
QKV 是三个参数，模型用它们算结果...
```

模型要学会提高 chosen 的概率，降低 rejected 的概率。

偏好对齐优化的是：

- 清晰度。
- 有用性。
- 安全性。
- 事实性倾向。
- 拒答边界。
- 风格偏好。
- 格式稳定性。

---

### RLHF：训练一个“评委”，再用评委调模型

RLHF 的经典流程：

```text
同一个 prompt 采样多个回答
  │
  ├─► 人类标注哪个更好
  │
  ├─► 训练 Reward Model
  │
  └─► 用 PPO 优化语言模型
```

#### Reward Model 是什么

Reward Model 像一个学出来的评委：

```text
输入: prompt + answer
输出: reward 分数
```

它不生成答案，只判断答案好不好。

#### 为什么还要 PPO 和 KL

如果只追求 reward，模型可能钻 Reward Model 空子。

例如：

- 变得特别啰嗦，因为评委偏好长答案。
- 用很多“看起来严谨”的格式掩盖错误。
- 迎合用户错误前提。

所以 PPO 里通常要加 KL 约束，让模型不要离原模型太远：

```text
提高 reward，同时不要偏离 reference model 太多
```

#### RLHF 的本质

RLHF 不是让模型突然拥有知识，而是调整模型的行为分布：

> 在多个可能回答中，更倾向于人类偏好的那类。

它能改善体验，但不能单独保证事实正确。事实性仍需要数据、RAG、工具和评估。

---

### DPO：不用单独训练评委，直接学偏好差异

DPO（Direct Preference Optimization）也使用 chosen/rejected 数据：

```text
(prompt, chosen, rejected)
```

但它不显式训练 Reward Model，也不跑 PPO。

直觉：

> 让模型更愿意生成 chosen，更不愿意生成 rejected，同时不要偏离参考模型太远。

#### DPO 为什么受欢迎

相比 RLHF：

- 流程更简单。
- 训练更稳定。
- 工程成本更低。
- 不需要单独维护 Reward Model。

#### DPO 不是魔法

DPO 的上限仍然依赖偏好数据。

如果 chosen/rejected 本身质量差，模型会学歪。

如果 rejected 太弱，模型学不到细微偏好。

如果 chosen 只是更长不更准，模型可能学会啰嗦。

#### RLHF vs DPO

| 维度 | RLHF | DPO |
|---|---|---|
| 核心思路 | 学一个 Reward Model，再优化模型 | 直接用偏好对优化模型 |
| 训练复杂度 | 高 | 较低 |
| 稳定性 | 更难 | 通常更稳 |
| 是否需要 PPO | 常见需要 | 不需要 |
| 关键风险 | reward hacking | 偏好数据质量 |

---

### KTO、ORPO 等方法怎么理解

这些方法不需要死背公式，可以记它们想解决的问题。

#### KTO

KTO 可以使用“这个回答好/不好”的反馈，而不一定要同一个 prompt 下的 chosen/rejected 成对比较。

适合：

- 只有单条回答好坏标注。
- 成对偏好数据不好构造。

#### ORPO

ORPO 试图把 SFT 和偏好优化合并到一个目标中。

直觉：

- 一边模仿 chosen。
- 一边拉开 chosen 和 rejected。

#### 记忆方式

```text
RLHF：先训练评委，再强化学习。
DPO：不用评委，直接比较 chosen/rejected。
KTO：可以用好/坏反馈。
ORPO：把模仿和偏好优化合在一起。
```

重点不是名字，而是知道：它们都在解决“如何让模型偏向更好回答”。

# 9. 工具调用和结构化输出训练

Agent 模型不仅要会回答，还要会行动。

工具调用样本通常包含：

```json
{
  "user": "查订单 A123 的物流",
  "tool_call": {
    "name": "get_order_status",
    "arguments": {"order_id": "A123"}
  },
  "tool_result": {
    "status": "运输中",
    "eta": "2026-05-23"
  },
  "assistant": "订单 A123 当前运输中，预计 2026-05-23 送达。"
}
```

模型要学会：

- 什么时候该调用工具。
- 调哪个工具。
- 参数怎么填。
- 工具失败怎么修正。
- 不要编造工具结果。
- 最终回答要基于工具返回。

这类能力光靠通用预训练很难稳定，需要 SFT 数据、schema 约束、失败样本和线上评估共同完成。

# 10. 安全对齐：不是只教模型拒绝

安全对齐的目标不是让模型什么都拒绝，而是让它学会边界。

它要区分：

```text
合法请求: 如何在 Linux 中 kill 一个进程？
危险请求: 如何破坏别人服务器上的进程？
双用途请求: 如何进行渗透测试？
```

好的安全数据应该包含：

- 明确有害请求 -> 拒答。
- 合法相似请求 -> 正常帮助。
- 双用途请求 -> 澄清或给安全版本。
- Prompt injection -> 坚持指令层级。
- 隐私请求 -> 拒绝或脱敏。

如果只堆拒答样本，模型会过度保守。

# 11. 数据比方法名更重要

训练算法很重要，但数据往往决定上限。

## 11.1 预训练数据看什么

- 规模是否足够。
- 去重是否彻底。
- 质量过滤是否合理。
- 多语言比例是否符合目标。
- 代码/数学/领域数据是否覆盖。
- benchmark 是否污染。

## 11.2 SFT 数据看什么

- 指令是否真实。
- 回答是否正确。
- 格式是否一致。
- 是否覆盖边界和失败情况。
- 是否包含多轮状态。
- 是否包含拒答和澄清。
- 是否符合目标用户风格。

## 11.3 偏好数据看什么

- chosen 是否真的更好。
- rejected 是否有代表性。
- 标注者标准是否一致。
- 是否偏好“长但空”的回答。
- 是否覆盖安全、事实、格式、工具等维度。

一句话：

> 低质量数据会把任何高级算法拖下水。

# 12. 工程含义：如何选择训练方法

先判断问题类型。

| 问题              | 更合适的方法                            |
| --------------- | --------------------------------- |
| 缺领域知识           | 继续预训练，或 RAG                       |
| 知道知识但不会按格式答     | SFT                               |
| 回答有多个版本，不知道哪个更好 | DPO / RLHF                        |
| JSON 不稳定        | 结构化 SFT + schema decoding + retry |
| 工具调用差           | 工具轨迹 SFT + 参数校验 + 失败样本            |
| 过度拒答            | 安全边界数据重做 + 偏好对齐                   |
| 数学/代码弱          | 专项数据 + 可验证反馈 + 测试集评估              |
| 幻觉严重            | RAG/工具/引用校验，不能只靠对齐                |

一个实用判断：

```text
不知道 -> 补知识
不会做 -> 补示范
做得不好 -> 补偏好
不稳定 -> 补约束和评估
```

# 13. 评估：训练完不代表能用

不同阶段要看不同指标。

## 13.1 预训练看什么

- validation loss。
- Perplexity。
- 基础 benchmark。
- 数据污染检查。

PPL 衡量模型预测 token 的不确定性：

$$
PPL = \exp\left(-\frac{1}{N}\sum_i \log P(x_i)\right)
$$

但 PPL 不等于 Chat 体验。

## 13.2 SFT / 对齐看什么

- 指令遵循。
- 格式稳定。
- 事实性。
- 安全边界。
- 多轮一致性。
- 工具调用准确率。
- 用户偏好胜率。

## 13.3 应用上线看什么

- 任务成功率。
- 用户采纳率。
- 人工接管率。
- JSON 解析失败率。
- 工具调用失败率。
- 幻觉投诉。
- 延迟和成本。

# 14. 常见误区

## 14.1 “SFT 能注入所有知识”

不对。SFT 数据量通常远小于预训练，主要改变行为和格式。知识缺失更适合继续预训练、RAG 或工具。

## 14.2 “DPO 一定比 RLHF 好”

不对。DPO 简单稳定，但复杂偏好、多目标安全或在线反馈场景中，RLHF/RLAIF 仍可能有价值。

## 14.3 “PPL 越低，助手越好”

不对。PPL 是语言建模指标，不直接衡量指令遵循、事实性、工具调用和安全。

## 14.4 “对齐能彻底解决幻觉”

不能。幻觉来自知识缺失、上下文不足、训练目标和采样不确定性。事实类任务通常需要 RAG、工具、引用和校验。

## 14.5 “安全就是多加拒答数据”

不对。安全是边界学习。只加拒答会导致合法请求也被拒绝。

# 15. 面试 Q&A

## Q1：预训练、SFT、偏好对齐分别解决什么问题？

**答**：预训练让模型学语言、知识和模式；SFT 让模型学会按指令和对话格式回答；偏好对齐让模型在多个可能回答中更倾向于有用、安全、符合人类偏好的回答。

## Q2：为什么 Base Model 不适合直接做聊天助手？

**答**：Base Model 的目标是续写高概率文本，不是稳定完成用户指令。它可能知识很强，但不一定遵守角色、格式、安全边界和多轮对话习惯。

## Q3：为什么 next token prediction 能学到推理能力？

**答**：要预测题解、代码和复杂文本的下一个 token，模型必须压缩其中的结构和步骤模式。规模和数据足够时，这些模式可以迁移到新的推理任务。

## Q4：RLHF 和 DPO 的区别是什么？

**答**：RLHF 通常先训练 Reward Model，再用 PPO 优化模型；DPO 直接用 chosen/rejected 偏好对优化模型，不显式训练 Reward Model，流程更简单。

## Q5：继续预训练和 SFT 怎么选？

**答**：缺领域知识或文本分布时，优先继续预训练；模型知道知识但不会按指令、格式或业务流程回答时，优先 SFT。

## Q6：为什么偏好数据会让模型变啰嗦？

**答**：如果标注者偏好长答案，chosen 往往比 rejected 更长，模型会学到“更长等于更好”。所以偏好数据要控制准确性、简洁性和任务适配。

## Q7：工具调用能力怎么训练？

**答**：需要工具 schema、用户请求、工具选择、参数、工具结果和最终回答的轨迹数据。训练之外还要有 schema validation、错误重试和调用成功率评估。

## Q8：安全对齐为什么容易过度拒答？

**答**：如果数据只告诉模型哪些请求要拒绝，没有提供合法相似请求和边界样本，模型会扩大拒答范围。安全训练要同时教拒绝、帮助和澄清。

## Q9：为什么 benchmark 泄漏会影响训练评估？

**答**：如果测试集样本进入训练数据，模型可能记住答案，评估分数会虚高，不能反映真实泛化能力。预训练、SFT 和偏好数据都要做污染检查。

## Q10：如何判断一个后训练模型是否可用？

**答**：不能只看 PPL 或排行榜。要看业务黄金集、指令遵循、事实性、安全边界、格式稳定、工具调用、多轮一致性、延迟和成本。

# 16. 记忆口诀

```text
预训练：把模型训练成强大的文本预测器。
SFT：把文本预测器教成听指令的助手。
偏好对齐：让助手知道哪个回答更好。
继续预训练：补知识和语料分布。
工具训练：学会行动，不要编结果。
安全对齐：学边界，不是只学拒绝。
评估：PPL 看地基，业务集看能不能用。
```
