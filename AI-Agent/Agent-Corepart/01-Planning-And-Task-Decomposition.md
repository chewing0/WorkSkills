> **核心考点**：规划不是让模型写一个漂亮列表，而是把模糊目标拆成可执行、可验证、可恢复的步骤。好的计划必须能指导行动，也必须允许根据反馈调整。

---

# 1. 核心问题：为什么 Agent 需要规划

用户目标常常是开放的：

```text
帮我分析这个项目为什么测试失败，并修一下。
```

这里至少包含：

- 查看失败日志。
- 定位失败模块。
- 阅读相关代码。
- 形成修复方案。
- 修改代码。
- 运行测试。
- 汇总结果。

如果模型直接给最终答案，很容易漏步骤。规划让 Agent 先建立任务结构，再逐步推进。

---

# 2. 好计划的标准

好计划应该满足：

| 标准 | 含义 |
|---|---|
| 面向目标 | 每一步都服务最终目标 |
| 可执行 | 步骤能转成工具调用或具体操作 |
| 可验证 | 每一步完成后知道是否成功 |
| 有依赖顺序 | 先拿信息，再判断，再行动 |
| 有停止条件 | 知道什么时候完成或中止 |
| 可调整 | 工具失败或新信息出现时能改计划 |

差计划常见问题：

- 步骤太抽象，比如“深入分析问题”。
- 没有验证方式。
- 忽略权限和风险。
- 一开始就执行高风险动作。
- 没有失败分支。

# 3. 任务拆解

任务拆解可以按几种方式。

## 3.1 按阶段拆

```text
理解需求 -> 收集信息 -> 制定方案 -> 执行 -> 验证 -> 汇报
```

适合调研、代码修改、数据分析。

## 3.2 按子目标拆

```text
目标：完成客服退款
  ├─► 识别意图
  ├─► 获取订单号
  ├─► 查询订单
  ├─► 判断退款条件
  ├─► 请求用户确认
  └─► 执行退款或转人工
```

适合业务流程。

## 3.3 按风险拆

把只读操作和写操作分开：

```text
先查询和分析
再提出计划
确认后执行写操作
```

适合文件修改、API 写入、支付、删除等高风险动作。

# 4. ReAct：边观察边行动

ReAct 适合环境反馈很重要的任务。

```text
观察：用户问题
思考：需要查订单
行动：query_order
观察：订单已签收 9 天
思考：需要查退货政策
行动：search_policy
观察：7 天内可退
最终：说明不满足自动退货条件
```

优点：

- 灵活。
- 能根据工具结果调整。
- 适合信息不足场景。

风险：

- 工具循环。
- 中间思路不稳定。
- 观察结果被恶意内容注入。
- 没有全局计划时容易漂移。

---

# 5. Plan-and-Execute：先全局计划再执行

适合任务较长、步骤较清楚的场景：

```text
1. 读取测试失败日志
2. 找到失败测试对应代码
3. 分析失败原因
4. 修改最小范围代码
5. 运行相关测试
6. 总结修改
```

优点：

- 结构清楚。
- 用户容易理解。
- 便于 checkpoint。

风险：

- 初始计划可能错。
- 计划过细会僵化。
- 新信息出现时需要重规划。

工程上常用：

```text
先制定计划
执行一步
观察结果
必要时更新计划
```

# 6. 动态重规划

Agent 执行中会遇到：

- 工具失败。
- 权限不足。
- 文件不存在。
- 检索无结果。
- 用户补充新约束。
- 测试结果和预期不符。

这时不能机械执行旧计划。需要重规划：

```text
当前计划是否仍然有效？
  │
  ├─► 是：继续下一步
  └─► 否：说明原因，调整计划
```

重规划要避免无边界探索。应限制：

- 最大重试次数。
- 最大工具调用次数。
- 最大执行时间。
- 高风险动作必须确认。

---

# 7. 停止条件

Agent 必须知道什么时候停止。

常见停止条件：

- 目标完成。
- 缺少必要信息，需要问用户。
- 工具失败超过重试次数。
- 没有权限继续。
- 超过成本或时间预算。
- 检测到循环。
- 需要人工审批。

没有停止条件，Agent 很容易陷入“继续搜索、继续分析、继续尝试”的循环。

---

# 8. 计划评估

评估计划要看：

- 是否覆盖用户目标。
- 是否遗漏关键依赖。
- 是否先做只读检查再写入。
- 是否有验证步骤。
- 是否有风险控制。
- 是否过度复杂。
- 是否能在预算内完成。

可以让模型生成计划后按清单自检，但高风险任务仍应由系统规则和人工确认控制。

---

# 9. 常见误区

## 9.1 计划越详细越好

不一定。过细计划容易僵化，也会浪费 token。计划应足够指导执行，但保留调整空间。

## 9.2 有计划就不会出错

计划只是初始假设。工具结果可能推翻假设，必须支持重规划。

## 9.3 复杂任务都适合全自动

不一定。复杂且高风险任务应拆出人工确认点。

## 9.4 规划可以替代评估

不能。计划合理不代表执行正确。仍要验证每一步结果。

# 10. 面试 Q&A

## Q1：Agent 规划解决什么问题？

规划把模糊目标拆成可执行步骤，明确依赖、验证方式和停止条件，降低模型一步到位时遗漏约束的风险。

## Q2：ReAct 和 Plan-and-Execute 如何选择？

如果任务依赖环境反馈、需要边查边判断，用 ReAct。若任务目标清楚、步骤较长，先计划再执行更清晰。生产系统常结合两者。

## Q3：如何防止 Agent 死循环？

设置最大工具调用次数、最大重试次数、时间预算、循环检测和停止条件。重复失败时应请求人工或向用户澄清。

## Q4：什么时候需要人工确认？

涉及写入、删除、支付、发消息、外部不可逆操作、敏感信息或权限边界时，需要人工确认或系统审批。
