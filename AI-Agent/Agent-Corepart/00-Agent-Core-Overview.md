> **核心考点**：Agent 不是“一个会聊天的 LLM”，而是一个能围绕目标进行多步决策、调用工具、更新状态并根据反馈继续行动的系统。LLM 是 Agent 的决策部件之一，不是整个 Agent。

---

# 1. 核心问题：Agent 到底是什么

普通 Chatbot 的典型模式是：

```text
用户输入 -> 模型回答
```

RAG 应用的典型模式是：

```text
用户问题 -> 检索证据 -> 模型基于证据回答
```

Agent 则多了一层“行动闭环”：

```text
目标
  │
  ├─► 观察当前状态
  ├─► 决定下一步
  ├─► 调用工具或执行动作
  ├─► 读取反馈
  ├─► 更新状态
  └─► 判断是否完成或继续
```

也就是说，Agent 的核心不是回答一次，而是围绕目标持续推进任务。

---

# 2. Agent 的最小闭环

一个最小 Agent 至少包含：

| 组件 | 作用 |
|---|---|
| Goal | 当前任务目标 |
| State | 当前进度、上下文、约束和历史结果 |
| Planner | 决定下一步做什么 |
| Tool Selector | 判断是否调用工具、调用哪个工具 |
| Action Executor | 执行工具、API、代码或文件操作 |
| Observer | 读取行动结果 |
| Stop Condition | 判断完成、失败、超预算或需要人工 |

可以抽象成：

```text
while not done:
  observe(state)
  decide(next_action)
  execute(action)
  update(state)
```

这看起来简单，但每一步都有工程风险：目标可能模糊、状态可能丢失、工具可能失败、动作可能越权、循环可能停不下来。

---

# 3. Agent 和 Workflow 的关系

Workflow 是预先定义好的流程：

```text
步骤 A -> 步骤 B -> 步骤 C
```

Agent 更强调动态决策：

```text
根据当前状态选择下一步
```

真实系统常常是两者结合：

- 固定、安全、高风险步骤用 workflow 控制。
- 模糊、开放、需要语言理解的部分交给 Agent 决策。

例如退款客服：

```text
模型负责：理解用户意图、提取订单号、解释政策
系统负责：查询订单、判断权限、计算金额、发起退款
工作流负责：必须先确认，再执行高风险动作
```

不要把所有流程都交给模型自由发挥。可靠 Agent 往往是“模型决策 + 程序护栏”的组合。

# 4. 三种常见 Agent 范式

## 4.1 ReAct

ReAct 把推理和行动交替：

```text
思考 -> 行动 -> 观察 -> 再思考 -> 再行动
```

适合工具调用、检索、网页操作等需要根据反馈继续推进的任务。

风险是循环、工具误用和观察结果被误解。

## 4.2 Plan-and-Execute

先制定计划，再逐步执行：

```text
生成计划 -> 执行步骤 1 -> 执行步骤 2 -> 汇总结果
```

适合长任务、代码修改、调研、复杂分析。

风险是早期计划错误会影响后续步骤，因此需要允许动态修正。

## 4.3 State Machine Agent

把任务拆成明确状态：

```text
等待信息 -> 查询工具 -> 等待确认 -> 执行动作 -> 完成
```

适合生产系统和高风险业务。状态机限制模型自由度，牺牲一些灵活性，换来可控性和可审计性。

# 5. Agent 适合做什么

适合：

- 多步信息收集。
- 多工具组合。
- 代码辅助和仓库修改。
- 数据分析和报告生成。
- 客服流程辅助。
- 需要根据反馈调整策略的任务。
- 半自动化办公流程。

不适合完全放权：

- 高风险金融交易。
- 删除生产数据。
- 无人工确认的支付、退款、发信。
- 法律、医疗等高风险最终决策。
- 权限边界不清的内部系统操作。

Agent 能提高自动化程度，但越接近真实动作，越需要权限、审计和人工确认。

# 6. 常见失败模式

## 6.1 目标漂移

Agent 在多步执行中忘记最初目标，开始处理旁支问题。

## 6.2 死循环

反复调用同一个工具、重复搜索、重复修复同一个错误。

## 6.3 工具幻觉

模型编造不存在的工具、参数或工具结果。

## 6.4 状态丢失

多轮任务中忘记已完成步骤、用户约束或工具返回结果。

## 6.5 越权行动

模型尝试执行没有授权的动作，或把用户输入当成足够授权。

## 6.6 成本失控

多次检索、反复生成、长上下文和工具循环导致 token、时间和 API 成本过高。

# 7. 常见误区

## 7.1 Agent 越自主越好

不一定。自主性越高，风险也越高。生产系统要根据任务风险决定自动化边界。

## 7.2 Agent 就是 ReAct prompt

不对。ReAct 只是 Agent 的一种决策模式。生产 Agent 还需要状态、权限、工具、审计、评估和恢复机制。

## 7.3 大模型可以替代工作流

不应完全替代。确定性业务流程、高风险动作和状态转移更适合程序控制。

## 7.4 最终答案对就说明 Agent 好

不够。Agent 还要看过程是否安全、成本是否合理、是否越权、是否可复现。

# 8. 面试 Q&A

## Q1：Agent 和普通 LLM 应用有什么区别？

普通 LLM 应用通常是单轮或固定链路回答。Agent 具备目标、状态、工具和反馈循环，能根据中间结果持续决定下一步行动。

## Q2：为什么生产 Agent 不能只靠模型自由循环？

因为模型可能目标漂移、死循环、误用工具、越权执行或成本失控。生产系统需要状态机、权限、预算、审计和停止条件。

## Q3：ReAct 和 Plan-and-Execute 的区别是什么？

ReAct 是边思考边行动，根据每次观察继续决策；Plan-and-Execute 先生成整体计划，再按步骤执行。前者灵活，后者结构更清楚。

## Q4：Agent 的可靠性怎么提升？

明确目标和停止条件，设计好工具 schema 和权限，保存状态和 trace，对失败做恢复策略，并用任务级评估集持续测试。
