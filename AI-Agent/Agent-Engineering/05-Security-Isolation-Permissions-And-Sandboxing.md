# 安全隔离、权限与沙箱

Agent 的安全问题比普通聊天机器人更复杂，因为 Agent 不只是生成文本，还可能检索资料、调用 API、读写文件、执行代码、发送消息甚至修改业务数据。

安全设计的核心原则是：模型可以提出意图，但系统必须控制权限和执行。

---

# 1. Agent 的主要风险

常见风险包括：

- Prompt injection：外部文档或用户输入诱导模型忽略系统规则。
- 工具越权：模型调用了用户无权使用的工具或数据。
- 参数污染：模型生成了错误、恶意或越界参数。
- 数据泄露：模型把敏感信息暴露给无关用户或外部服务。
- 代码执行风险：生成代码访问文件系统、网络或密钥。
- 供应链风险：工具、插件、依赖或外部 API 不可信。
- 组合风险：多个看似低风险动作组合成高风险后果。

不要试图只靠 prompt 解决这些问题。Prompt 可以提醒模型，但不能替代系统级权限和隔离。

---

# 2. 指令层级与外部内容隔离

Agent 通常会接触多种文本：

- 系统指令：最高优先级，定义安全边界。
- 开发者指令：定义业务规则和工具使用方式。
- 用户输入：表达任务目标。
- 外部内容：网页、文档、邮件、数据库字段、工具结果。

外部内容最容易携带 prompt injection。系统应明确告诉模型哪些内容是不可信数据，不是指令。

工程上还要做隔离：

- 外部内容进入 prompt 前做标记，例如放入引用块或结构化字段。
- 检索结果不要直接覆盖系统规则。
- 工具结果不要自动触发高风险工具。
- 外部文本中的“忽略之前指令”只能被当作数据。

对于高风险任务，最好让模型输出结构化动作，再由系统根据策略判断是否执行。

---

# 3. 工具权限模型

工具权限至少要考虑四个维度：

```text
谁：用户、租户、角色、Agent 身份
能做什么：工具能力和操作类型
对什么资源：文件、订单、数据库记录、项目、环境
在什么条件下：任务类型、风险等级、审批状态、时间和预算
```

例如，同一个“查询订单”工具，用户只能查自己的订单，客服可以查授权范围内的订单，管理员可能需要额外审计。模型不应该自己决定这些权限。

工具权限要在 Tool Gateway 中校验。模型生成的工具参数只是请求，不是授权。

---

# 4. 参数校验和输出约束

工具调用必须有 schema，并且系统要做严格校验。

校验内容包括：

- 必填字段是否存在。
- 类型是否正确。
- 枚举值是否合法。
- 字符串长度和格式是否合规。
- 数值范围是否合理。
- 资源 ID 是否属于当前用户或租户。
- 操作是否需要审批。

模型输出格式错误时，可以让模型修复；但权限错误不能靠模型自我修复绕过。权限失败应该由系统拒绝，并记录审计。

结构化输出、JSON schema、Pydantic、OpenAPI 等工具能提高稳定性，但仍不能替代业务权限检查。

---

# 5. 沙箱隔离

代码执行、文件操作、浏览器自动化和插件运行都需要沙箱。

常见隔离方式：

- Docker：易用，适合一般容器隔离，但要注意权限配置。
- gVisor：在容器和内核之间增加用户态隔离层。
- Firecracker：轻量虚拟机，隔离更强，适合高风险多租户。
- WebAssembly：适合受限运行环境和插件沙箱。
- 语言级沙箱：适合简单表达式或受控脚本，但安全边界较弱。

沙箱要限制：

- 文件系统访问范围。
- 网络访问。
- CPU、内存和执行时间。
- 环境变量和密钥。
- 系统调用能力。
- 进程创建和后台任务。

不要把“容器里运行”自动等同于安全。容器配置、挂载目录、网络权限、用户权限都会影响风险。

---

# 6. 密钥与敏感数据

Agent 不应该直接看到长期密钥。

更安全的做法是：

- 密钥存储在专门的 secret manager。
- 工具服务代表 Agent 使用密钥，而不是把密钥注入 prompt。
- 每个工具使用最小权限 token。
- 日志和 trace 自动脱敏。
- 高风险数据按租户和权限过滤后再进入模型上下文。

如果模型上下文中出现密钥、身份证、订单隐私、内部系统 token，就有泄露风险。即使模型供应商可信，日志、调试、评估和下游工具也可能扩大暴露面。

---

# 7. 人工审批和审计

高风险动作需要 human-in-the-loop。

常见需要审批的动作：

- 转账、退款、下单、删除数据。
- 修改生产配置。
- 发送外部邮件或公开消息。
- 执行生成代码。
- 访问高敏感数据。
- 跨权限边界操作。

审批界面应该展示：用户目标、模型建议动作、工具参数、影响范围、风险解释、可回滚性和历史 trace。审批不是让人看一大段聊天记录，而是让人快速判断是否允许执行。

审计记录要包括谁批准、批准了什么、基于什么上下文、何时执行、执行结果如何。
