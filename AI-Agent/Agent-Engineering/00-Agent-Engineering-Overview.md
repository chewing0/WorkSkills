# Agent 工程化总览

很多 Agent demo 的结构很简单：用户输入、拼 prompt、调用模型、必要时调用工具、返回答案。这个结构足以验证想法，但离生产系统还很远。

生产环境里的 Agent 会面对真实用户、真实权限、真实成本和真实失败。模型可能输出格式错误，工具可能超时，用户可能输入恶意内容，外部 API 可能不稳定，长任务可能中断，模型升级可能让原来稳定的行为变化。Agent 工程化就是为这些不确定性建立边界和恢复机制。

---

# 1. Demo 和生产系统的差别

Demo 通常关注单次任务能否跑通。生产系统关注的是大量任务能否持续稳定运行。

| 维度 | Demo | 生产系统 |
|---|---|---|
| 输入 | 少量手工测试 | 大量真实用户、异常输入、攻击输入 |
| 状态 | 临时内存或聊天历史 | 可持久化、可恢复、可审计 |
| 工具 | 直接调用函数 | 权限校验、参数校验、幂等、审计 |
| 模型 | 单一模型 | 模型路由、降级、灰度、版本管理 |
| 失败 | 手动重试 | 自动重试、补偿、告警、人工介入 |
| 质量 | 看几个样例 | 评估集、线上监控、回归测试 |
| 成本 | 不敏感 | token 预算、缓存、限流、成本归因 |

所以工程化不是锦上添花，而是 Agent 能否进入真实业务的前提。

# 2. Agent 系统的基本分层

一个较完整的 Agent 系统通常至少有这些层：

```text
Client / API
  │
  ▼
Access Layer
  │  鉴权、限流、输入校验、租户识别
  ▼
Agent Runtime
  │  规划、工具选择、状态更新、停止条件
  ├────────► Model Gateway
  │          模型路由、推理调用、重试、流式输出
  ├────────► Tool Gateway
  │          权限、schema 校验、工具执行、沙箱
  ├────────► State Store
  │          会话、任务、checkpoint、长期记忆
  └────────► Queue / Worker
             异步任务、后台执行、补偿和通知
```

这个分层的目的不是把系统弄复杂，而是把风险隔离开。模型调用、工具执行、状态写入和外部副作用都应该有清楚边界。

在小项目中，这些层可以在同一个服务里；在大项目中，它们会拆成多个服务。关键不是物理拆分，而是逻辑职责清楚。

# 3. 工程化的核心问题

Agent 工程化可以归纳为六个问题。

第一，如何控制模型的不确定性？模型输出可能不稳定，因此需要 schema、解析器、重试、验证器、评估集和版本管理。

第二，如何控制工具的副作用？工具会读写文件、调用 API、修改数据，因此需要权限、审计、幂等、事务或补偿。

第三，如何管理状态？Agent 是多步过程，只保存最终答案不够。系统要知道任务进行到哪里、调用了什么工具、哪些结果已经确认、失败后从哪里恢复。

第四，如何保证安全？外部内容可能包含 prompt injection，用户可能越权请求，模型可能误调用危险工具。安全边界必须由系统实现，而不是只靠 prompt 约束。

第五，如何观测和评估？Agent 的错误通常发生在过程中，最终答案只是结果。没有 trace，就无法定位是检索错、规划错、工具错、状态错还是模型错。

第六，如何控制成本和延迟？Agent 通常多轮调用模型和工具，如果没有预算、缓存、路由、限流和降级，很容易成本失控或响应过慢。

# 4. Agent Runtime 的职责

Agent Runtime 可以理解为 Agent 的执行引擎。它不等于模型，也不等于框架。

它通常负责：

- 接收用户目标和当前上下文。
- 组织 prompt、模型调用和工具调用。
- 维护任务状态和中间结果。
- 判断下一步动作和停止条件。
- 处理工具失败、模型格式错误和重试。
- 写入 trace、日志、指标和 checkpoint。
- 在需要时请求人工确认或升级处理。

如果没有 Runtime，Agent 只是几次散落的模型调用。Runtime 的价值在于把这些调用变成可管理、可恢复、可观测的流程。

# 5. 工程化不是只选框架

很多团队会把“Agent 工程化”理解成“用了 LangChain、LangGraph 或某个低代码平台”。框架确实能减少编排成本，但不能自动解决所有生产问题。

框架通常能帮你做：

- 定义链路、节点、工具和状态。
- 记录一部分 trace。
- 组织回调、重试和持久化。
- 快速接入模型和工具生态。

但仍然需要你自己设计：

- 业务权限和租户隔离。
- 高风险工具的审批和审计。
- 线上评估和质量门禁。
- 成本预算和限流策略。
- 数据安全、密钥管理和合规要求。
- 灰度发布、回滚和灾备。

框架是骨架，不是运营体系。

# 6. 从小到大的落地路径

一个稳妥的落地路径通常是：

```text
单接口 demo
  -> 固定 workflow
  -> 加入结构化输出和工具校验
  -> 加入状态持久化和 trace
  -> 加入评估集和回归测试
  -> 加入队列、异步、重试和人工审批
  -> 加入成本控制、限流、灰度和告警
```

不要一开始就把系统做成复杂的分布式 Agent 平台。先把一个业务闭环跑稳，再把重复出现的问题抽象成平台能力。

工程化的好标准不是“架构图很漂亮”，而是当任务失败时，你能回答：

```text
失败发生在哪一步？
输入和状态是什么？
调用了哪个模型和工具？
是否越权？
能否安全重试？
是否影响其他用户？
是否需要人工处理？
如何避免下次再犯？
```
