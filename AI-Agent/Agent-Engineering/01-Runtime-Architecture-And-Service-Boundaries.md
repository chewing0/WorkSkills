# 运行时架构与服务边界

Agent 系统最容易一开始写成一个大函数：接收请求、查数据库、调用模型、执行工具、拼结果。短期很快，长期很难维护。随着工具数量、用户数量、任务长度和风险等级上升，必须把职责拆清楚。

服务边界不是为了微服务而微服务，而是为了让模型的不确定性、工具的副作用和业务系统的稳定性彼此隔离。

---

# 1. 推荐的逻辑架构

一个常见的逻辑架构如下：

```text
Client
  │
  ▼
API Gateway / Access Layer
  │
  ▼
Agent Runtime
  ├─► Model Gateway
  ├─► Tool Gateway
  ├─► State Store
  ├─► Memory / Knowledge
  ├─► Queue / Worker
  └─► Observability
```

这些模块可以部署在同一个进程，也可以拆成多个服务。早期项目可以单体实现，但代码层面仍应保持边界清楚。

清楚边界的好处是，当系统出问题时，你能判断是模型行为问题、工具执行问题、状态恢复问题、业务权限问题，还是部署容量问题。

---

# 2. 接入层

接入层负责处理进入 Agent 系统之前的确定性问题。

它通常包括：

- 用户鉴权和租户识别。
- 请求限流和配额检查。
- 输入大小限制和文件类型检查。
- 请求 ID、trace ID、会话 ID 生成。
- 基础安全过滤，例如明显恶意 payload。
- 同步、异步或流式响应模式选择。

接入层不应该承担复杂推理，也不应该直接执行工具。它的职责是把请求变成一个受控任务，并给后续链路打上可追踪的标识。

---

# 3. Agent Runtime

Agent Runtime 是系统核心，负责把用户目标推进成一系列可执行步骤。

它通常维护：

- 当前任务目标。
- 当前状态和上下文。
- 可用工具和权限。
- 模型调用策略。
- 下一步动作。
- 停止条件。
- 错误处理和重试策略。

Runtime 的关键是显式控制循环。不要让模型无限自由地“继续思考”。系统应控制最大轮次、最大工具调用次数、最大耗时和人工介入条件。

Runtime 还需要区分两种结果：模型建议的动作，以及系统实际执行的动作。模型可以提出“调用退款接口”，但系统必须先检查权限、参数、风险和审批状态，才能真正执行。

---

# 4. Model Gateway

Model Gateway 封装所有模型调用。

它解决的问题包括：

- 统一不同模型供应商或自托管模型的接口。
- 根据任务类型选择模型。
- 管理超时、重试、降级和熔断。
- 记录 token、延迟、错误和模型版本。
- 支持流式输出。
- 做 prompt 模板版本和参数管理。

有了 Model Gateway，业务代码不需要到处写具体模型调用细节。后续更换模型、灰度模型、增加小模型路由，也更容易。

需要注意，Model Gateway 不应该偷偷改变业务语义。比如自动截断上下文、替换模型、压缩 prompt 都可能影响结果，应该被记录在 trace 中。

---

# 5. Tool Gateway

Tool Gateway 是 Agent 工程化里非常重要的一层。它把模型的工具调用意图转成受控的外部操作。

它通常负责：

- 工具注册和 schema 管理。
- 参数校验和类型转换。
- 用户、租户、角色和任务权限检查。
- 敏感操作审批。
- 幂等键和重复调用防护。
- 超时、重试和错误分类。
- 工具结果摘要和审计记录。

不要让模型直接访问数据库、shell、内部 API 或密钥。模型应该只生成结构化工具请求，Tool Gateway 再决定是否执行。

这种设计能把“模型可能犯错”限制在请求层，把真正的副作用交给确定性系统控制。

---

# 6. State Store

State Store 保存 Agent 运行所需的状态。

常见状态包括：

- 会话状态：用户、会话、历史摘要、偏好。
- 任务状态：任务 ID、阶段、负责人、进度、失败原因。
- 工作流状态：当前节点、分支、等待条件。
- 工具状态：调用参数、结果、耗时、错误。
- Checkpoint：可恢复的执行快照。
- 审计日志：关键动作、权限判断、人工审批。

状态不应该只存在模型上下文里。上下文窗口是给模型看的，State Store 是给系统恢复、审计和协作看的。

对于长任务，状态持久化尤其重要。服务重启、网络中断或模型超时后，系统应该能知道任务进行到哪里，而不是从头再跑。

---

# 7. Queue / Worker

不是所有 Agent 任务都适合同步完成。

适合异步队列的任务包括：

- 长时间研究和报告生成。
- 大批量文件处理。
- 多工具、多步骤任务。
- 需要等待外部系统回调的任务。
- 失败后需要重试或补偿的任务。

队列的价值是削峰填谷、重试、隔离慢任务和保护在线服务。同步接口负责创建任务和返回任务 ID，后台 Worker 负责推进执行，用户通过轮询、WebSocket、SSE 或 Webhook 获取结果。

---

# 8. 服务边界的常见反模式

第一个反模式是业务系统直接暴露工具给模型。这样会让权限和审计非常难做。

第二个反模式是模型调用散落在各处。模型版本、参数、成本和错误无法统一管理。

第三个反模式是状态只保存在内存。服务重启、任务中断或多实例部署时会丢失上下文。

第四个反模式是所有任务都同步执行。长任务会拖垮接口，用户体验和系统容量都会变差。

第五个反模式是 trace 缺失。没有统一 trace ID，跨模型、工具、队列和数据库定位问题会非常痛苦。
