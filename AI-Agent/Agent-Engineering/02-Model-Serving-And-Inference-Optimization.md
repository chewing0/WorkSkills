# 模型服务与推理优化

Agent 的模型调用通常不是一次问答，而是多轮规划、工具选择、结果解释、反思和总结。因此模型服务的稳定性、成本和延迟会被 Agent 放大。

做 Agent 工程化时，不一定要自己训练或部署模型，但必须理解模型服务层对系统行为的影响。

---

# 1. API 模型与自托管模型

模型使用方式大致有两类：调用外部 API，或自托管开源/私有模型。

| 方式 | 优势 | 代价 |
|---|---|---|
| API 模型 | 接入快、能力强、免运维、弹性好 | 成本按量、数据合规限制、供应商依赖、可控性有限 |
| 自托管模型 | 数据可控、可深度优化、可私有化、可定制 | 需要 GPU/运维/容量规划，模型能力和推理优化要自己负责 |

很多团队会混合使用：复杂推理调用强模型 API，简单分类和格式化走小模型或自托管模型；敏感数据走私有模型，通用任务走外部模型。

关键不是选一种，而是通过 Model Gateway 把选择变成可配置、可观测、可回滚的策略。

---

# 2. 推理引擎解决什么

自托管模型时，推理引擎负责高效执行模型生成。

常见关注点包括：

- 如何管理 KV Cache。
- 如何把多个请求合并批处理。
- 如何支持流式输出。
- 如何减少显存占用。
- 如何支持量化模型。
- 如何提高吞吐和降低延迟。

常见推理引擎或工具包括 vLLM、TGI、TensorRT-LLM、SGLang、llama.cpp 等。不要只记名字，要理解它们解决的是推理服务的性能、部署和硬件适配问题。

Agent 场景对推理引擎有额外要求：请求长度差异大、上下文经常很长、工具调用会导致多轮短输出和长输入交替出现，普通聊天场景的容量估算不一定适用。

---

# 3. KV Cache 与长上下文成本

LLM 推理可以分成 prefill 和 decode。

prefill 阶段处理输入上下文，建立 KV Cache；decode 阶段逐 token 生成输出。长 prompt 会增加 prefill 成本，长输出会增加 decode 成本。

Agent 往往会把对话历史、工具结果、RAG 片段、任务状态都塞进上下文。如果不控制，上下文会越来越长，导致延迟和成本上升。

工程上常见策略包括：

- 对历史消息做摘要，而不是全量保留。
- 工具结果分层，只把必要摘要给模型。
- RAG 片段控制数量和长度。
- 将结构化状态保存在 State Store，需要时选择性注入。
- 对长任务使用 checkpoint，而不是每轮重放所有历史。

KV Cache 能优化推理，但不能替代上下文治理。上下文越乱，模型越容易被无关信息干扰。

# 4. Continuous Batching

在线服务中，请求会不断到达，每个请求长度不同。如果一个批次必须等所有请求都生成完再处理下一批，吞吐会很差。

Continuous batching 的思想是动态把新请求加入正在运行的批处理中，同时把已完成请求移出。这样可以提升 GPU 利用率。

对 Agent 来说，这很重要，因为 Agent 调用模型的模式非常碎片化：路由、工具参数生成、结果总结、审查都可能是短请求；而 RAG 总结和报告生成又可能是长请求。推理服务需要同时处理这些不同形态。

但 batching 也会带来排队延迟。吞吐和单请求延迟之间需要权衡。高并发后台任务可以更偏吞吐，交互式聊天更偏低延迟。

---

# 5. 量化与模型大小

量化通过降低权重或计算精度减少显存和计算成本。常见思路包括 8-bit、4-bit、GPTQ、AWQ 等。

量化的收益是更低显存、更低成本、更容易部署。代价是可能损失模型质量，尤其在复杂推理、工具参数生成、结构化输出和长上下文任务上需要评估。

不要只看通用 benchmark。Agent 场景应该用自己的任务集评估：

- 工具选择是否准确。
- JSON/schema 输出是否稳定。
- 长上下文是否保持一致。
- 事实引用是否更容易错。
- 多轮任务是否更容易偏离目标。

小模型加工具和 RAG 可以解决很多任务，但不能假设量化小模型在所有 Agent 任务上都足够。

---

# 6. 模型路由

模型路由是控制成本和质量的核心策略。

常见路由方式：

- 按任务类型：分类、摘要、检索改写用小模型，复杂推理用大模型。
- 按风险等级：高风险任务用更强模型或人工审批。
- 按上下文长度：长上下文任务使用支持长窗口的模型。
- 按用户等级或预算：不同租户使用不同模型策略。
- 按失败重试：小模型失败后升级到大模型。

模型路由不能只看成本，还要记录质量影响。每次路由决策都应进入 trace，包括候选模型、选择理由、输入长度、输出长度、延迟和错误。

---

# 7. 容量规划

模型服务容量规划需要看这些指标：

- QPS：每秒请求数。
- 输入 token 和输出 token 分布。
- 平均延迟和 P95/P99 延迟。
- 并发会话数。
- GPU 利用率和显存占用。
- 队列等待时间。
- 错误率、超时率、限流率。

Agent 系统还要关注“每个用户请求会触发多少次模型调用”。一个用户请求可能触发规划、检索改写、工具参数生成、结果总结、审查等多次调用。容量估算要按调用链，而不是按用户请求数。
