# 可观测性、评估与运营

Agent 的失败往往不是一个简单异常，而是一条链路逐步偏离：检索召回不准，模型基于错误证据规划，工具参数略有问题，重试后状态被覆盖，最后输出看似合理但实际错误。

所以 Agent 可观测性不能只看日志，也不能只看最终答案。需要把整个执行过程记录成可分析的 trace。

---

# 1. Trace 是核心

一个完整 trace 应该能回答：

```text
用户请求是什么？
系统选择了哪个任务流程？
调用了哪些模型？
每次模型输入输出是什么摘要？
调用了哪些工具？
工具参数和结果是什么？
状态如何变化？
哪里发生了重试、失败、审批或降级？
最终输出来自哪些证据？
成本和延迟是多少？
```

Trace 不等于把所有隐藏推理都原样保存。更推荐记录可审计的过程摘要、工具调用、状态变化、证据引用和模型输出。对于敏感数据，要做脱敏和访问控制。

Agent trace 的价值在于定位责任：是 prompt 问题、模型问题、检索问题、工具问题、状态问题，还是调度问题。

---

# 2. 日志、指标与事件

日志适合记录离散事件，指标适合看趋势，trace 适合串联一次请求。

常见日志：

- 任务创建、状态变化、结束。
- 工具调用开始、成功、失败。
- 权限拒绝和审批记录。
- 模型调用异常和解析失败。
- 系统降级和回滚事件。

常见指标：

- 请求量、任务量、并发数。
- 成功率、失败率、超时率。
- P50/P95/P99 延迟。
- 输入/输出 token。
- 单任务平均模型调用次数。
- 工具成功率和重试次数。
- 成本按用户、租户、任务类型归因。
- 人工审批命中率。

事件用于驱动运营和告警，例如某类任务失败率升高、某个工具连续超时、成本突然增长。

# 3. 评估集

Agent 评估需要自己的数据集。只看通用 benchmark 不够，因为业务 Agent 的失败往往和具体工具、流程、权限、知识库有关。

一个好的评估集应该包含：

- 常见正常请求。
- 边界情况。
- 历史线上失败案例。
- 恶意或注入样例。
- 工具失败场景。
- 权限不足场景。
- 长上下文和多轮任务。
- 需要拒答或人工介入的任务。

每个样例不一定只有一个标准答案。对于 Agent，更重要的是评价标准：是否使用正确工具、是否引用证据、是否越权、是否按流程审批、是否在预算内完成。

---

# 4. 离线评估与在线监控

离线评估用于发布前回归。每次改 prompt、模型、工具 schema、路由策略、RAG 索引或 Agent 流程，都应该跑关键评估集。

在线监控用于发现真实流量中的问题。它关注：

- 质量趋势是否下降。
- 失败率是否上升。
- 用户是否频繁追问或纠错。
- 工具调用是否异常。
- 成本是否突然增长。
- 特定租户或任务类型是否异常。

离线评估和在线监控要结合。离线评估覆盖可预期问题，线上监控发现新分布和未知失败。

---

# 5. LLM-as-a-Judge 的使用边界

用模型做评审很有用，尤其适合开放文本质量、摘要完整性、回答风格和初步事实一致性判断。

但它有边界：

- Judge 也会幻觉。
- Judge 可能偏好更长或更自信的答案。
- Judge 对专业事实不一定可靠。
- Judge 不能替代权限和安全规则。
- Judge 结果需要抽样人工校准。

更稳的方式是混合评估：

- 确定性规则检查格式、权限和 schema。
- 工具或测试检查代码、SQL、计算结果。
- RAG 证据检查引用是否支持结论。
- LLM Judge 评估语言质量和复杂语义。
- 人工抽检校准关键指标。

# 6. 版本管理

Agent 行为由很多版本共同决定：

- 代码版本。
- Prompt 版本。
- 模型版本。
- 工具 schema 版本。
- RAG 索引版本。
- 路由策略版本。
- 评估规则版本。

一次线上变化可能不是代码导致，而是模型供应商更新、检索索引重建、prompt 调整或工具返回格式变化。

因此 trace 中要记录这些版本。否则出现质量回退时，很难定位原因。

版本管理还支持 A/B 测试和灰度发布。不同版本的质量、成本和延迟必须能对比。

---

# 7. 运营闭环

Agent 上线后，运营闭环大致是：

```text
收集 trace 和用户反馈
  -> 聚类失败案例
  -> 判断失败类型
  -> 修复 prompt / 工具 / 流程 / 知识库
  -> 更新评估集
  -> 离线回归
  -> 灰度上线
  -> 继续监控
```

最有价值的评估集往往来自线上失败。每修一个问题，都应该把它沉淀成回归样例，否则同类问题会反复出现。
