> **核心考点**：Fine-tuning 是用训练数据继续优化模型参数或附加参数，让模型在目标任务分布上更倾向产生期望行为。它不是万能知识注入器，也不是替代 Prompt、RAG、工具和评估的银弹。

---

# 1. 核心问题：微调到底在改变什么

LLM 推理时根据上下文预测下一个 token。微调通过继续训练改变模型的参数或少量附加参数，使某些输入下的目标输出概率更高。

直观理解：

```text
微调前：
用户问业务问题 -> 模型按通用助手风格回答

微调后：
用户问业务问题 -> 模型更倾向按你的格式、术语、流程和边界回答
```

它改变的是模型的行为分布：

- 更熟悉某类任务格式。
- 更稳定遵守某种输出结构。
- 更像某个领域或产品的助手。
- 更会调用某类工具或生成某类参数。
- 更符合某种偏好和拒答边界。

但微调不是让模型拥有一个可更新、可溯源的数据库。如果目标是回答最新政策、私有文档、实时库存，RAG 或工具通常更合适。

---

# 2. 什么时候该微调

适合微调的情况：

## 2.1 任务行为长期稳定

例如：

- 固定格式的信息抽取。
- 固定风格的客服回复。
- 某类代码生成规范。
- 特定领域问答表达。
- 多轮对话流程风格。

如果任务规则频繁变化，Prompt 或工具配置可能更灵活。

## 2.2 Prompt 很长且仍不稳定

当你需要在 prompt 里反复写大量格式、术语、风格规则，而模型仍不稳定，微调可以把这些模式内化一部分，减少 prompt 长度和输出波动。

## 2.3 有足够高质量样本

微调不是拿一堆日志直接喂进去。你需要清洗、标注、覆盖边界和失败模式的数据。

数据不够好时，微调会稳定地学坏。

## 2.4 需要降低推理成本

如果通过很长的 system prompt 和 few-shot 示例才能稳定完成任务，微调后可以减少上下文 token，降低延迟和成本。

---

# 3. 什么时候不该微调

不适合优先微调的情况：

| 目标 | 更适合的方案 | 原因 |
|---|---|---|
| 使用最新文档回答 | RAG | 知识会更新，需要可引用 |
| 查询实时状态 | 工具/API | 需要外部系统真实数据 |
| 简单格式控制 | Prompt/schema | 微调成本过高 |
| 少量规则变化 | Prompt/配置 | 微调不够灵活 |
| 权限控制 | 系统权限 | 不能交给模型参数 |
| 精确计算 | 程序工具 | 模型不适合做可靠计算 |

一句话：

> 如果问题本质是“缺证据”，先做 RAG；如果问题本质是“缺外部动作”，先做工具；如果问题本质是“行为长期不稳定”，再考虑微调。

# 4. 微调的主要类型

## 4.1 Continued Pretraining

也叫继续预训练或领域继续训练。用大量领域语料继续做语言建模。

适合：

- 领域术语很多。
- 模型对领域文本分布不熟。
- 有大量无标注语料。

风险：

- 成本高。
- 容易遗忘通用能力。
- 不直接教模型听指令。

## 4.2 SFT

Supervised Fine-Tuning，用输入输出样本训练模型按指令回答。

适合：

- 学习任务格式。
- 学习领域回答方式。
- 学习工具参数输出。
- 学习多轮对话模式。

SFT 是多数应用微调的起点。

## 4.3 PEFT

Parameter-Efficient Fine-Tuning，只训练少量参数，例如 LoRA、QLoRA、Adapter、Prefix Tuning。

适合：

- 显存有限。
- 需要多任务多 adapter。
- 希望降低训练和存储成本。

## 4.4 Preference Alignment

偏好对齐使用“哪个回答更好”的数据，让模型更符合人类偏好、安全边界和产品风格。

常见方法：

- RLHF。
- DPO。
- KTO。
- ORPO。

它通常在 SFT 之后进行。

# 5. 微调完整流程

```text
目标定义
  │
  ├─► 选择基座模型
  ├─► 设计数据格式
  ├─► 清洗和标注数据
  ├─► 划分 train/valid/test
  ├─► 选择训练方式：full / LoRA / QLoRA
  ├─► 训练和监控 loss
  ├─► 离线评估：能力、格式、安全、回归
  ├─► 小流量上线
  ├─► 线上监控和人工抽检
  └─► 收集失败样本继续迭代
```

其中最容易被低估的是：

- 数据构造。
- 验证集设计。
- 回归评估。
- 上线监控。

训练跑通只是中间一小步。

# 6. 微调和 RAG、Prompt 的组合

真实系统常常组合使用：

```text
Prompt：定义当前任务和输出契约
RAG：提供外部证据和引用来源
Fine-tuning：让模型更稳定遵守领域格式和行为模式
Tool：查询实时状态或执行动作
Validator：校验输出和权限
```

例子：

企业客服系统：

- RAG 负责检索政策条款。
- Tool 负责查订单和退款状态。
- Prompt 负责组织当前任务和证据。
- Fine-tuning 负责让模型稳定使用客服口吻、拒答边界和工具参数格式。

不要让微调承担所有责任。它应该是系统的一层。

# 7. 常见失败模式

## 7.1 数据污染和低质量样本

模型会学习数据里的错误、啰嗦、幻觉和不一致格式。

## 7.2 过拟合

训练集表现很好，真实问题变差。尤其是数据量小、epoch 太多、学习率过高时。

## 7.3 灾难性遗忘

模型在目标任务上变好，但通用能力、安全能力或多语言能力下降。

## 7.4 格式学会了，事实没变好

SFT 可以让模型更会写某种格式，但不保证事实正确。事实仍需要 RAG、工具和评估。

## 7.5 评估不完整

只看 loss 或少量 demo，容易忽略安全回归、边界失败和成本变化。

# 8. 常见误区

## 8.1 微调就是给模型灌知识

不准确。微调可以让模型更熟悉某些领域模式，但不适合做频繁更新、精确可溯源的知识库。

## 8.2 loss 越低模型越好

不一定。loss 低可能是过拟合或学习了训练集风格。应用质量要看任务评估、格式稳定、事实性、安全和线上反馈。

## 8.3 LoRA 一定不如全量微调

不一定。很多指令和风格任务上 LoRA 足够好，成本低、风险小、易管理。全量微调更强但更贵也更容易破坏原能力。

## 8.4 数据越多越好

不一定。高质量、覆盖边界、格式一致的数据比大量低质量数据更重要。

# 9. 面试 Q&A

## Q1：Fine-tuning、Prompt 和 RAG 如何取舍？

Prompt 适合快速约束本次任务，RAG 适合补充外部知识和引用，Fine-tuning 适合长期稳定改变模型行为、格式和风格。如果问题是缺知识，优先 RAG；如果是缺行为稳定性，再考虑微调。

## Q2：微调的最大风险是什么？

常见风险包括数据质量差、过拟合、灾难性遗忘、安全能力退化和评估不充分。微调会把数据中的模式固化进模型行为，因此数据和评估比训练代码更关键。

## Q3：为什么微调不能替代权限控制？

权限是系统级约束。模型参数不能可靠判断实时权限，也不能防止敏感信息泄露。未授权数据不应进入训练集或推理上下文。

## Q4：应用微调最常见的起点是什么？

通常是 SFT 或 LoRA SFT。先用高质量指令数据让模型稳定完成目标任务，再根据需要做偏好对齐或进一步优化。
