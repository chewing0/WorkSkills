> **核心考点**：微调首先是数据工程问题。训练代码只能把数据中的模式放大；如果数据目标不清、格式混乱、边界缺失，模型会稳定地学到错误行为。

---

# 1. 核心问题：数据决定模型学什么

SFT 数据通常长这样：

```text
输入：用户问题、上下文、系统规则
输出：期望模型回答
```

模型不是理解“你想要什么”，而是在训练中提高目标输出 token 的概率。样本里出现什么模式，模型就更倾向学什么模式。

因此数据设计要先回答：

1. 目标任务是什么？
2. 期望输出长什么样？
3. 哪些输入应该拒答？
4. 哪些边界最容易错？
5. 哪些格式必须稳定？
6. 哪些能力不能被破坏？

没有这些定义，数据越多越乱。

---

# 2. 高质量数据的特征

好数据通常具备：

| 特征 | 含义 |
|---|---|
| 目标清楚 | 每条样本都服务于明确行为 |
| 输入真实 | 覆盖用户真实问法和噪声 |
| 输出一致 | 风格、格式、字段、拒答方式统一 |
| 边界充分 | 包含缺失信息、冲突、越权、反例 |
| 难度分布合理 | 不只放简单样本 |
| 无敏感泄露 | 不包含密钥、隐私、越权数据 |
| 可评估 | 能判断模型输出是否合格 |

低质量数据的典型问题：

- 输出啰嗦。
- 答案互相矛盾。
- 不知道时强行回答。
- JSON 字段时有时无。
- 用户语气不真实。
- 混入旧规则和错误标签。
- 包含训练不该记住的隐私数据。

# 3. 指令数据格式

常见格式有两类。

## 3.1 单轮 instruction

```json
{
  "instruction": "把用户反馈分类为 positive、neutral 或 negative",
  "input": "界面不错，就是偶尔会卡。",
  "output": "neutral"
}
```

适合分类、抽取、改写、总结等简单任务。

## 3.2 Chat messages

```json
{
  "messages": [
    {"role": "system", "content": "你是客服助手。"},
    {"role": "user", "content": "我想退货。"},
    {"role": "assistant", "content": "请提供订单号，我会帮你查询退货条件。"}
  ]
}
```

适合对话模型、多轮状态、工具调用风格和安全规则。

训练时要使用目标模型对应的 chat template。不同模型对 system、user、assistant、special token 的格式可能不同。格式错了，模型会学到错误边界。

# 4. Loss Mask：哪些 token 应该参与训练

在聊天 SFT 中，通常只对 assistant 输出计算 loss，不对 system 和 user 内容计算 loss。

直观原因：

```text
system/user：条件
assistant：模型要学习生成的目标
```

如果把用户输入也当目标训练，模型可能学习复述用户，而不是回答用户。

典型训练样本：

```text
<system>你是客服助手</system>
<user>退款多久到账？</user>
<assistant>退款通常在 3-5 个工作日到账...</assistant>
```

loss mask 应只覆盖 assistant 部分。

工具调用、多轮对话也要明确哪些 assistant 消息参与训练，哪些工具结果只是上下文。

---

# 5. 数据覆盖：不要只放正例

很多微调失败来自训练集全是“理想输入 -> 理想输出”。

真实用户会：

- 问不完整问题。
- 使用错别字。
- 混合多个需求。
- 请求越权操作。
- 提供矛盾信息。
- 要求模型忽略规则。
- 追问上一轮内容。

训练集应包含：

| 样本类型 | 作用 |
|---|---|
| 标准正例 | 学习正常任务 |
| 边界样本 | 学习区分相似类别 |
| 缺失信息 | 学习澄清或输出 null |
| 拒答样本 | 学习安全边界 |
| 反例 | 学习什么不能做 |
| 多轮样本 | 学习上下文状态 |
| 格式样本 | 学习稳定 schema |

微调是让模型更稳定地走你给过的路径。没给过边界，就不要指望它自动稳。

# 6. 数据划分与泄漏

至少划分：

```text
train：训练
validation：调参和早停
test：最终评估
```

注意数据泄漏：

- 同一个问题的改写同时出现在 train 和 test。
- 同一篇文档切出的相似样本跨集合。
- 合成数据模板过于重复。
- 测试集来自训练集清洗后的残留。

如果 test 被污染，评估会虚高。

对于业务微调，建议额外保留：

- 历史失败集。
- 安全回归集。
- 格式稳定集。
- 通用能力回归集。

# 7. 合成数据：有用但危险

LLM 可以帮助生成训练样本：

- 扩写用户问法。
- 生成边界样本。
- 改写风格。
- 生成负例。
- 标注初稿。

但合成数据有风险：

- 模型编造业务规则。
- 样本风格过于统一。
- 难度分布不真实。
- 把 teacher model 的偏见传给 student。
- 大量模板化数据导致模型输出模板化。

合成数据最好经过：

```text
规则校验 -> 人工抽检 -> 去重 -> 分布检查 -> 小规模训练验证
```

不要把未审核的合成数据直接作为高风险业务训练集。

# 8. 数据清洗和去重

清洗包括：

- 删除乱码。
- 删除重复样本。
- 统一字段。
- 修复格式错误。
- 去除敏感信息。
- 检查标签一致性。
- 删除低质量输出。

去重很重要。重复样本会让模型过度记住某些表达，影响泛化，也会污染验证集。

近重复也要注意：

```text
退款多久到账？
退款什么时候到账？
退款大概几天到？
```

这些可以作为问法扩展，但不应无控制地跨 train/test。

# 9. 安全与隐私

训练数据不应包含：

- 密钥、token、密码。
- 用户身份证、手机号、地址等隐私。
- 未授权内部资料。
- 不能被模型复述的敏感内容。
- 已废弃或错误政策。

微调后的模型可能记忆训练样本中的敏感片段，尤其是重复出现的小数据集内容。

安全数据也要包含：

- 拒绝危险请求。
- 拒绝越权请求。
- 隐私保护示例。
- 不确定时转人工或澄清。

安全不是只在上线时过滤，训练数据里也要体现边界。

# 10. 常见误区

## 10.1 日志可以直接拿来训练

不建议。日志包含错误回答、用户隐私、重复噪声和未审核内容。需要清洗、脱敏、标注和筛选。

## 10.2 数据量越大越好

不一定。几千条高质量、覆盖边界的数据，可能比几十万条噪声日志更有价值。

## 10.3 格式不重要，模型会理解

格式非常重要。chat template、role token、assistant mask、JSON 字段都会影响模型学到的行为。

## 10.4 只训练正例就够

不够。没有拒答、缺失信息、冲突和越权样本，模型会倾向在所有情况下都给答案。

# 11. 面试 Q&A

## Q1：为什么说微调主要是数据问题？

因为训练会放大数据中的行为模式。数据目标不清、格式混乱、边界缺失时，模型会稳定学到错误输出。训练技巧无法弥补根本的数据质量问题。

## Q2：SFT 数据为什么通常只对 assistant 部分算 loss？

system 和 user 是条件，assistant 是模型要学习生成的目标。如果对用户部分也算 loss，模型可能学习复述输入，而不是根据输入生成回答。

## Q3：合成数据能不能用于微调？

可以，但需要校验、去重、人工抽检和分布检查。合成数据适合扩展问法和边界样本，但不能未经审核地用于高风险业务。

## Q4：训练集、验证集、测试集怎么防泄漏？

要按问题簇、文档来源或用户会话级别划分，避免同一问题改写或同一文档切片同时出现在 train 和 test 中。
