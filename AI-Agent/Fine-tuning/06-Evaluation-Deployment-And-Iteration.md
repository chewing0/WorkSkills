> **核心考点**：微调是否成功不能只看训练 loss。真正要回答的是：目标任务是否变好，原有能力是否退化，安全边界是否保持，线上成本和稳定性是否可接受。

---

# 1. 核心问题：如何证明微调真的变好了

微调后至少要比较：

```text
base model / old model
  vs
fine-tuned model
```

看四类变化：

1. 目标任务是否提升。
2. 格式和流程是否更稳定。
3. 通用能力和安全能力是否退化。
4. 成本、延迟、部署复杂度是否可接受。

如果只看几个 demo，容易被幸存样本骗。

---

# 2. 离线评估集设计

评估集应包含：

| 类型 | 作用 |
|---|---|
| 目标任务样本 | 看核心任务是否提升 |
| 边界样本 | 看容易混淆处是否改善 |
| 格式样本 | 看 JSON/schema/工具调用稳定性 |
| 拒答样本 | 看安全和不确定性处理 |
| 历史失败样本 | 看是否修复真实问题 |
| 通用能力样本 | 看是否灾难性遗忘 |
| 安全回归样本 | 看是否越权、泄露、危险回答 |

每次微调都要跑同一批评估集，才能比较版本。

---

# 3. 指标不能只看 loss

训练指标：

- train loss。
- validation loss。
- learning curve。

任务指标：

- 分类准确率。
- 字段 F1。
- JSON 合法率。
- schema 通过率。
- 工具参数准确率。
- 拒答准确率。
- 人工评分。
- LLM-as-a-Judge rubric。

回归指标：

- 通用 benchmark 子集。
- 安全测试。
- 多语言能力。
- 代码能力。
- RAG 忠实性。
- 格式稳定性。

loss 只说明模型拟合验证文本的程度，不直接等于业务质量。

# 4. A/B 和人工评审

开放生成任务很难自动打分。可以用：

- Pairwise 比较。
- Rubric 打分。
- 人工专家审核。
- LLM judge 初筛。
- 用户反馈。

Pairwise 示例：

```text
同一个 prompt：
回答 A：旧模型
回答 B：新模型
标注：哪个更好，为什么
```

优点是比绝对打分更稳定。

注意：

- 盲评，避免知道模型版本。
- 记录偏好原因。
- 关注事实、格式、安全，不只看流畅度。

---

# 5. 安全和回归评估

微调可能让模型：

- 过度服从用户。
- 拒答能力下降。
- 泄露训练样本。
- 对危险请求更配合。
- 忘记原本的安全边界。

所以需要安全回归：

- prompt injection。
- jailbreak。
- 隐私请求。
- 越权操作。
- 医疗/法律/金融高风险建议。
- 自残、暴力、违法内容。

业务模型也要测：

- 错误政策是否被复述。
- 是否编造工具结果。
- 是否无权限回答。
- 是否在资料不足时拒答。

# 6. 部署方式

## 6.1 全量模型部署

全量微调后部署完整权重。

优点：

- 推理简单。
- 不需要 adapter 逻辑。

缺点：

- 存储大。
- 多版本成本高。
- 回滚和对比成本高。

## 6.2 Base + Adapter 部署

LoRA/Adapter 常用：

```text
base model + adapter
```

优点：

- 多任务 adapter 易管理。
- 存储小。
- 可按租户或业务切换。

缺点：

- 推理框架要支持 adapter。
- 多 adapter 并发和路由更复杂。

## 6.3 Merge 后部署

把 LoRA merge 到基座。

优点：

- 推理链路简单。

缺点：

- 不方便动态切换。
- 需要重新生成完整权重。

---

# 7. 上线策略

不要直接全量替换。

推荐：

```text
离线评估通过
  │
  ├─► shadow 流量：只记录不返回
  ├─► 小流量灰度
  ├─► A/B 对比
  ├─► 人工抽检
  └─► 扩大流量
```

同时准备：

- 回滚方案。
- 模型版本记录。
- adapter 版本记录。
- prompt 和工具 schema 版本。
- 监控指标。
- 人工兜底流程。

---

# 8. 线上监控

监控：

| 类别 | 指标 |
|---|---|
| 质量 | 用户满意度、差评率、人工质检 |
| 格式 | JSON 失败率、schema 失败率 |
| 工具 | 工具选择准确率、参数错误率 |
| 安全 | 拒答率、违规率、敏感泄露 |
| 性能 | 延迟、吞吐、超时率 |
| 成本 | token、GPU、adapter 存储 |
| 漂移 | 新问题类型、失败样本变化 |

线上坏例子要进入下一轮数据闭环：

```text
线上失败 -> 标注原因 -> 加入评估集 -> 修数据或训练 -> 回归测试
```

---

# 9. 版本管理

必须记录：

- base model。
- tokenizer。
- chat template。
- training data version。
- training config。
- adapter/full checkpoint。
- prompt version。
- evaluation set version。
- metrics。
- deployment config。

否则无法回答：

```text
这次变好是因为数据、模型、prompt、参数还是工具 schema？
```

模型迭代要像代码迭代一样可追踪、可比较、可回滚。

# 10. 常见误区

## 10.1 训练 loss 降了就能上线

不够。要看任务指标、格式、安全、通用能力回归和线上灰度表现。

## 10.2 新模型目标任务更好就一定值得

如果安全退化、延迟上升、成本过高或通用能力下降，可能不值得上线。

## 10.3 线上失败只改 prompt 就行

不一定。失败可能来自数据缺口、训练偏差、工具问题、RAG 问题或安全边界。要先分类原因。

## 10.4 微调后不需要继续收集数据

需要。上线后的真实失败样本是下一轮迭代最有价值的数据。

# 11. 面试 Q&A

## Q1：如何评估微调模型是否成功？

比较新旧模型在目标任务、格式稳定、安全、通用能力回归、成本和延迟上的表现。不能只看训练 loss 或少量 demo。

## Q2：为什么要做回归评估？

微调可能提升目标任务，同时破坏原有能力或安全边界。回归评估用于发现灾难性遗忘和安全退化。

## Q3：LoRA 模型部署有哪些方式？

可以 base + adapter 动态加载，也可以 merge 到基座权重部署。前者灵活，后者推理链路简单。

## Q4：线上失败样本如何利用？

先分类失败原因，再补充到评估集和训练数据中。下一次训练后必须回归验证，防止修好一个问题又引入新问题。
