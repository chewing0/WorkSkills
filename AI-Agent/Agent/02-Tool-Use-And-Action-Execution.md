# 工具使用与行动执行

工具是 Agent 从“会说”变成“会做”的关键。检索、数据库查询、API 调用、代码执行、文件操作、消息发送，这些都属于工具或行动。

但工具也是 Agent 最大的风险入口。模型可以生成调用意图，但真正执行必须由系统接管。

---

# 1. Function Calling 解决什么

Function Calling 的作用是让模型输出结构化工具调用，而不是在自然语言里说“我想查一下订单”。

一个工具调用通常包含：

```text
tool_name
arguments
```

这让系统可以解析、校验和执行，也能记录 trace。

但 Function Calling 不等于工具安全。它只是把模型意图结构化，不能保证工具选得对、参数合法、权限允许、动作安全。

---

# 2. 工具 schema 怎么设计

好的工具 schema 应该清晰、收窄、可校验。

不要给模型一个过宽的工具，例如：

```text
run_any_command(command: string)
```

更好的方式是给具体能力：

```text
search_docs(query, filters)
get_order(order_id)
create_refund_request(order_id, reason)
run_unit_tests(test_path)
```

工具越具体，模型越容易选对，系统越容易校验，风险也越低。

schema 应包含参数类型、枚举、范围、必填项、说明和示例。对于业务资源 ID，系统还要校验是否属于当前用户或租户。

---

# 3. Tool Gateway

生产系统中，工具调用最好通过 Tool Gateway。

Tool Gateway 负责：

- 工具注册。
- schema 校验。
- 参数规范化。
- 权限检查。
- 风险分级。
- 审批判断。
- 幂等控制。
- 超时、重试和错误分类。
- 工具结果摘要。
- 审计记录。

模型不应该直接拿到数据库连接、shell 权限、内部 API token 或长期密钥。它只能发起工具请求，Tool Gateway 决定是否执行。

---

# 4. 参数校验

参数错误非常常见。模型可能生成不存在的字段、格式错误的日期、越界金额、错误资源 ID。

校验至少包括：

- 类型是否正确。
- 必填参数是否存在。
- 枚举值是否合法。
- 字符串长度和格式是否合规。
- 数值范围是否合理。
- 资源是否属于当前权限范围。
- 动作是否需要审批。

格式错误可以让模型修正；权限错误应直接拒绝，不能让模型通过改写参数绕过。

---

# 5. 工具结果如何返回给模型

工具结果不应该总是原样塞回上下文。

如果结果很短，可以直接返回。如果结果很长，应该分层处理：

- 原始结果完整存入日志或对象存储。
- 提取关键摘要给模型。
- 把关键事实写入状态。
- 把错误码和失败原因结构化。

例如测试日志很长时，修复 Agent 需要失败用例和错误堆栈；协调 Agent 只需要知道测试是否通过和是否阻塞。

---

# 6. 幂等和副作用

读工具通常可以安全重试，写工具必须谨慎。

高风险写动作包括：

- 退款。
- 下单。
- 删除数据。
- 修改配置。
- 发送邮件。
- 部署代码。
- 写生产数据库。

这类动作要有幂等键、执行记录和审批。重试前先检查动作是否已经成功，避免重复执行。

Agent 工程里最危险的不是模型答错，而是模型在错误状态下真的做了外部动作。

---

# 7. 代码执行与沙箱

代码执行工具很强，也很危险。

沙箱需要限制：

- 文件系统访问。
- 网络访问。
- CPU、内存和执行时间。
- 环境变量和密钥。
- 进程创建。
- 系统调用。

常见隔离方式包括 Docker、gVisor、Firecracker、WebAssembly 和受限解释器。隔离强度要和风险匹配。

代码执行工具还要保存输入、输出、错误、退出码和资源消耗，方便复盘。

---

# 8. 错误恢复

工具失败要分类处理：

- 参数错误：让模型修正参数。
- 权限错误：拒绝或请求授权。
- 超时：可重试或降级。
- 外部服务失败：等待、重试、熔断。
- 业务规则失败：说明原因，不要强行绕过。
- 不可恢复失败：停止任务并返回可解释状态。

错误信息要给模型足够上下文，但不要暴露敏感内部细节。
