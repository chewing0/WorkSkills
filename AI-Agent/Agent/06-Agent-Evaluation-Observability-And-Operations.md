# 评估、可观测性与运营

Agent 评估不能只看最终答案。一个 Agent 最终回答看起来正确，过程可能越权、重复调用工具、引用错误证据、成本爆炸，或者只是偶然成功。生产 Agent 必须评估过程。

可观测性是 Agent 运营的基础。没有 trace，就没有调试；没有评估集，就不知道改动是变好还是变差。

---

# 1. Agent 评估对象

Agent 评估至少分五层：

- 目标完成：是否解决用户问题。
- 规划质量：任务拆解和下一步选择是否合理。
- 工具行为：工具是否选对、参数是否正确、结果是否被正确使用。
- 状态控制：是否重复、遗漏、循环、越界。
- 生产指标：成本、延迟、错误率、安全和人工介入。

最终答案只是其中一层。

---

# 2. 任务成功率

任务成功率要按业务定义。

客服 Agent 的成功可能是解决工单；代码 Agent 的成功可能是测试通过；RAG Agent 的成功可能是回答正确且引用支持结论；办公 Agent 的成功可能是生成并保存正确文件。

不要只用“用户点赞”或“LLM Judge 分数”作为唯一指标。它们有用，但容易偏。

---

# 3. 过程指标

过程指标能帮助定位失败。

常见过程指标：

- 平均规划轮次。
- 工具调用成功率。
- 工具参数错误率。
- 重试次数。
- 循环检测命中。
- 人工审批命中。
- 拒答率。
- 任务中断率。
- token 成本。
- P95/P99 延迟。

这些指标能告诉你 Agent 是“不聪明”，还是“工具不稳”，或者“流程设计太复杂”。

---

# 4. Trace 记录什么

Agent trace 应包含：

```text
用户目标
任务状态
模型调用
Prompt 版本
模型版本
工具调用
工具参数
工具结果
状态变化
重试和错误
人工审批
最终输出
成本和延迟
```

Trace 不一定要暴露模型完整隐藏推理，但要记录可审计的决策摘要、工具行为和状态变化。

对于敏感数据，要做脱敏和权限控制。

---

# 5. 评估集

Agent 评估集应来自真实业务。

建议包含：

- 常见成功任务。
- 历史失败案例。
- 边界输入。
- 权限不足场景。
- 工具失败场景。
- Prompt injection 样例。
- 长上下文任务。
- 需要拒答或人工确认的任务。

每次线上失败都应该沉淀进评估集。否则同类问题会反复出现。

---

# 6. LLM-as-a-Judge

LLM Judge 可以评估开放文本质量、任务完成度、引用是否相关、回答是否清晰。

但它不能替代：

- 权限规则。
- 工具执行结果。
- 单元测试。
- 事实证据。
- 人工抽检。

更稳的做法是混合评估：规则检查格式和权限，工具检查事实和执行，LLM Judge 看语义质量，人工校准关键样本。

---

# 7. 线上运营闭环

Agent 上线后的迭代循环是：

```text
收集 trace 和反馈
  -> 聚类失败模式
  -> 定位失败环节
  -> 修复 prompt / 工具 / 状态 / 流程 / 知识库
  -> 更新评估集
  -> 离线回归
  -> 灰度上线
  -> 继续监控
```

运营的关键不是不断加 prompt，而是把失败模式分类后用合适层解决：检索问题改 RAG，工具问题改 schema 和权限，状态问题改 workflow，模型问题再考虑 prompt 或模型。

---

# 8. 成本和可靠性

Agent 常常多轮调用模型和工具，所以成本和延迟会被放大。

治理方式：

- 最大 token 和轮次预算。
- 模型路由。
- 工具超时。
- 缓存。
- 异步任务。
- 降级策略。
- 熔断。
- 人工介入。

可靠 Agent 不是永不失败，而是失败时可解释、可恢复、可降级。
