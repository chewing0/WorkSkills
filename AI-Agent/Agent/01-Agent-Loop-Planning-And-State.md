# Agent 循环、规划与状态

Agent 的核心不是“想得多”，而是能把一个目标推进成一系列可执行步骤，并根据反馈调整方向。这里最重要的是三件事：规划要落到行动，行动要更新状态，循环要知道何时停止。

没有状态的 Agent 只是多轮聊天；没有停止条件的 Agent 很容易变成无限循环。

---

# 1. 从目标到下一步

用户经常给的是目标，而不是步骤。例如：

```text
帮我分析这个报表异常，并给出可能原因。
修复这个测试失败。
根据这些资料写一份调研报告。
```

Agent 需要把目标转成下一步可执行动作：

```text
目标
  -> 当前已知信息
  -> 缺失信息
  -> 可用工具
  -> 下一步动作
  -> 期望结果
```

好的规划不是生成一长串漂亮计划，而是让下一步明确、可执行、可验证。

---

# 2. ReAct：边想边做

ReAct 的核心是把 reasoning 和 acting 交替起来：

```text
观察 -> 思考 -> 行动 -> 观察工具结果 -> 再思考 -> 再行动
```

它适合信息逐步展开的任务，例如搜索、问答、排查、轻量工具调用。ReAct 的好处是灵活：模型不需要一开始就规划所有步骤，可以根据工具结果动态调整。

它的问题也明显：如果没有系统控制，模型可能反复调用工具、陷入循环、过度搜索，或者把工具结果误读成结论。

工程上使用 ReAct 时，应设置最大轮次、工具白名单、参数校验、失败处理和停止条件。

---

# 3. Plan-and-Execute：先拆再做

Plan-and-Execute 先生成计划，再逐步执行。

```text
目标
  -> 任务拆解
  -> 执行第 1 步
  -> 执行第 2 步
  -> 汇总结果
```

它适合结构较清晰的复杂任务，例如写报告、代码修改、数据分析、多文档总结。相比 ReAct，它更容易观察进度，也更容易插入人工确认。

但计划不是越长越好。太细会增加管理成本，太粗又无法执行。一个好计划应该包含：

- 子任务目标。
- 输入和输出。
- 依赖关系。
- 完成标准。
- 失败时如何处理。

---

# 4. 重规划

真实任务很少按原计划顺利完成。工具可能失败，检索可能找不到资料，用户可能补充新要求，测试可能暴露新问题。

重规划的触发条件包括：

- 子任务失败。
- 工具结果和预期不一致。
- 发现新约束。
- 成本或时间超预算。
- 当前计划无法继续。

重规划不是把所有东西推倒重来，而是基于当前状态修改后续步骤。系统要保留已经完成且可信的结果，只调整受影响部分。

---

# 5. 状态是什么

Agent 状态不是聊天历史。聊天历史是给模型看的上下文，状态是系统用来推进任务的数据结构。

常见状态包括：

- 用户目标。
- 当前阶段。
- 已完成步骤。
- 待办步骤。
- 工具调用结果。
- 已确认事实。
- 未解决问题。
- 风险和审批状态。
- 成本、轮次和时间预算。

状态越复杂，越需要结构化。否则模型每轮都要从长文本里重新推断当前进度，既贵又容易错。

---

# 6. 工作状态与长期记忆

要区分两类东西：

- 工作状态：当前任务进行到哪里，通常随任务结束而归档。
- 长期记忆：跨任务复用的偏好、知识、经验和项目背景。

把工作状态误当长期记忆，会让系统记住大量临时信息；把长期记忆当工作状态，又会让每个任务重复建立背景。

生产系统通常还会有审计日志。审计日志不是给模型每轮使用的，而是用于复盘、合规和评估。

---

# 7. 停止条件

Agent 必须知道何时停止。常见停止条件包括：

- 目标完成。
- 没有必要继续调用工具。
- 资料不足，需要向用户提问。
- 权限不足，需要人工审批。
- 关键工具失败且不可恢复。
- 达到最大轮次、最大 token、最大时间或最大成本。
- 检测到循环或重复动作。

停止不是失败。很多时候，可靠的 Agent 应该明确告诉用户“现在无法继续，因为缺少权限/证据/输入”，而不是继续猜。

---

# 8. 设计建议

如果任务简单，用 ReAct 或单步工具调用就够。

如果任务复杂但路径稳定，用 workflow 或状态机更可靠。

如果任务复杂且路径不完全固定，可以让模型参与规划，但关键状态、权限和停止条件仍由系统控制。

对于高风险任务，计划应先进入人工确认，再执行会改变外部状态的动作。
