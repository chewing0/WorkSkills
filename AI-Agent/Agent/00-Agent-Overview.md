# Agent 总览

Agent 最容易被误解成“会自己做事的聊天机器人”。这个说法只说对了一小半。真正有用的 Agent 不是让模型自由发挥，而是把模型放进一个可控执行系统里：模型负责理解、判断和生成行动意图；系统负责状态、权限、工具、校验、执行、观测和恢复。

如果说普通 LLM 应用的核心是“输入 -> 输出”，那么 Agent 应用的核心是“目标 -> 多步行动 -> 反馈 -> 状态更新 -> 达成或停止”。

---

# 1. Agent 到底是什么

一个最小 Agent 至少包含四个部分：

```text
目标：用户或系统想完成什么
状态：当前已经知道什么、做过什么、还缺什么
工具：能对外部世界做什么操作
策略：下一步如何选择，何时停止
```

LLM 在其中扮演的是“语义决策组件”，而不是整个系统。它可以把自然语言目标转成计划，可以选择工具，可以解释工具结果，可以判断是否继续。但它不应该直接拥有所有权限，也不应该独自决定高风险动作是否执行。

一句话：

> Agent = LLM + 状态 + 工具 + 反馈 + 控制边界。

---

# 2. Agent 与 Chatbot、RAG、Workflow 的区别

| 形态 | 核心能力 | 适合场景 | 局限 |
|---|---|---|---|
| Chatbot | 根据上下文生成回复 | 普通问答、陪伴、说明解释 | 通常不改变外部状态 |
| RAG | 检索证据后生成回答 | 知识库问答、引用溯源 | 重点是找证据，不一定行动 |
| Workflow | 按预设流程执行 | 稳定业务流程、审批、ETL | 灵活性有限 |
| Agent | 动态决定下一步并使用工具 | 多步任务、开放目标、工具协作 | 成本、风险、评估更复杂 |

很多业务其实不需要 Agent。固定路径能解决的问题，workflow 往往更可靠；知识问答能解决的问题，RAG 往往更清晰。Agent 适合那些路径不完全固定、需要模型动态判断下一步、并且确实需要调用工具或维护状态的任务。

---

# 3. Agent 的最小闭环

可以用这条链路理解 Agent：

```text
Observe -> Think/Plan -> Act -> Observe result -> Update state -> Stop or Continue
```

Observe 是读取当前输入、状态、工具结果和外部环境。没有观察，模型只能凭空猜。

Think/Plan 是判断下一步。它可以是一步 ReAct，也可以是完整任务分解，也可以是状态机中的节点选择。

Act 是行动。行动可能是调用搜索、查询数据库、执行代码、写文件、发 API 请求，也可能是请求人工确认。

Update state 是把行动结果写回系统状态。状态不能只藏在聊天历史里，否则恢复、审计和调试都会变难。

Stop 是判断任务是否完成、失败、超预算、需要人工，还是继续下一轮。

---

# 4. 什么时候值得用 Agent

适合用 Agent 的任务通常有这些特征：

- 目标明确，但路径不完全固定。
- 需要多步操作，而不是一次回答。
- 需要工具调用或外部系统交互。
- 中间结果会影响后续决策。
- 可能需要失败恢复、重试或人工确认。
- 需要在信息不足时主动补充检索、提问或分解任务。

例如：数据分析助手、代码修复助手、复杂客服处理、研究报告生成、运维排障、自动化办公、带审批的业务操作。

不适合 Agent 的任务：

- 单轮固定问答。
- 简单文本改写。
- 路径完全确定的业务流程。
- 高风险且无法校验的外部动作。
- 成本和延迟极敏感的场景。

---

# 5. Agent 的能力来源

Agent 的能力不是只来自模型大小，而来自多个层的组合：

- 模型能力：理解、生成、推理、工具参数生成。
- Prompt 设计：角色、目标、上下文、输出契约。
- 工具能力：检索、计算、API、代码执行、文件操作。
- 状态管理：任务进度、历史结果、长期记忆。
- 工作流控制：分支、循环、重试、停止。
- 安全边界：权限、沙箱、审计、人工审批。
- 评估反馈：trace、回归集、线上监控。

模型越强，Agent 上限越高；工程边界越清楚，Agent 下限越稳。

---

# 6. 常见失败模式

Agent 常见失败不是“不会说话”，而是“系统失控”。

第一类是规划失败。目标理解错、任务拆解错、下一步选择错，后面做得再努力也会偏离目标。

第二类是工具失败。工具选错、参数错、权限错、外部 API 超时，都会让结果不可靠。

第三类是状态失败。模型忘记已经做过什么，重复调用工具，或把未确认信息当事实。

第四类是停止失败。Agent 不知道何时结束，反复自我修正、重复检索、循环调用工具。

第五类是安全失败。Prompt injection、越权操作、敏感信息泄露、高风险动作未审批。

这些问题都不能只靠“换更强模型”解决，需要系统设计。

---

# 7. Agent 的设计原则

第一，先判断是否真的需要 Agent。能用固定 workflow 解决，就不要让模型自由决策。

第二，工具越危险，系统边界越要硬。模型生成工具调用意图，系统负责校验和执行。

第三，状态要显式。关键任务状态、工具结果、审批记录和失败原因要结构化保存。

第四，循环要有限。最大轮次、最大成本、最大时间、最大工具调用次数都要有边界。

第五，评估要看过程。Agent 的最终答案只是结果，trace 才能解释为什么走到那里。
