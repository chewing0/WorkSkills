# 什么是Redis

Redis是一个内存数据库，用作另一个“真实”数据库前面的缓存，已帮助提高应用程序性能。通过利用内存的高速访问熟读，从而减轻核心应用程序数据库的负载。
- 缓存数据：商品信息缓存、文章详情缓存等
- 临时数据：验证码、邮箱验证码、登录token等
- 会话数据：用户登录session、在线状态等
- 计数器数据：浏览量、点赞量等
- 排行榜数据
- 限流数据
- 分布式锁
- 队列数据
- 集合关系数据
- 去重统计数据
==高频访问、高频变化、短期有效、允许丢失或可重建==

# Redis架构

## 单个Redis实例

单机 Redis 是最简单的部署方式，适合小型系统和缓存场景。它部署简单、性能高，但缺点是没有高可用能力，一旦这个 Redis 实例挂了，所有依赖它的请求都会失败。Redis 的数据主要在**内存**中处理，所以速度很快；如果需要防止重启后数据丢失，可以开启 **RDB 或 AOF 持久化**，把数据保存到磁盘。Redis 重启后，会从 RDB 或 AOF 文件中恢复数据到内存，然后继续对外提供服务。

RDB：Redis Database Backup
**原理：** 在指定的时间间隔内，将内存中的数据集**快照**写入磁盘，生成一个 `.rdb` 文件。
**特点：**
- 文件紧凑，体积小，适合备份和灾难恢复
- 恢复速度快（直接加载快照文件到内存）
- 但可能丢失最后一次快照之后的数据（如果突然宕机）

AOF：Append Only File
**原理：** 将 Redis 执行的**每一条写命令**追加到日志文件中，重启时重新执行这些命令来恢复数据。
**特点：**
- 数据安全性更高，默认每秒同步一次，最多丢失 1 秒数据
- 文件体积通常比 RDB 大
- 恢复速度比 RDB 慢（需要逐条重放命令）
- 支持重写机制（`BGREWRITEAOF`）压缩文件

fork进程：Redis主进程还要继续处理客户端请求。复制出一个子进程，让子进程去做比较耗时的磁盘写入工作。

### Q1：如果没有开启持久化，会怎么样？
数据会丢失，如果丢失的是验证码、session、计数器、队列任务，需要考虑是否会影响业务。

## Redis高可用性

当某个 Redis 实例宕机、重启、网络异常时，系统仍然尽可能继续提供 Redis 服务，而不是整个缓存/数据服务直接不可用。
```
主 Redis 挂了
    ↓
备用 Redis 自动接管
    ↓
客户端继续访问新的 Redis 主节点
```

### 主从复制

主节点执行完之后，会把这些修改数据的命令同步给从节点。从节点接收到之后，也执行同样的命令，于是数据就逐渐和主节点一致。
```
客户端写入主节点
   ↓
主节点执行成功
   ↓
主节点返回成功给客户端
   ↓
主节点之后把写命令同步给从节点
```
Redis 复制速度快、延迟低，但代价是：**主从之间可能存在短暂数据不一致，这有可能导致数据丢失**。官方文档也说明，Redis 默认使用异步复制，主节点不会每次都等待副本处理完成再继续。

**第一次同步：全量同步**
如果一个从节点刚启动，或者第一次连接主节点，它没有主节点的数据。这时需要做**全量同步**。
```
从节点连接主节点
   ↓
主节点生成一份当前数据快照
   ↓
主节点把快照发送给从节点
   ↓
从节点加载这份数据
   ↓
主节点再把同步期间产生的新写命令继续发给从节点
```
官方文档描述全量同步时，主节点会在后台生成 RDB 文件，同时缓冲新的写命令；RDB 传给副本并加载后，再把缓冲的命令发给副本。

**后续同步：增量同步**
当主从已经同步完成后，主节点后面发生的写操作，会持续同步给从节点。
```
INCR article:1:views
SET user:2 lisi
DEL session:abc
```
主节点执行这些命令后，会把命令流发送给从节点。从节点执行同样的命令，数据就继续保持接近一致。
官方文档还说明，主从节点连接中断后，副本会尝试部分重同步；如果不能部分重同步，就会请求全量重同步。

### 哨兵模式

Redis 官方文档对 Sentinel 的定位是：在不使用 Redis Cluster 的情况下，为 Redis 提供高可用能力；它负责**监控、通知、自动故障转移**，并且可以作为**客户端获取当前主节点地址**的配置提供者。解决的是**服务可用性问题**，仍然存在数据丢失可能，原理部分可以看出。
```
主从复制里，主节点挂了以后，谁来判断它真的挂了？
谁来把从节点提升为新的主节点？
谁来通知客户端新的主节点地址？
```

**核心功能：**
- **监控**：持续检查主节点、从节点是否正常运行
- **通知**：节点异常时，通过 API 向管理员或应用发送告警
- **发现故障**：如果超过设定quorum数量的哨兵认为主节点挂了，则主节点进入故障状态
- **自动故障转移**：主节点宕机时，自动选举一个从节点晋升为主节点，并通知其他从节点切换复制目标
- **配置中心**：客户端向哨兵询问当前主节点地址，无需硬编码 IP

**故障转移流程：**
```
1. Sentinel 持续监控主节点、从节点
2. 主节点没有响应
3. 一个 Sentinel 判断主节点主观下线
4. 多个 Sentinel 达成一致，认为主节点客观下线
5. Sentinel 之间选出一个 leader
6. leader 从从节点里选择一个最合适的节点
7. 把这个从节点提升为新的主节点
8. 让其他从节点复制新的主节点
9. 通知客户端新的主节点地址
```

**部署建议：**
- 哨兵节点至少部署 **3 个**（奇数个），避免脑裂和选举死锁
- 哨兵节点应部署在独立的服务器上，不要和 Redis 数据节点混布

### 集群模式

Redis Cluster 解决的是：
```
数据太多，一个 Redis 放不下
请求太多，一个 Redis 扛不住
希望 Redis 节点故障后能自动恢复
```
一个典型 Redis Cluster 至少会有多个主节点，每个主节点再配一个或多个从节点。Redis 官方文档也说明，Redis Cluster 使用 master-replica 模型，每个 hash slot 由一个主节点负责，并且可以有副本节点在故障时接替。
```
HASH_SLOT = CRC16(key) mod 16384

主节点 A：负责 slot 0 - 5500
主节点 B：负责 slot 5501 - 11000
主节点 C：负责 slot 11001 - 16383
```
#### Q2：为什么要用 slot，而不是直接按节点取模？
因为节点数量可能会变化。比如一开始有 3 个主节点，后来要扩容成 4 个主节点。如果直接按节点数量取模：
```
hash(key) % 3
变成
hash(key) % 4
```
大量 key 的位置都会变化，迁移成本很高。Redis Cluster 使用固定的 16384 个 slot，扩容时只需要迁移一部分 slot。
```
原来：
A：0 - 5500
B：5501 - 11000
C：11001 - 16383

新增 D 后：
A 分一些 slot 给 D
B 分一些 slot 给 D
C 分一些 slot 给 D
```

**Redis Cluster 是 Redis 的分布式集群方案，它把数据拆成 16384 个 hash slot，分布到多个主节点上；每个主节点可以有从节点，在主节点故障时由从节点接管。**
```
Cluster = 数据分片 + 主从复制 + 自动故障转移

Cluster 不等于强一致，也不适合单独保存绝对不能丢的核心业务数据
```

#### 集群模式健康检查

```
1. 节点之间能不能互相通信
2. 是否有节点被判定为故障
3. 16384 个 hash slot 是否都有正常节点负责
```

1、节点之间通过cluster bus通信
通常是Redis服务端口+10000。Redis 官方文档说明，Cluster Bus 是节点之间的通信通道，用于 failure detection、configuration updates、failover authorization 等事情。

2、节点之间会互相发送PING/PONG
```
节点 A 问节点 B：你还活着吗？PING
节点 B 回复节点 A：我还活着。PONG

我知道哪些节点
我认为哪些节点正常
我认为哪些节点可能故障
我负责哪些 hash slot
我的 cluster_state 是 ok 还是 fail
```
官方 Cluster 规范说明，PING 和 PONG 包中包含节点 ID、epoch、节点 flags、节点负责的 hash slots、cluster port、发送者视角下的 cluster state 等信息，并且还包含 gossip section，用来传播其他节点状态。

3、如果某个节点长时间不响应，设置为PFALL（Possible Failure）（本地认为故障）
Redis 官方文档说明：当一个节点超过 `NODE_TIMEOUT` 时间不可达时，另一个节点会把它标记为 `PFAIL`；`PFAIL` 表示 Possible failure，是一种尚未确认的故障状态。

4、多数主节点都认为它有问题，升级为 FAIL
官方规范说明，`PFAIL` 升级为 `FAIL` 需要收集到多数 master 的故障报告；满足条件后，节点会把目标节点标记为 `FAIL`，并向其他可达节点发送 `FAIL` 消息。

5、节点故障后，故障转移
Redis 官方文档说明，Cluster 使用 master-replica 模型，每个 hash slot 由 master 负责，并可以有 replica；当 master 不可达时，如果有可用 replica，集群可以通过提升 replica 来继续服务。

```
节点之间能通信吗？
   ↓
有没有节点超过超时时间不响应？
   ↓
是否只是 PFAIL，还是多数 master 确认 FAIL？
   ↓
如果 master FAIL，有没有 replica 可以接管？
   ↓
16384 个 hash slot 是否都能被正常服务？
   ↓
当前节点能不能连接到多数 master？
   ↓
cluster_state 是 ok 还是 fail
```
